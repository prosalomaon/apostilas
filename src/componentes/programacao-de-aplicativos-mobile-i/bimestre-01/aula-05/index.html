Teoria & Conceitos

1. O Conceito de Ciclo de Vida

No Android, as aplicações são organizadas em torno de Activities, que representam telas com interface gráfica. Diferente de programas desktop tradicionais, onde o controle do fluxo pertence ao usuário, o sistema Android tem controle total sobre o início, a suspensão e o encerramento das atividades.

Isso acontece porque:

  • O Android precisa gerenciar a memória de forma eficiente, pois dispositivos móveis têm recursos limitados.
  • Chamadas telefônicas, notificações e mudanças de orientação podem interromper o app a qualquer momento.
  • O sistema pode destruir Activities em segundo plano para liberar memória para apps em primeiro plano.

Para lidar com essa realidade, o desenvolvedor sobrescreve callbacks — métodos especiais chamados automaticamente pelo sistema em momentos específicos do ciclo de vida. É através desses callbacks que realizamos ações como carregar dados, pausar animações, salvar estado e liberar recursos.

2. Os Estados e Callbacks Principais

Uma Activity passa por três estados principais durante sua existência. Cada transição entre estados dispara um ou mais callbacks:

A. Estado: Ativo (Running)

A Activity está em primeiro plano e o usuário pode interagir com ela. Este é o único estado em que o app está totalmente ativo.

B. Estado: Pausado (Paused)

A Activity ainda está visível, mas parcialmente coberta por outra Activity transparente ou por um diálogo. Ela ainda mantém conexão com o gerenciador de janelas, mas não recebe entradas do usuário.

C. Estado: Parado (Stopped)

A Activity está completamente invisível para o usuário. Ela permanece na pilha de memória, mas o sistema pode reclassificá-la como "descartável" se precisar liberar memória.

Callbacks e Ordem de Execução

Callback Momento Uso Recomendado
onCreate() Activity criada pela primeira vez. Definir layout, inicializar variáveis, vincular dados.
onStart() Activity prestes a se tornar visível. Registrar listeners, iniciar animações leves.
onResume() Activity em primeiro plano, pronta para interação. Atualizar dados, retomar sensores, iniciar câmera.
onPause() Activity prestes a perder o foco. Salvar dados temporários, pausar animações.
onStop() Activity completamente invisível. Salvar dados persistentes, liberar recursos pesados.
onRestart() Activity parada está prestes a ser reiniciada. Reiniciar operações pausadas no onStop().
onDestroy() Activity prestes a ser destruída. Liberar memória, encerrar threads, desregistrer listeners.

3. Fluxo Completo do Ciclo de Vida

A sequência completa de callbacks varia dependendo da ação que o usuário ou o sistema executa. Veja os cenários mais comuns:

A. Primeira Inicialização do App

onCreate() → onStart() → onResume()  → [App ativo e interativo]

B. Botão Voltar Pressionado

[App ativo] → onPause() → onStop() → onDestroy()

C. Chamada Telefônica ou Notificação

[App ativo] → onPause() → onStop()
... (usuário atende e depois retorna) ...
onRestart() → onStart() → onResume()

D. Rotação da Tela (Mudança de Orientação)

[App ativo] → onPause() → onStop() → onDestroy()
→ onCreate() → onStart() → onResume()

Este é o cenário mais crítico: a Activity é destruída e recriada do zero. Sem a persistência de estado via Bundle, todos os dados temporários da interface seriam perdidos.

E. App Enviado para Segundo Plano (Home Button)

[App ativo] → onPause() → onStop()
... (usuário retorna ao app) ...
onRestart() → onStart() → onResume()

4. Persistência de Estado e o Objeto Bundle

O sistema pode destruir uma Activity a qualquer momento — especialmente durante rotação de tela ou quando o dispositivo fica sem memória. Para evitar a perda de dados da interface, utilizamos o método onSaveInstanceState().

A. Como Funciona o Bundle

  • O Bundle é um objeto chave-valor que armazena dados primitivos (Strings, Integers, Booleans, etc.).
  • Quando a Activity é destruída, o sistema salva o Bundle automaticamente.
  • Quando a Activity é recriada, o Bundle é entregue ao onCreate(savedInstanceState) como parâmetro.
  • Se não houver dados salvos (primeira execução), o parâmetro savedInstanceState será null.

B. Salvando e Recuperando Dados

class MainActivity : AppCompatActivity() {

    override fun onCreate(savedInstanceState: Bundle?) {
        super.onCreate(savedInstanceState)
        setContentView(R.layout.activity_main)

        // Recuperando dados salvos anteriormente
        savedInstanceState?.let { bundle ->
            val nome = bundle.getString("chave_nome") ?: "Usuário"
            val pontuacao = bundle.getInt("chave_pontuacao", 0)
            // Utilizar os dados recuperados na interface
        }
    }

    override fun onSaveInstanceState(outState: Bundle) {
        super.onSaveInstanceState(outState)
        // Salvando dados antes da destruição
        outState.putString("chave_nome", "João")
        outState.putInt("chave_pontuacao", 1500)
    }
}

C. onRestoreInstanceState()

Além do onCreate(), existe o onRestoreInstanceState(), chamado apenas quando o Bundle não é nulo (ou seja, quando a Activity está sendo recriada, não na primeira execução). 

override fun onRestoreInstanceState(savedInstanceState: Bundle) {
    super.onRestoreInstanceState(savedInstanceState)
    // O Bundle nunca é nulo aqui
    val nome = savedInstanceState.getString("chave_nome")
}

D. O que Salvar no Bundle

Dado Salvar no Bundle? Motivo
Texto digitado em um campo Sim Evita que o usuário precise digitar novamente.
Posição de scroll Sim Mantém a posição visual ao retornar.
ID do item selecionado Sim Preserva a seleção do usuário.
Referência a um Context ou View Não Objetos Android não são serializáveis no Bundle.
Dados de rede (API response) Não Deve ser recarregado da fonte original ao recriar a Activity.
Bitmaps grandes Não O Bundle tem limite de tamanho (~1MB); cause TransactionTooLargeException.

5. Ciclo de Vida no Jetpack Compose

No Jetpack Compose, o ciclo de vida da Activity continua funcionando da mesma forma. No entanto, a recomposição das funções @Composable é gerenciada separadamente. Para integrar o ciclo de vida com Compose, utilize o LifecycleObserver: 

class MyLifecycleObserver : LifecycleEventObserver {
    override fun onStateChanged(source: LifecycleOwner, event: Lifecycle.Event) {
        when (event) {
            Lifecycle.Event.ON_RESUME -> {
                // App voltou para primeiro plano
            }
            Lifecycle.Event.ON_PAUSE -> {
                // App foi pausado
            }
            Lifecycle.Event.ON_DESTROY -> {
                // Activity será destruída
            }
            else -> {}
        }
    }
}

// Registrar o observer na Activity
class MainActivity : ComponentActivity() {
    override fun onCreate(savedInstanceState: Bundle?) {
        super.onCreate(savedInstanceState)
        lifecycle.addObserver(MyLifecycleObserver())
        setContent {
            // UI Compose aqui
        }
    }
}

Laboratório Prático: Monitor de Ciclo de Vida

Vamos criar um app simples que exibe na tela qual callback está sendo executado em tempo real, permitindo visualizar o ciclo de vida ao interagir com o dispositivo.

1. Estrutura do Código

// MainActivity.kt
class MainActivity : ComponentActivity() {

    private var logEntries = mutableStateListOf<String>()

    override fun onCreate(savedInstanceState: Bundle?) {
        super.onCreate(savedInstanceState)
        addLog("onCreate() — Activity criada")

        // Recuperar dados salvos (se houver)
        savedInstanceState?.let { bundle ->
            val count = bundle.getInt("counter", 0)
            addLog("  ↳ Dados recuperados: counter = $count")
        }

        setContent {
            LifecycleScreen(logs = logEntries)
        }
    }

    override fun onStart() {
        super.onStart()
        addLog("onStart() — Activity visível")
    }

    override fun onResume() {
        super.onResume()
        addLog("onResume() — Activity em primeiro plano")
    }

    override fun onPause() {
        super.onPause()
        addLog("onPause() — Activity perdendo foco")
    }

    override fun onStop() {
        super.onStop()
        addLog("onStop() — Activity invisível")
    }

    override fun onRestart() {
        super.onRestart()
        addLog("onRestart() — Retornando de stopped")
    }

    override fun onDestroy() {
        super.onDestroy()
        addLog("onDestroy() — Activity destruída")
    }

    override fun onSaveInstanceState(outState: Bundle) {
        super.onSaveInstanceState(outState)
        outState.putInt("counter", logEntries.size)
        addLog("  ↳ onSaveInstanceState: counter salvo (${logEntries.size})")
    }

    private fun addLog(message: String) {
        logEntries.add(message)
    }
}

2. Tela de Exibição

// LifecycleScreen.kt
@Composable
fun LifecycleScreen(logs: List<String>) {
    Column(
        modifier = Modifier
            .fillMaxSize()
            .padding(16.dp)
    ) {
        Text(
            text = "Monitor de Ciclo de Vida",
            style = MaterialTheme.typography.headlineMedium
        )
        Spacer(modifier = Modifier.height(8.dp))
        Text(
            text = "Gire a tela, envie para 2º plano, ou volte para observar os callbacks.",
            style = MaterialTheme.typography.bodyMedium,
            color = MaterialTheme.colorScheme.onSurfaceVariant
        )
        Spacer(modifier = Modifier.height(16.dp))

        LazyColumn(
            modifier = Modifier.fillMaxSize()
        ) {
            items(logs) { entry ->
                Text(
                    text = entry,
                    fontFamily = FontFamily.Monospace,
                    fontSize = 13.sp,
                    modifier = Modifier.padding(vertical = 2.dp)
                )
            }
        }
    }
}

Execute o app e teste: gire a tela, pressione o botão Home, abra uma notificação e volte ao app. Observe a sequência de callbacks exibida na tela.

Dicas & Lembretes

1. Sempre Chame super

Ao sobrescrever qualquer callback de ciclo de vida, lembre de chamar super.onXxx() como primeira linha. Sem isso, o comportamento padrão do sistema é comprometido e erros silenciosos podem ocorrer.

2. onPause() é Crítico

O onPause() é o único callback garantido a ser chamado em todas as situações (exceto quando a Activity é finalizada com finish()). Sempre salve dados importantes aqui.

3. Evite Trabalho Pesado no onPause()

O onPause() deve ser rápido, pois a próxima Activity não será exibida até que ele termine. Operações pesadas (salvar no banco, enviar dados) devem ser feitas no onStop().

4. Bundle Tem Limite de Tamanho

O Bundle tem um limite de aproximadamente 1MB. Salvar Bitmaps ou listas grandes pode causar TransactionTooLargeException. Para dados grandes, utilize ViewModel ou banco de dados local.

5. ViewModel ≠ Ciclo de Vida

O ViewModel sobrevive às mudanças de configuração (rotação) sem precisar do Bundle. Use-o para dados que devem persistir durante a vida útil da Activity, e o Bundle apenas para dados de restauração de estado da interface.
