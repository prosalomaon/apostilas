Teoria & Conceitos

1. A Hierarquia de Pastas (Visão "Android")

Quando você cria um novo projeto no Android Studio, o IDE gera automaticamente uma estrutura de pastas padronizada. No modo de exibição "Android" (o padrão do IDE), os arquivos são organizados de forma lógica para facilitar a navegação do desenvolvedor. Entender essa estrutura é essencial para saber onde colocar cada tipo de arquivo.

A. Pasta manifests

Contém o arquivo AndroidManifest.xml, que funciona como a "carteira de identidade" do aplicativo. É aqui que o sistema Android descobre quais componentes (Activities, Services) o app possui, quais permissões ele requer e qual é a tela inicial exibida ao usuário.

B. Pasta java (ou kotlin/java)

Armazena todos os arquivos de código-fonte organizados por pacotes (namespaces). No padrão moderno, esta pasta contém tanto código Kotlin quanto Java quando necessário. Aqui residem:

  • Activities: Classes que representam telas do app.
  • ViewModels: Classes que gerenciam dados e lógica de negócio.
  • Repositorys: Classes que abstraem fontes de dados.
  • Outras classes: Modelos, utilitários, adaptadores, etc.

C. Pasta res (Resources)

Guarda todos os recursos não codificados do projeto. É a pasta mais diversificada e inclui:

  • layout/: Arquivos XML que definem a interface do usuário (ex: activity_main.xml). No Jetpack Compose, esta pasta é menos utilizada, pois a UI é definida diretamente no código Kotlin.
  • drawable/: Imensagens, ícones e vetores gráficos (PNG, SVG, XML vector).
  • values/: Arquivos de configuração de valores:
    • strings.xml: Centraliza todos os textos do app (facilita tradução e manutenção).
    • colors.xml: Define as cores utilizadas no tema.
    • themes.xml: Configura o tema visual global do app.
  • mipmap/: Ícones do aplicativo em diferentes densidades (launcher icons).

D. Pasta Gradle Scripts

Contém os arquivos de configuração do sistema de build. Não aparece na visão "Android" padrão, mas pode ser acessada na visão "Project". Inclui os arquivos build.gradle.kts (ou build.gradle) do projeto e do módulo.

2. O Manifesto do Aplicativo (AndroidManifest.xml)

O AndroidManifest.xml é o arquivo mais importante para a configuração do app. Ele informa ao sistema Android tudo o que o aplicativo precisa para funcionar corretamente.

A. Declaração de Componentes

Toda Activity, Service, ContentProvider ou BroadcastReceiver deve ser registrada no manifesto. Sem essa declaração, o sistema não consegue iniciar o componente. 

<application
    android:allowBackup="true"
    android:icon="@mipmap/ic_launcher"
    android:label="@string/app_name"
    android:theme="@style/Theme.MyApp">

    <activity
        android:name=".MainActivity"
        android:exported="true">
        <intent-filter>
            <action android:name="android.intent.action.MAIN" />
            <category android:name="android.intent.category.LAUNCHER" />
        </intent-filter>
    </activity>

    <activity android:name=".DetailActivity" />

</application>

B. Permissões

Antes de acessar recursos do dispositivo (câmera, internet, localização), o app precisa declarar a permissão correspondente no manifesto. No Android 6.0+, muitas permissões são solicitadas ao usuário em tempo de execução. 

<!-- Permissões declaradas fora do <application> -->
<uses-permission android:name="android.permission.INTERNET" />
<uses-permission android:name="android.permission.CAMERA" />
<uses-permission android:name="android.permission.ACCESS_FINE_LOCATION" />

<application ...>
    ...
</application>

C. Metadados do App

O manifesto também define informações visuais e comportamentais do app, como o nome exibido na loja, o ícone do launcher e o tema visual aplicado.

  • android:label: Nome exibido ao usuário (geralmente referencia @string/app_name).
  • android:icon: Ícone do aplicativo no launcher e na loja.
  • android:theme: Tema visual base aplicado a todas as Activities.

D. O Intent Filter

Dentro de uma declaração de Activity, o <intent-filter> define como o sistema deve reagir a intents. A combinação MAIN + LAUNCHER indica que aquela Activity é a tela inicial do app, exibida quando o usuário toca no ícone.

3. O Sistema de Build Gradle

O Gradle é a ferramenta automatizada responsável por compilar o código Kotlin/Java, gerenciar dependências de terceiros, aplicar plugins e gerar o arquivo final de instalação (APK ou AAB). Um projeto Android possui dois arquivos principais de configuração.

A. build.gradle.kts (Project-Level)

Localizado na raiz do projeto, define configurações globais que afetam todos os módulos. Gereciencia versões de plugins e repositórios de bibliotecas. 

// build.gradle.kts (Project - raiz)
plugins {
    id("com.android.application") version "8.2.2" apply false
    id("org.jetbrains.kotlin.android") version "1.9.22" apply false
}

allprojects {
    repositories {
        google()
        mavenCentral()
    }
}

B. build.gradle.kts (Module: app)

Localizado dentro da pasta app/, é o arquivo mais utilizado pelo desenvolvedor. Aqui são definidas as dependências do módulo, a versão do SDK e as configurações de compilação. 

// build.gradle.kts (Module: app)
plugins {
    id("com.android.application")
    id("org.jetbrains.kotlin.android")
}

android {
    namespace = "com.example.meuapp"
    compileSdk = 34

    defaultConfig {
        applicationId = "com.example.meuapp"
        minSdk = 24
        targetSdk = 34
        versionCode = 1
        versionName = "1.0"
    }

    buildTypes {
        release {
            isMinifyEnabled = false
            proguardFiles(
                getDefaultProguardFile("proguard-android-optimize.txt"),
                "proguard-rules.pro"
            )
        }
    }

    compileOptions {
        sourceCompatibility = JavaVersion.VERSION_17
        targetCompatibility = JavaVersion.VERSION_17
    }

    kotlinOptions {
        jvmTarget = "17"
    }
}

dependencies {
    implementation("androidx.core:core-ktx:1.12.0")
    implementation("androidx.activity:activity-compose:1.8.2")
    implementation(platform("androidx.compose:compose-bom:2024.02.00"))
    implementation("androidx.compose.ui:ui")
    implementation("androidx.compose.material3:material3")
    implementation("androidx.navigation:navigation-compose:2.8.3")
}

C. Campos Essenciais do build.gradle (Module)

Campo Função
applicationId Identificador único do app na Play Store (não pode ser alterado após o primeiro upload).
minSdk Versão mínima do Android suportada pelo app (ex: 24 = Android 7.0).
targetSdk Versão do Android para a qual o app foi otimizado (afeta comportamentos de segurança).
compileSdk Versão do SDK usada durante a compilação (deve ser igual ou superior ao targetSdk).
versionCode Número interno incrementado a cada versão (usado pela Play Store para identificar atualizações).
versionName Nome da versão exibido ao usuário (ex: "1.0.0").

D. Gerenciamento de Dependências

As dependências são bibliotecas de terceiros que o projeto utiliza. Cada linha no bloco dependencies segue o padrão: 

implementation("grupo:nome:versão")

// Exemplos:
implementation("androidx.core:core-ktx:1.12.0")
//              ↑ grupo          ↑ nome      ↑ versão

implementation("com.google.code.gson:gson:2.10.1")
//              ↑ biblioteca externa do Google

Osescopo de dependência mais comuns:

  • implementation: A biblioteca está disponível apenas dentro do módulo atual.
  • api: A biblioteca é exposta também para módulos que dependem deste (menos recomendado).
  • compileOnly: A biblioteca é usada apenas na compilação, não é incluída no APK final.
  • testImplementation: A biblioteca é usada apenas em testes unitários.

4. Ciclo de Vida e Integração

Compreender a estrutura de pastas é o primeiro passo para entender o Ciclo de Vida de um App, pois cada arquivo tem um momento específico de carregamento e execução pelo sistema Android.

A ordem de carregamento ao iniciar um app é:

  1. O sistema Android lê o AndroidManifest.xml para descobrir qual Activity possui o intent-filter MAIN + LAUNCHER.
  2. A Activity principal é instanciada e o método onCreate() é chamado.
  3. Dentro de onCreate(), o método setContentView(R.layout.activity_main) carrega o layout XML da pasta res/layout/ e injeta na tela.
  4. No Jetpack Compose, em vez de XML, o método setContent { } executa funções Compose que desenham a interface diretamente no código Kotlin.

Essa separação entre código (java/) e interface (res/ ou Compose) permite que o app seja flexível, adaptando-se a diferentes tamanhos de tela e configurações de hardware.

Aspecto build.gradle.kts (Project) build.gradle.kts (Module: app)

Quem edita? Geralmente apenas ao criar o projeto ou atualizar versões globais. O desenvolvedor edita constantemente.

Dicas & Lembretes

1. Centralize Textos no strings.xml

Nunca escreva textos diretamente no código Kotlin ou nos layouts XML. Use sempre @string/nome_do_texto. Isso facilita a tradução para outros idiomas e a manutenção futura.

2. O applicationId é Imutável

Uma vez que o app é publicado na Play Store com um applicationId, ele nunca mais pode ser alterado. Se precisar criar uma versão "free" e "pro", use applicationIds diferentes (ex: com.empresa.app.free e com.empresa.app.pro).

3. Versões LTS vs. bleeding-edge

Em ambiente educacional, prefira sempre as versões estáveis (LTS) do SDK e das dependências. Evite usar versões alpha ou beta, que podem conter bugs e mudanças incompatíveis.

4. Nunca Edite o Manifesto sem Entender

Erros no AndroidManifest.xml podem causar crashes que o app não consegue iniciar. Sempre que alterar o manifesto, teste o app imediatamente para verificar se ele ainda abre corretamente.

5. sync é Obrigatório

Após alterar qualquer arquivo build.gradle.kts, clique em "Sync Now" no banner que aparece no topo do Android Studio. Sem o sync, as alterações não entram em vigor e o projeto pode não compilar.
