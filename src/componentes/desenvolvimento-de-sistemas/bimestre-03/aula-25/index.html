Teoria & Conceitos

1. O que é Persistência?

O armazenamento de informações de forma que elas sobrevivam ao encerramento da execução de um programa é chamado de persistência. Sem ela, os dados ficam restritos à memória volátil (RAM) e são perdidos assim que a aplicação termina. Por isso, sistemas reais gravam seus dados em bancos de dados relacionais (MySQL, PostgreSQL, Oracle, SQL Server, entre outros).

2. O que é JDBC?

Em Java, a principal biblioteca para interagir com bancos de dados relacionais é o JDBC (Java Database Connectivity), que consiste em um conjunto de interfaces contidas no pacote java.sql. O JDBC define um "contrato" único: a aplicação fala com o banco apenas por essas interfaces, sem depender de detalhes proprietários de cada SGBD.

3. O Driver JDBC: o "tradutor"

O Driver JDBC funciona como um "tradutor" entre o código Java e o protocolo proprietário de cada banco de dados (MySQL, Oracle, PostgreSQL, etc.). A API fornece a interface, mas a implementação concreta vem do driver, que normalmente é distribuído como um arquivo .jar.

flowchart LR A["Aplicação Java\n(código JDBC)"] -->|"interfaces java.sql"| B["Driver JDBC\n(arquivo .jar)"] B -->|"protocolo proprietário"| C["SGBD\n(MySQL / PostgreSQL / Oracle)"]

4. Portabilidade

A API JDBC é portátil: o mesmo código Java consegue manipular diferentes bancos de dados, desde que o driver correto seja fornecido. A única parte que muda é a URL de conexão, que identifica qual driver e qual banco serão utilizados.

Conectando ao Banco: A Anatomia da Conexão

Para estabelecer uma conexão, a classe DriverManager utiliza uma String de Conexão (URL), além de um usuário e senha. A URL segue o formato protocolo:subprotocolo://endereco:porta/nome_do_banco:

flowchart LR A["jdbc:mysql://localhost:3306/agenda_contatos"] A --> B["protocolo: jdbc"] A --> C["subprotocolo: mysql\n(identifica o driver)"] A --> D["endereço + porta\n(localhost:3306)"] A --> E["nome do banco\n(agenda_contatos)"] 
import java.sql.Connection;
import java.sql.DriverManager;
import java.sql.SQLException;

public class ExemploConexao {
    public static void main(String[] args) {
        // URL no formato: protocolo:subprotocolo://endereco:porta/nome_do_banco
        String url = "jdbc:mysql://localhost:3306/agenda_contatos";

        try (Connection conexao = DriverManager.getConnection(url, "root", "senha")) {
            System.out.println("Conectado ao banco de dados!");
        } catch (SQLException e) {
            // SQLException é uma exceção do tipo checked
            e.printStackTrace();
        }
    }
}

Observe dois detalhes importantes: a conexão é aberta dentro de um bloco try-with-resources (que a fechará automaticamente) e o erro é uma SQLException, uma exceção checked — ou seja, o compilador obriga você a tratá-la ou repassá-la.

Executando Comandos SQL

Existem duas formas principais de enviar comandos ao banco: Statement e PreparedStatement. A recomendação prática é quase sempre o PreparedStatement.

1. Statement: o perigo da concatenação

O Statement comum monta o SQL por concatenação de strings. Além de difícil de ler, ele é vulnerável a SQL Injection — o texto digitado pelo usuário vira parte do comando executável: 

// MODO ERRADO: concatenação de strings
String sql = "SELECT * FROM contatos WHERE nome = '" + nomeUsuario + "'";

// Se nomeUsuario = "'; DROP TABLE contatos; --"
// o comando executado passa a ser (catastrófico!):
// SELECT * FROM contatos WHERE nome = ''; DROP TABLE contatos; --'

2. PreparedStatement: a prática recomendada

Diferente do Statement, o PreparedStatement cria instruções SQL pré-compiladas com parâmetros, indicados pelo caractere ?.

  • Segurança: É a principal defesa contra SQL Injection, pois trata a entrada do usuário estritamente como dado, não como parte do comando executável.
  • Performance: É mais eficiente para instruções executadas múltiplas vezes com valores diferentes, pois o SQL é compilado uma única vez.
String sql = "INSERT INTO contatos (nome, email) VALUES (?, ?)";

try (Connection conexao = DriverManager.getConnection(url, "root", "senha");
     PreparedStatement stmt = conexao.prepareStatement(sql)) {

    stmt.setString(1, "João Silva"); // preenche o primeiro '?'
    stmt.setString(2, "joao@email.com");
    stmt.executeUpdate();            // usado para INSERT, UPDATE e DELETE
}

Repare que o valor é passado via setString(posicao, valor): o Java envia o conteúdo como dado e o banco nunca o interpreta como sintaxe.

flowchart TD A[Entrada do usuário] --> B{Como montar o SQL?} B -->|"Statement + concatenação"| C["SQL é reescrito\n(risco de SQL Injection)"] B -->|"PreparedStatement"| D["Valor enviado como dado\n(posições ? pré-compiladas)"] C --> E[("Dados vulneráveis")] D --> F[("Consulta segura")]

3. ResultSet: recuperando dados

Para consultas (SELECT), utilizamos o método executeQuery(), que retorna um objeto ResultSet. Ele permite navegar pelos registros através do método next(), que avança uma linha por vez e retorna false quando não há mais registros: 

String sql = "SELECT id, nome, email FROM contatos WHERE nome LIKE ?";

try (PreparedStatement stmt = conexao.prepareStatement(sql)) {
    stmt.setString(1, "%" + termoBusca + "%");

    try (ResultSet rs = stmt.executeQuery()) {
        while (rs.next()) {
            int id = rs.getInt("id");
            String nome = rs.getString("nome");
            String email = rs.getString("email");
            System.out.println(id + " - " + nome + " - " + email);
        }
    }
}

Os valores das colunas podem ser lidos pelo nome da coluna (como no exemplo) ou pelo índice — mas atenção: diferente dos arrays de Java, que começam em 0, as colunas do ResultSet e os parâmetros do PreparedStatement começam em 1.

Boas Práticas: Exceções e Gerenciamento de Recursos

1. Relançando SQLException como RuntimeException

Uma prática comum é capturar a SQLException (checked) e relançá-la como uma RuntimeException (unchecked), evitando que a API JDBC "vaze" pelas demais camadas do sistema e desacople o código de negócio da implementação de banco de dados. 

public void salvar(Contato contato) {
    String sql = "INSERT INTO contatos (nome, email) VALUES (?, ?)";

    try (Connection conexao = Conexao.abrir();
         PreparedStatement stmt = conexao.prepareStatement(sql)) {

        stmt.setString(1, contato.getNome());
        stmt.setString(2, contato.getEmail());
        stmt.executeUpdate();

    } catch (SQLException e) {
        // relança como unchecked para não acoplar as camadas superiores
        throw new RuntimeException("Erro ao salvar contato", e);
    }
}

2. Fechando recursos sempre

Recursos "caros" como conexões devem ser fechados o mais rápido possível. O uso do bloco finally ou da instrução try-with-resources (Java 7+) garante que a conexão será encerrada mesmo em caso de erro — como ocorre em todos os exemplos desta aula.

flowchart TD A[Início do try-with-resources] --> B[Abre a conexão] B --> C[Executa a instrução SQL] C --> D{Erro?} D -->|Não| E[Fecha recursos automaticamente] D -->|Sim| F[Catch trata a exceção] F --> E

Padrão DAO: Separando a Persistência do Negócio

Misturar código SQL com a lógica de negócio torna o sistema difícil de manter. A solução é o padrão DAO (Data Access Object), que isola todo o acesso ao banco em classes específicas. Com ele, a camada de negócio conhece apenas a interface, não os detalhes do JDBC.

flowchart TB subgraph App ["Camadas da aplicação"] A["Controller / View"] --> B["Service\n(lógica de negócio)"] B --> C["DAO\n(interface)"] C --> D["DAOImpl\n(implementação JDBC)"] D --> E["Banco de dados"] end

1. O Java Bean que representa a tabela

É comum utilizar classes que seguem o padrão Java Beans (construtor vazio e getters/setters) para representar as tabelas do banco no código Java: 

public class Contato {
    private int id;
    private String nome;
    private String email;

    public Contato() { } // construtor vazio exigido pelo padrão Java Beans

    public int getId() { return id; }
    public void setId(int id) { this.id = id; }

    public String getNome() { return nome; }
    public void setNome(String nome) { this.nome = nome; }

    public String getEmail() { return email; }
    public void setEmail(String email) { this.email = email; }
}

2. A interface do DAO

import java.util.List;

public interface ContatoDAO {
    void salvar(Contato contato);
    List<Contato> listar();
    Contato buscarPorId(int id);
    void excluir(int id);
}

3. A implementação com JDBC

import java.util.ArrayList;
import java.util.List;

public class ContatoDAOImpl implements ContatoDAO {

    @Override
    public List<Contato> listar() {
        List<Contato> contatos = new ArrayList<>();
        String sql = "SELECT id, nome, email FROM contatos";

        try (Connection conexao = Conexao.abrir();
             PreparedStatement stmt = conexao.prepareStatement(sql);
             ResultSet rs = stmt.executeQuery()) {

            while (rs.next()) {
                Contato c = new Contato();
                c.setId(rs.getInt("id"));
                c.setNome(rs.getString("nome"));
                c.setEmail(rs.getString("email"));
                contatos.add(c);
            }
        } catch (SQLException e) {
            throw new RuntimeException("Erro ao listar contatos", e);
        }
        return contatos;
    }
}

Se amanhã o sistema trocar de banco (de MySQL para PostgreSQL), apenas o driver e a URL mudam — o código que usa o ContatoDAO permanece intacto. Isso é a portabilidade do JDBC aliada ao padrão DAO.

Dicas & Lembretes Técnicos

  • Índices no JDBC: Ao contrário dos arrays (que começam em 0), os índices de colunas no ResultSet e os parâmetros no PreparedStatement começam em 1.
  • Classpath: Lembre-se de adicionar o arquivo .jar do driver do seu banco de dados ao Build Path do projeto para que o Java localize a implementação do driver.
  • Java Beans: É comum usar classes com construtor vazio e getters/setters para representar as tabelas do banco no código Java.
  • Nunca concatene SQL: Sempre que houver um valor vindo do usuário, use PreparedStatement — isso elimina o risco de SQL Injection.
  • execute vs executeUpdate: Para INSERT, UPDATE e DELETE, prefira executeUpdate(), que ainda informa quantas linhas foram afetadas.

Como aplicar na Prática

  • Cadastro de usuários: Use um PreparedStatement para inserir os dados recebidos de um formulário, jamais concatenando o valor digitado no SQL.
  • CRUD completo: Crie uma interface XxxDAO com salvar/listar/buscarPorId/excluir e uma implementação JDBC para cada tabela do sistema.
  • Conexão centralizada: Coloque a abertura de conexão em uma classe utilitária única (ex.: Conexao.abrir()) para evitar repetição e facilitar a troca de banco.
  • Login com segurança: Consulte o usuário com WHERE email = ? — a proteção contra SQL Injection começa na consulta, não na tela.
