Teoria & Conceitos

1. O que é uma Exceção?

Uma exceção representa uma situação que normalmente não ocorre e indica algo estranho ou inesperado no sistema, como uma divisão por zero ou o acesso a um índice inválido de um array. No Java, as exceções são objetos que herdam da classe Throwable.

  • Exception: situações que o aplicativo pode capturar e tratar para tentar se recuperar.
  • Error: problemas graves na Máquina Virtual Java (JVM), como falta de memória (OutOfMemoryError), que geralmente não devem ser tratados pelo programador.

O grande benefício do tratamento de exceções é separar a detecção do erro (feita nos métodos que lançam a exceção) da recuperação do erro (feita por quem captura). Sem esse mecanismo, o programador precisaria poluir a lógica de negócio com dezenas de if para verificar retornos de cada método.

2. A Hierarquia de Exceções no Java

Toda exceção ou erro em Java descende da classe raiz Throwable, que define os métodos mais importantes usados no tratamento:

  • getMessage(): retorna a mensagem descritiva cadastrada no momento do lançamento.
  • printStackTrace(): imprime no console o rastro completo da pilha de chamadas.
  • getCause(): retorna a exceção que originou esta (usado no encadeamento de erros).

Perceba que RuntimeException (e suas subclasses) fica abaixo de Exception na hierarquia — mas, conceitualmente, ela representa as exceções unchecked. Já as classes IOException e SQLException são checked, pois não herdam de RuntimeException.

3. Conhecendo a Stacktrace

Quando ocorre um erro não tratado, o Java exibe a Stacktrace (rastro da pilha). Ela fornece informações fundamentais para a resolução de problemas, listando o nome da exceção, o erro ocorrido e a sequência de chamadas de métodos até o ponto exato da falha. 

Exception in thread "main" java.lang.ArithmeticException: / by zero
    at Aplicacao.dividir(Aplicacao.java:12)
    at Aplicacao.calcularMedia(Aplicacao.java:22)
    at Aplicacao.main(Aplicacao.java:30)

A leitura deve ser feita de cima para baixo: a primeira linha informa a exceção e a mensagem, e as linhas seguintes mostram a cadeia de chamadas — o primeiro frame (Aplicacao.java:12) é onde o erro realmente aconteceu. Cada método chamado antes aparece logo abaixo.

4. Os Blocos try, catch e finally

A. O Bloco try (Tentar)

O bloco try delimita o "código de risco", ou seja, instruções que podem disparar uma exceção. Se uma exceção ocorrer dentro dele, o restante das instruções do bloco é ignorado e o controle é passado para o respectivo tratamento.

B. O Bloco catch (Capturar)

O bloco catch contém o código que será executado apenas se uma exceção específica ocorrer no bloco try correspondente. A exceção é capturada na variável declarada entre parênteses (no exemplo, e).

Exemplo Prático: tratando divisão por zero

try {
    int quociente = 100 / 0; // Código de risco
    System.out.println("Resultado: " + quociente); // Não é executado!
} catch (ArithmeticException e) {
    // Trata a exceção específica de erro matemático
    System.err.println("Erro: Não é possível dividir por zero!");
}

Quando a linha 100 / 0 é avaliada, a JVM lança uma ArithmeticException. A instrução seguinte (println) é pulada e o controle salta direto para o catch.

C. Multicatch (Java 7+)

Desde o Java 7, é possível capturar vários tipos de exceção em um único bloco catch caso a tratativa seja a mesma, separando as classes pelo caractere |. As exceções agrupadas não podem ter relação de herança entre si — o compilador impede, por exemplo, Exception | ArithmeticException. 

try {
    String valor = entrada.nextLine();
    int numero = Integer.parseInt(valor);   // pode lançar NumberFormatException
    System.out.println(valor.toUpperCase()); // pode lançar NullPointerException
} catch (NumberFormatException | NullPointerException e) {
    System.err.println("Ocorreu um erro matemático ou de referência nula.");
}
D. O Bloco finally (Finalmente)

O bloco finally é opcional e, se presente, será executado sempre, independentemente de ter ocorrido uma exceção ou não. É o local ideal para liberar recursos "caros", como fechar conexões com bancos de dados ou arquivos abertos, garantindo que não ocorram vazamentos de memória. 

try {
    abrirConexao();
    processarDados();
} catch (Exception e) {
    System.err.println("Erro no processamento.");
} finally {
    fecharConexao(); // Sempre executa para limpar recursos
}

O diagrama abaixo resume a ordem de execução dos três blocos:

flowchart TD A[Início do bloco try] --> B[Tenta executar as instruções] B --> C{Exceção lançada?} C -->|Não| D[Pula os blocos catch] C -->|Sim| E[Procura um catch compatível] E --> F{Encontrou?} F -->|Sim| G[Executa o catch] F -->|Não| H[Exceção sobe para o método chamador] D --> I[Executa o finally, se existir] G --> I H --> I I --> J[Programa continua ou método encerra]

Exceções Checked vs. Unchecked

Essa é a distinção mais importante para decidir quando e como tratar uma exceção. A regra é definida pelo compilador: exceções checked obrigam o tratamento; as unchecked não.

Tipo Característica Exemplos
Unchecked (RuntimeException) Erros causados geralmente por falhas de lógica do programador. O compilador não obriga a tratar com try/catch. NullPointerException, ArithmeticException, ArrayIndexOutOfBoundsException
Checked Condições fora do controle direto do programa. O compilador obriga o desenvolvedor a tratar a exceção ou declarar que o método pode lançá-la. IOException (arquivo não encontrado), SQLException

Exemplo comparativo — o que o compilador exige em cada caso:

// UNCHECKED: compila sem try/catch. O erro só aparece em tempo de execução.
int[] numeros = {1, 2, 3};
System.out.println(numeros[10]); // ArrayIndexOutOfBoundsException

// CHECKED: NÃO compila sem tratamento ou declaração throws
FileReader arquivo = new FileReader("dados.txt"); // erro de compilação!

Para a linha do FileReader compilar, duas opções são válidas:

// Opção 1: tratar no próprio método
try {
    FileReader arquivo = new FileReader("dados.txt");
} catch (FileNotFoundException e) {
    System.err.println("Arquivo não encontrado: " + e.getMessage());
}

// Opção 2: delegar com throws (quem chamar assume a responsabilidade)
public void lerArquivo(String caminho) throws IOException {
    FileReader arquivo = new FileReader(caminho);
}

Exemplos Funcionais

1. Calculadora protegida contra erros

Um programa completo que captura múltiplas exceções: divisão por zero e entrada inválida do usuário. 

import java.util.InputMismatchException;
import java.util.Scanner;

public class Calculadora {
    public static void main(String[] args) {
        Scanner entrada = new Scanner(System.in);

        try {
            System.out.print("Digite o numerador: ");
            int numerador = entrada.nextInt();

            System.out.print("Digite o denominador: ");
            int denominador = entrada.nextInt();

            int quociente = numerador / denominador;
            System.out.println("Resultado: " + quociente);

        } catch (ArithmeticException e) {
            System.err.println("Erro: divisão por zero não é permitida.");
        } catch (InputMismatchException e) {
            System.err.println("Erro: você deve digitar números inteiros.");
        } finally {
            entrada.close();
            System.out.println("Fim do programa.");
        }
    }
}

Observe que o finally fecha o Scanner mesmo quando o usuário digita um valor inválido e uma exceção é capturada.

2. Exceção personalizada + regra de negócio

Quando as exceções da API Java não representam bem o problema do domínio, criamos nossa própria exceção. Primeiro, a classe da exceção: 

public class SaldoInsuficienteException extends RuntimeException {
    public SaldoInsuficienteException(String mensagem) {
        super(mensagem);
    }
}

Agora, a classe de negócio que usa throw e throws:

public class ContaBancaria {
    private double saldo;

    public void depositar(double valor) {
        if (valor <= 0) {
            throw new IllegalArgumentException("Depósito deve ser positivo.");
        }
        this.saldo += valor;
    }

    public void sacar(double valor) throws SaldoInsuficienteException {
        if (valor > this.saldo) {
            throw new SaldoInsuficienteException(
                "Saldo insuficiente! Disponível: R$ " + this.saldo);
        }
        this.saldo -= valor;
    }

    public double getSaldo() {
        return saldo;
    }
}

Por fim, o cliente que captura e reage à exceção de negócio:

public class Principal {
    public static void main(String[] args) {
        ContaBancaria conta = new ContaBancaria();
        conta.depositar(100);

        try {
            conta.sacar(150);
            System.out.println("Saque realizado com sucesso!");
        } catch (SaldoInsuficienteException e) {
            System.err.println("Operação negada: " + e.getMessage());
        }

        System.out.println("Saldo final: R$ " + conta.getSaldo());
    }
}

3. Lendo arquivos com try-with-resources

O bloco try-with-resources (Java 7+) simplifica a desalocação de recursos que implementam a interface AutoCloseable. O Java fecha automaticamente o recurso ao final do bloco try, dispensando o uso explícito do finally para dar .close(). 

import java.io.BufferedReader;
import java.io.FileReader;
import java.io.IOException;

public class LeitorArquivo {
    public static void main(String[] args) {
        String caminho = "notas.txt";

        try (BufferedReader leitor = new BufferedReader(
                new FileReader(caminho))) { // recurso declarado nos parênteses
            String linha;
            while ((linha = leitor.readLine()) != null) {
                System.out.println(linha);
            }
        } catch (IOException e) {
            System.err.println("Erro ao ler o arquivo: " + e.getMessage());
        }
        // Nenhum finally necessário: o leitor foi fechado automaticamente
    }
}

Vários recursos podem ser declarados nos parênteses, separados por ;:

try (Connection con = DriverManager.getConnection(url);
     PreparedStatement stmt = con.prepareStatement(sql)) {
    stmt.setString(1, "João");
    stmt.executeUpdate();
} catch (SQLException e) {
    e.printStackTrace();
}
flowchart TD A[Declara o recurso nos parênteses] --> B[Abre o recurso] B --> C[Executa o corpo do try] C --> D{Exceção lançada?} D -->|Não| E[Fecha recursos automaticamente] D -->|Sim| F[Catch trata a exceção] F --> E E --> G[Programa continua]

Lançando e Delegando Exceções: throw e throws

  • throw: palavra-chave usada no imperativo para lançar efetivamente uma exceção quando uma regra de negócio é violada. Sempre acompanhada de new: throw new MinhaExcecao("mensagem").
  • throws: usada na assinatura do método para avisar ao compilador e a quem chama o método que ele pode disparar certas exceções, delegando a responsabilidade do tratamento. 
public void saca(double valor) throws SaldoInsuficienteException {
    if (this.saldo < valor) {
        throw new SaldoInsuficienteException("Saldo insuficiente!"); // Lança a exceção
    }
    this.saldo -= valor;
}

A regra de ouro: throw lança, throws delega. Quem não quer (ou não pode) tratar a exceção, declara throws na assinatura e empurra a responsabilidade para o chamador. Para exceções checked, essa cadeia de delegação precisa terminar em algum catch — ou o programa nem compila.

Exceções e Padrões de Projeto

As exceções são uma peça importante em vários padrões de projeto, seja para sinalizar falhas de regra de negócio, seja para garantir a execução de etapas obrigatórias. Veja como elas aparecem em quatro padrões clássicos.

1. Factory Method — rejeitando tipos desconhecidos

Em uma fábrica, quando o parâmetro pede algo que a fábrica não conhece, o padrão é lançar uma IllegalArgumentException para deixar claro que a entrada é inválida: 

public class FabricaDeFormas {

    public static Forma criar(String tipo) {
        return switch (tipo.toLowerCase()) {
            case "circulo"   -> new Circulo(5.0);
            case "quadrado"  -> new Quadrado(4.0);
            case "triangulo" -> new Triangulo(3.0, 4.0, 5.0);
            default -> throw new IllegalArgumentException(
                "Tipo de forma desconhecido: " + tipo);
        };
    }
}

O padrão garante que a fábrica só retorna objetos válidos — se não consegue, falha de forma explícita em vez de retornar null.

2. Template Method — garantindo etapas com try/finally

O Template Method define o esqueleto de um algoritmo e permite que subclasses preencham partes. Como a etapa de limpeza é obrigatória, o esqueleto usa try/finally para executá-la sempre, mesmo que a implementação da subclasse falhe: 

public abstract class Relatorio {

    public final void gerar() {          // esqueleto do algoritmo
        try {
            abrirArquivo();
            escreverCabecalho();
            escreverCorpo();             // hook: implementado pela subclasse
            escreverRodape();
        } finally {
            fecharArquivo();             // executa SEMPRE
        }
    }

    protected abstract void escreverCorpo();

    private void abrirArquivo()  { System.out.println("Abrindo arquivo..."); }
    private void fecharArquivo() { System.out.println("Fechando arquivo..."); }
    private void escreverCabecalho() { System.out.println("Cabeçalho"); }
    private void escreverRodape()    { System.out.println("Rodapé"); }
}

public class RelatorioAlunos extends Relatorio {
    @Override
    protected void escreverCorpo() {
        // se algo falhar aqui, o finally do método gerar() ainda executa
        System.out.println("Lista de alunos...");
    }
}

3. Strategy — validação que lança exceção de domínio

No Strategy, cada algoritmo encapsulado pode rejeitar sua entrada lançando uma exceção específica. Quem usa a estratégia não precisa conhecer os detalhes de cada regra: 

public interface EstrategiaPagamento {
    void pagar(double valor) throws SaldoInsuficienteException;
}

public class CartaoCredito implements EstrategiaPagamento {
    private double limite;

    public CartaoCredito(double limite) {
        this.limite = limite;
    }

    @Override
    public void pagar(double valor) throws SaldoInsuficienteException {
        if (valor > limite) {
            throw new SaldoInsuficienteException(
                "Limite insuficiente no cartão. Disponível: R$ " + limite);
        }
        limite -= valor;
    }
}

public class CarteiraDigital implements EstrategiaPagamento {
    private double saldo;

    public CarteiraDigital(double saldo) {
        this.saldo = saldo;
    }

    @Override
    public void pagar(double valor) throws SaldoInsuficienteException {
        if (valor > saldo) {
            throw new SaldoInsuficienteException(
                "Saldo insuficiente na carteira. Disponível: R$ " + saldo);
        }
        saldo -= valor;
    }
}

O checkout não muda quando novas estratégias são adicionadas — ele apenas captura a exceção comum: 

public class Checkout {
    private EstrategiaPagamento estrategia;

    public Checkout(EstrategiaPagamento estrategia) {
        this.estrategia = estrategia;
    }

    public void finalizar(double valor) {
        try {
            estrategia.pagar(valor);
            System.out.println("Pagamento aprovado!");
        } catch (SaldoInsuficienteException e) {
            System.err.println("Pagamento recusado: " + e.getMessage());
        }
    }
}

4. DAO — isolando a camada com RuntimeException

No padrão DAO (Data Access Object), a camada de negócio não deve conhecer exceções de infraestrutura como SQLException. A prática comum é capturar a checked e relançá-la como uma exceção unchecked do domínio, mantendo o desacoplamento entre camadas: 

public class PersistenciaException extends RuntimeException {
    public PersistenciaException(String mensagem, Throwable causa) {
        super(mensagem, causa);
    }
}
public class ProdutoDAOImpl implements ProdutoDAO {
    @Override
    public void salvar(Produto produto) {
        try (Connection con = Conexao.abrir();
             PreparedStatement stmt = con.prepareStatement(
                 "INSERT INTO produtos (nome, preco) VALUES (?, ?)")) {

            stmt.setString(1, produto.getNome());
            stmt.setBigDecimal(2, produto.getPreco());
            stmt.executeUpdate();

        } catch (SQLException e) {
            // checked -> unchecked, sem vazar detalhes do JDBC
            throw new PersistenciaException("Falha ao salvar o produto", e);
        }
    }
}

Repare no throw new PersistenciaException(..., e): o segundo argumento preserva a causa original (getCause()), o que é essencial para depuração. A camada de negócio captura apenas PersistenciaException e continua independente do banco.

Dicas & Lembretes

  • Nunca ignore uma exceção: deixar um bloco catch vazio pode esconder bugs críticos e dificultar a depuração. No mínimo, registre o erro com e.printStackTrace() ou um log.
  • Especifique o erro: evite capturar apenas o tipo genérico Exception; tente tratar os erros específicos para saber exatamente como recuperar o sistema.
  • Crie suas próprias exceções: se as exceções da API Java não representarem bem o seu problema, crie classes que herdam de RuntimeException ou Exception para personalizar suas mensagens de erro.
  • Preserve a causa original: ao relançar uma exceção, sempre passe a exceção capturada como segundo argumento do construtor (new MinhaExcecao("msg", causa)) para não perder o rastro do erro real.
  • Prefira try-with-resources: para recursos AutoCloseable (arquivos, conexões, statements), use try-with-resources em vez de finally manual — o código fica menor e à prova de esquecimento.
  • Não use exceções para controle de fluxo: exceções são para situações excepcionais. Estruturas de repetição e condições normais devem usar if/else e laços.
