Teoria & Conceitos

1. O que é o Padrão DAO?

O Data Access Object (DAO) é um padrão de projeto que visa remover o código de acesso ao banco de dados das classes de lógica de negócio, centralizando as operações de persistência em classes específicas.

  • Objetivo Principal: Isolar todo o acesso ao banco de dados em classes simples, onde cada instância é um objeto responsável por acessar e manipular os dados de uma entidade específica.
  • Problema que resolve: Evita que o código SQL fique espalhado por toda a aplicação, o que tornaria o sistema difícil de ler, manter e evoluir.
  • Independência: O uso do DAO permite que, caso o banco de dados mude, apenas as classes DAO precisem ser alteradas, sem impactar a lógica de negócio.

Lembre-se

Na aula anterior (Aula 25) vimos os fundamentos do JDBC — conexão, PreparedStatement e ResultSet. Agora, o padrão DAO organiza esses elementos em uma arquitetura limpa e sustentável.

2. Componentes de uma Implementação DAO

Para implementar este padrão com eficácia, geralmente trabalhamos com três elementos principais: a Entidade, a Interface e a Classe Concreta.

A. Entidade (JavaBean)

Representa a tabela do banco de dados no mundo orientado a objetos. Deve seguir o padrão JavaBean: possuir um construtor sem argumentos e métodos de acesso get e set. 

public class Contato {
    private Long id;
    private String nome;
    private String email;

    // Construtor vazio (padrão JavaBean)
    public Contato() { }

    // Getters e Setters
    public Long getId() { return id; }
    public void setId(Long id) { this.id = id; }

    public String getNome() { return nome; }
    public void setNome(String nome) { this.nome = nome; }

    public String getEmail() { return email; }
    public void setEmail(String email) { this.email = email; }
}

Cada atributo da classe corresponde a uma coluna da tabela. O construtor vazio é essencial para que frameworks e ferramentas (como JDBC e serializadores) consigam instanciar o objeto sem conhecer os detalhes de construção.

B. Interface DAO (Opcional, mas Recomendada)

Define o contrato de quais operações de dados devem existir (como salvar, excluir ou buscar), permitindo o uso de tipos genéricos <E> para maior flexibilidade. 

import java.util.List;

// Interface genérica para qualquer entidade
public interface DAO<E> {
    void salvar(E entidade);
    E recuperarPorId(Object id);
    List<E> listarTodos();
    void atualizar(E entidade);
    void excluir(Object id);
}

A interface DAO é o "contrato" que a camada de serviço conhece. A implementação concreta pode ser trocada sem alterar o código que consome o DAO — esse é o princípio da programação para interfaces.

C. Implementação Concreta

A classe concreta implementa a interface DAO e contém toda a lógica de acesso ao banco de dados via JDBC. Cada método representa uma operação de persistência.

Implementação Prática: O ContatoDao

A classe DAO concreta contém a conexão com o banco e os métodos que executam as instruções SQL utilizando a API JDBC. Vejamos uma implementação completa passo a passo.

1. A Classe ConnectionFactory

Para evitar repetição de código, a abertura de conexão é centralizada em uma classe utilitária. Essa classe encapsula os detalhes de URL, usuário e senha — se o banco mudar, alteramos apenas este ponto. 

import java.sql.Connection;
import java.sql.DriverManager;
import java.sql.SQLException;

public class ConnectionFactory {

    private static final String URL = "jdbc:mysql://localhost:3306/agenda_contatos";
    private static final String USUARIO = "root";
    private static final String SENHA = "senha";

    public Connection getConnection() {
        try {
            return DriverManager.getConnection(URL, USUARIO, SENHA);
        } catch (SQLException e) {
            throw new RuntimeException("Erro ao conectar ao banco de dados", e);
        }
    }
}

Por que encapsular a conexão?

  • DRY (Don't Repeat Yourself): Evita repetir a lógica de conexão em cada DAO.
  • Manutenção: Se a senha ou URL mudar, altera-se apenas a ConnectionFactory.
  • Testabilidade: Em testes unitários, pode-se mockar ou substituir a ConnectionFactory.

2. O ContatoDao Completo

Note como cada método utilize PreparedStatement (nunca concatenação de strings) e como as exceções SQLException são capturadas e relançadas como RuntimeException: 

import java.sql.Connection;
import java.sql.PreparedStatement;
import java.sql.ResultSet;
import java.sql.SQLException;
import java.util.ArrayList;
import java.util.List;

public class ContatoDao {

    private Connection connection;

    // A conexão é obtida através da ConnectionFactory
    public ContatoDao() {
        this.connection = new ConnectionFactory().getConnection();
    }

    // CREATE — Inserir um novo contato
    public void adiciona(Contato contato) {
        String sql = "INSERT INTO contatos (nome, email) VALUES (?, ?)";

        try (PreparedStatement stmt = connection.prepareStatement(sql)) {
            stmt.setString(1, contato.getNome());
            stmt.setString(2, contato.getEmail());
            stmt.execute();
        } catch (SQLException e) {
            throw new RuntimeException("Erro ao adicionar contato", e);
        }
    }

    // READ — Listar todos os contatos
    public List<Contato> Lista() {
        List<Contato> contatos = new ArrayList<>();
        String sql = "SELECT id, nome, email FROM contatos";

        try (PreparedStatement stmt = connection.prepareStatement(sql);
             ResultSet rs = stmt.executeQuery()) {

            while (rs.next()) {
                Contato contato = new Contato();
                contato.setId(rs.getLong("id"));
                contato.setNome(rs.getString("nome"));
                contato.setEmail(rs.getString("email"));
                contatos.add(contato);
            }
        } catch (SQLException e) {
            throw new RuntimeException("Erro ao listar contatos", e);
        }
        return contatos;
    }

    // READ — Buscar contato por ID
    public Contato buscaPorId(Long id) {
        String sql = "SELECT id, nome, email FROM contatos WHERE id = ?";

        try (PreparedStatement stmt = connection.prepareStatement(sql)) {
            stmt.setLong(1, id);

            try (ResultSet rs = stmt.executeQuery()) {
                if (rs.next()) {
                    Contato contato = new Contato();
                    contato.setId(rs.getLong("id"));
                    contato.setNome(rs.getString("nome"));
                    contato.setEmail(rs.getString("email"));
                    return contato;
                }
            }
        } catch (SQLException e) {
            throw new RuntimeException("Erro ao buscar contato por ID", e);
        }
        return null;
    }

    // UPDATE — Atualizar dados de um contato
    public void atualiza(Contato contato) {
        String sql = "UPDATE contatos SET nome = ?, email = ? WHERE id = ?";

        try (PreparedStatement stmt = connection.prepareStatement(sql)) {
            stmt.setString(1, contato.getNome());
            stmt.setString(2, contato.getEmail());
            stmt.setLong(3, contato.getId());
            stmt.executeUpdate();
        } catch (SQLException e) {
            throw new RuntimeException("Erro ao atualizar contato", e);
        }
    }

    // DELETE — Excluir contato por ID
    public void remove(Long id) {
        String sql = "DELETE FROM contatos WHERE id = ?";

        try (PreparedStatement stmt = connection.prepareStatement(sql)) {
            stmt.setLong(1, id);
            stmt.execute();
        } catch (SQLException e) {
            throw new RuntimeException("Erro ao remover contato", e);
        }
    }
}

3. Uso no Código da Aplicação

Com o DAO implementado, a camada de negócio se torna simples e limpa — ela não precisa saber como os dados são salvos, apenas que o DAO é capaz de salvá-los: 

public class Main {
    public static void main(String[] args) {
        ContatoDao dao = new ContatoDao();

        // Criando e salvando um contato
        Contato c = new Contato();
        c.setNome("Ana Souza");
        c.setEmail("ana@email.com");
        dao.adiciona(c);

        // Listando todos os contatos
        List<Contato> lista = dao.Lista();
        for (Contato contato : lista) {
            System.out.println(contato.getId() + " - " + contato.getNome());
        }

        // Buscando por ID
        Contato encontrado = dao.buscaPorId(1L);
        if (encontrado != null) {
            System.out.println("Encontrado: " + encontrado.getNome());
        }

        // Atualizando
        encontrado.setNome("Ana Souza Silva");
        dao.atualiza(encontrado);

        // Excluindo
        dao.remove(1L);
    }
}

Acoplamento e Injeção de Dependência

Uma evolução importante no design de DAOs é a Inversão de Controle (IoC). No exemplo anterior, o DAO cria sua própria conexão dentro do construtor — isso gera acoplamento direto com a ConnectionFactory.

Problema: Múltiplas Conexões

Se cada DAO abre sua própria conexão, uma única operação que envolva vários DAOs pode consumir várias conexões simultaneamente, desperdiçando recursos do servidor.

Solução: Injeção de Dependência

Em vez de o DAO criar sua própria conexão, ele passa a recebê-la de fora (via construtor ou método setter). O DAO declara que "precisa" de uma conexão, e o sistema (ou um framework como Spring) "injeta" essa conexão no momento da criação do objeto. 

// Versão com Injeção de Dependência
public class ContatoDao {

    private Connection connection;

    // A conexão é INJETADA pelo construtor (não criada internamente)
    public ContatoDao(Connection connection) {
        this.connection = connection;
    }

    public void adiciona(Contato contato) {
        String sql = "INSERT INTO contatos (nome, email) VALUES (?, ?)";

        try (PreparedStatement stmt = connection.prepareStatement(sql)) {
            stmt.setString(1, contato.getNome());
            stmt.setString(2, contato.getEmail());
            stmt.execute();
        } catch (SQLException e) {
            throw new RuntimeException("Erro ao adicionar contato", e);
        }
    }

    // ... outros métodos permanecem iguais
}
// Uso: a conexão é compartilhada entre múltiplos DAOs
ConnectionFactory factory = new ConnectionFactory();
Connection conexao = factory.getConnection();

ContatoDao contatoDao = new ContatoDao(conexao);
TelefoneDao telefoneDao = new TelefoneDao(conexao);

// Ambos usam a MESMA conexão — economiza recursos e suporta transações
try {
    contatoDao.adiciona(novoContato);
    telefoneDao.adiciona(novoTelefone);
    conexao.commit(); // confirma ambas as operações
} catch (Exception e) {
    conexao.rollback(); // desfaz tudo em caso de erro
}

DAOs e Camadas de Serviço

Em arquiteturas modulares, as classes da Camada de Serviço são responsáveis pelas regras de negócio e colaboram com os DAOs para persistir informações. A separação de responsabilidades é fundamental:

Camada Responsabilidade Exemplo
Controller Receber requisições, validar entrada e chamar o Service ContatoController
Service Aplicar regras de negócio, orquestrar operações ContatoService
DAO Acessar o banco de dados (CRUD) ContatoDao
Entity Representar a tabela como objeto Java Contato

Exemplo: ContatoService usando ContatoDao

public class ContatoService {

    private ContatoDao contatoDao;

    // Injeção de Dependência: o Service recebe o DAO
    public ContatoService(ContatoDao contatoDao) {
        this.contatoDao = contatoDao;
    }

    // Regra de negócio: não permitir e-mails duplicados
    public void cadastrarContato(Contato contato) {
        List<Contato> existentes = contatoDao.Lista();

        for (Contato c : existentes) {
            if (c.getEmail().equals(contato.getEmail())) {
                throw new IllegalArgumentException(
                    "Já existe um contato com esse e-mail: " + contato.getEmail()
                );
            }
        }

        // Se passou pela regra, persiste
        contatoDao.adiciona(contato);
    }

    // Regra de negócio:-formatar lista para exibição
    public String listarFormatado() {
        List<Contato> contatos = contatoDao.Lista();
        StringBuilder sb = new StringBuilder();

        for (Contato c : contatos) {
            sb.append(String.format("[%d] %s — %s%n",
                c.getId(), c.getNome(), c.getEmail()));
        }
        return sb.toString();
    }
}

Repare que o ContatoService não sabe como o dado é salvo — ele apenas sabe que o ContatoDao é capaz de salvá-lo. Se amanhã a implementação JDBC for substituída por Hibernate/JPA, o Service permanece intacto.

Factory Method para criação de DAOs

Para desacoplar ainda mais a criação de instâncias, pode-se utilizar o padrão Factory Method para delegar a criação da instância correta do DAO para uma subclasse específica: 

public abstract class DAOFactory {

    // Factory Method abstrato
    public abstract ContatoDao getContatoDao();

    // Factory concreta para JDBC
    public static DAOFactory getJdbcFactory(Connection conexao) {
        return new JdbcDAOFactory(conexao);
    }
}

public class JdbcDAOFactory extends DAOFactory {

    private Connection conexao;

    public JdbcDAOFactory(Connection conexao) {
        this.conexao = conexao;
    }

    @Override
    public ContatoDao getContatoDao() {
        return new ContatoDao(conexao);
    }
}

// Uso:
DAOFactory factory = DAOFactory.getJdbcFactory(conexao);
ContatoDao dao = factory.getContatoDao();

Dicas & Lembretes Técnicos

  • Sempre feche os recursos: Certifique-se de fechar PreparedStatement e Connection (preferencialmente usando try-with-resources) para evitar vazamentos de memória.
  • Encapsule Exceções: Capture SQLException e relance como uma exceção de tempo de execução (como RuntimeException ou uma customizada DAOException) para não "sujar" as outras camadas com detalhes de banco de dados.
  • Use PreparedStatements: Nunca concatene Strings para montar SQL; o uso de parâmetros ? é essencial para performance e segurança contra ataques de SQL Injection.
  • Uma entidade = um DAO: Mantenha o princípio de que cada tabela do banco deve ter seu próprio DAO dedicado. Isso facilita a localização e manutenção do código.
  • Evolução para ORM: Se o projeto crescer e as consultas SQL se tornarem muito complexas ou manuais, considere evoluir para ferramentas de ORM (Object Relational Mapping) como o Hibernate ou a especificação JPA.

Como aplicar na Prática

  • Cadastro de usuários: Crie uma interface UsuarioDAO com salvar/listar/buscarPorId/excluir e uma implementação JDBC para a tabela de usuários.
  • Compartilhe a conexão: Use Injeção de Dependência para que múltiplos DAOs compartilhem a mesma Connection em uma operação transacional.
  • Factory Pattern: Implemente uma DAOFactory para criar DAOs sem expor a implementação concreta ao restante da aplicação.
  • Camada de Serviço: Nunca chame o DAO diretamente do Controller — sempre passe pelo Service para que as regras de negócio sejam aplicadas antes da persistência.
  • Testes unitários: Crie implementações "falsas" (mocks) da interface DAO para testar a lógica de negócio sem depender do banco de dados real.
