Teoria & Conceitos

1. Objetivos da Aula

  • Compreender a perspectiva e os fundamentos do Teste de Caixa Branca (estrutural).
  • Aprender a construir e interpretar um Grafo de Fluxo de Controle (CFG).
  • Calcular a Complexidade Ciclomática de McCabe para mensurar o esforço de teste.
  • Aplicar critérios de cobertura de código (instruções, desvios e caminhos).

2. O que é Teste de Caixa Branca?

Também conhecido como teste estrutural ou "caixa de vidro", esta abordagem verifica a implementação interna de unidades de software, como instruções, estruturas de dados e caminhos lógicos.

  • Responsabilidade: Geralmente é realizado pelos próprios programadores durante a fase de teste de unidade, dado o conhecimento íntimo necessário do código-fonte.
  • Foco: Reduzir falhas internas para que o sistema seja robusto independentemente do ambiente de entrada.

Diferentemente da caixa preta — que enxerga apenas entradas e saídas —, a caixa branca permite analisar o que acontece dentro do programa: cada desvio, cada laço e cada caminho de execução passa a ser alvo de verificação.

3. Grafo de Fluxo de Controle (CFG)

O CFG é uma representação gráfica detalhada de uma unidade de programa utilizada para visualizar todos os caminhos possíveis de execução.

  • Nós de Processamento: Correspondem a atribuições de variáveis ou chamadas de funções.
  • Nós de Decisão/Desvio: Representam comandos condicionais (ex: if, switch-case). Cada saída é marcada com sua condição específica (ex: Verdadeiro/Falso).
  • Nós de Junção: Pontos onde diferentes fluxos de controle se encontram novamente.

A partir do CFG, o testador consegue enxergar quantas rotas distintas o programa pode percorrer e, assim, planejar os testes para percorrê-las.

4. Complexidade Ciclomática de McCabe

É uma métrica baseada na teoria dos grafos que define o número de caminhos independentes de fluxo de controle para um determinado programa.

Fórmula: v = e - n + 2

  • v = complexidade ciclomática.
  • e = número de arestas (links entre os nós).
  • n = número de nós (grupos sequenciais de instruções).

Regra de Ouro: Módulos com complexidade maior que 10 são considerados extremamente difíceis de serem testados adequadamente e podem esconder um número maior de defeitos.

5. Critérios de Cobertura (Testing Coverage)

Os testes de caixa branca utilizam métricas para determinar quando parar de testar:

  • Cobertura de Instrução (Statement Coverage): 100% de cobertura significa que todas as linhas de código foram executadas pelo menos uma vez. É considerado o critério mais fraco.
  • Cobertura de Desvio (Branch Coverage): Garante que cada condição (como um if) foi avaliada como Verdadeira e como Falsa em diferentes execuções.
  • Cobertura de Predicado: Explora todas as combinações possíveis de valores de verdade que afetam um caminho.
  • Cobertura de Caminho (All-Path Coverage): Testa todos os caminhos independentes do CFG. É o mais completo, porém difícil de alcançar em sistemas complexos devido à explosão combinatória.

Exemplos Práticos

1. Construção de CFG: Cálculo da Média de Alunos

Imagine um código simples de cálculo de média de alunos. Se a nota for maior que 6, o aluno passa; caso contrário, vai para recuperação.

flowchart TD A([Início]) --> B[Ler nota] B --> C{nota > 6?} C -->|V| D[Aprovado] C -->|F| E[Recuperação] D --> F([Fim]) E --> F

No CFG, o nó de decisão (if nota > 6) terá duas arestas saindo dele: uma para o nó "Aprovado" (V) e outra para o nó "Recuperação" (F).

2. Cálculo da Métrica

Se esse grafo tiver 9 arestas e 8 nós, sua complexidade será:

v = e - n + 2 = 9 - 8 + 2 = 3

Isso indica que são necessários, no mínimo, 3 casos de teste para cobrir os caminhos independentes básicos.

Caso de Teste Caminho Percorrido Entrada
CT-01 Início → nota > 6 (V) → Aprovado → Fim nota = 8
CT-02 Início → nota > 6 (F) → Recuperação → Fim nota = 5
CT-03 Caso adicional para validar a fronteira do desvio nota = 6

3. Identificação de Riscos

Um método com muitos loops aninhados e dezenas de ifs terá uma complexidade muito alta (ex: 25). Isso sinaliza que o código precisa de refatoração para ser decomposto em unidades menores e mais testáveis.

A complexidade ciclomática atua, assim, como um termômetro de manutenibilidade: valores acima de 10 apontam a necessidade de simplificar o módulo antes de ampliar a suíte de testes.

4. Limitações e Desafios

  • Omissões: O teste de caixa branca não detecta caminhos ou funcionalidades que deveriam existir, mas foram esquecidos no código (problemas de design ou especificação).
  • Caminhos Inviáveis: Alguns caminhos lógicos no CFG podem ser impossíveis de executar com dados reais, o que exige que o testador selecione outros caminhos para satisfazer os critérios de cobertura.

Dicas & Lembretes

  • Fórmula sempre à mão: v = e - n + 2. A complexidade ciclomática equivale ao número mínimo de caminhos independentes que devem ser testados.
  • Regra do 10: complexidade acima de 10 é um sinal de alerta — refatore antes de ampliar os testes.
  • Cobertura de instrução não basta: executar 100% das linhas não garante que todos os desvios (V/F) foram avaliados. Prefira a cobertura de desvio como meta mínima.
  • Quem executa: o teste de caixa branca é realizado, em geral, pelos próprios programadores durante o teste de unidade.
  • Cuidado com caminhos inviáveis: alguns caminhos do CFG nunca serão executados com dados reais — escolha caminhos alternativos para satisfazer a cobertura.
  • Ferramentas ajudam: depuradores da IDE, frameworks xUnit (JUnit) e análise estática (SonarQube) automatizam o cálculo da complexidade e a medição de cobertura.
