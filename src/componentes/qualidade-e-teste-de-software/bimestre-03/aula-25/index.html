Teoria & Conceitos

1. Objetivos da Aula

  • Compreender os conceitos e objetivos fundamentais do Teste de Segurança de software.
  • Conhecer e validar a Tríade CIA (Confidencialidade, Integridade e Disponibilidade).
  • Identificar as vulnerabilidades de código mais comuns, como SQL Injection, XSS, Buffer Overflows e Backdoors.
  • Aplicar o princípio de Falha Segura (Fail-Secure) no tratamento de erros.
  • Aprender a elaborar cenários de testes negativos baseados em Casos de Abuso (Misuse Cases).

2. O que é Teste de Segurança?

Diferentemente dos testes funcionais tradicionais, que verificam se o sistema faz o que foi projetado para fazer, o teste de segurança enfoca o que o software não deve fazer. Ele busca garantir que o sistema se comporte de maneira segura e consistente sob todas as condições (esperadas ou inesperadas), e que falhas acidentais não exponham recursos a invasores.

Um dos princípios de ouro do desenvolvimento seguro é o Fail-Secure (Falha Segura): quando o software falhar, o tratamento de erros e exceções deve resolver a falha de forma a não deixar dados, recursos ou o ambiente vulneráveis a ataques ou modificações não autorizadas.

3. A Tríade CIA (CIA Triad)

Qualquer estratégia de segurança da informação é construída sobre três pilares fundamentais, que devem ser validados pelo testador:

Pilar Descrição Foco dos Testes
Confidencialidade Garante que dados e processos sejam protegidos contra revelação ou acesso por pessoas e sistemas não autorizados. Autenticação (login, expiração de senha, proteção de cookies e sessões) e controle de acesso a arquivos e diretórios.
Integridade Garante que as informações e processos não sofram modificações, inserções ou adulterações não autorizadas, seja em trânsito pela rede ou armazenadas em disco. Robustez de algoritmos de criptografia e assinaturas digitais.
Disponibilidade Garante que os dados e processos estejam sempre acessíveis aos usuários autorizados, mesmo sob estresse, picos de tráfego ou tentativas de interrupção de serviço. Resistência a ataques de negação de serviço e restabelecimento íntegro.

4. Principais Ameaças e Vulnerabilidades de Software

Os testadores de segurança devem ter um olhar crítico voltado para as brechas mais exploradas por atacantes. No desenvolvimento de sistemas, as mais críticas incluem:

Vulnerabilidade Descrição Risco
Buffer Overflow Ocorre quando uma aplicação grava mais dados em uma área de memória temporária (buffer) do que ela é capaz de suportar. Permite que atacantes corrompam dados e executem comandos arbitrários no sistema.
SQL Injection Comandos SQL maliciosos são inseridos em campos de entrada (inputs) e enviados diretamente ao banco de dados sem sanitização adequada. Permite acesso não autorizado, manipulação ou destruição de dados no banco.
Cross-Site Scripting (XSS) Scripts maliciosos de terceiros são injetados em páginas web legítimas e executados no navegador de outros usuários. Roubo de sessões, cookies e credenciais de usuários.
Backdoors Atalhos ou mecanismos de acesso alternativos deixados intencionalmente (ou por descuido) por desenvolvedores na aplicação. Comprometem todo o sistema ao fornecer caminhos ocultos de acesso.

5. Protocolos de Comunicação Segura

Para proteger a transmissão de dados contra interceptação (eavesdropping) ou intrusão, o software deve utilizar protocolos que garantam canais seguros:

Protocolo Camada Finalidade
SSL/TLS (HTTPS) Transporte (Layer 4) Autenticação de servidores e criptografia de comunicações em sessões web.
IPSec Rede (Layer 3) Confidencialidade e integridade da comunicação ao nível de rede (muito usado em VPNs).
Wireless (EAP, PEAP, TLS, TTLS) Enlace de dados Autenticação e tráfego seguro em redes sem fio.

6. Princípio de Falha Segura (Fail-Secure)

Quando um sistema encontra uma falha ou exceção, o comportamento deve ser seguro por padrão. Isso significa que:

  • Exceções não tratadas não devem expor dados internos (caminhos de diretório, strings de conexão, stack traces).
  • O sistema deve reverter qualquer estado parcial e bloquear a operação até que a validação seja confirmada.
  • Mensagens de erro devem ser genéricas e amigáveis, evitando revelar detalhes de infraestrutura a atacantes.

Exemplos Práticos

1. Teste de Penetração em SQL Injection

Imagine uma tela de autenticação administrativa simples que conecta a um banco de dados SQL.

Código vulnerável por trás da tela:

SELECT * FROM usuarios WHERE login = '$usuario' AND senha = '$password';

Abordagem do Testador (Caso de Abuso):

No campo de login, em vez de digitar um usuário válido, o testador insere o seguinte comando: 

admin' OR '1'='1

Resultado do teste de penetração:

Como a entrada não foi sanitizada, a query enviada ao banco de dados se torna: 

SELECT * FROM usuarios WHERE login = 'admin' OR '1'='1' AND senha = '...';

Como a condição '1'='1' é sempre verdadeira, o banco de dados ignora a senha e concede acesso total ao testador de segurança.

2. Testando o Princípio de Falha Segura (Fail-Secure)

Cenário: O sistema de faturamento de uma empresa consome uma API externa de pagamentos para aprovar uma transação.

Abordagem do Testador:

  • O testador simula uma falha catastrófica de rede ou a indisponibilidade total da API externa durante o momento do clique de "Pagar".

Análise do comportamento de erro:

Comportamento Descrição
Falha Insegura O sistema dispara uma exceção não tratada na tela (exibindo caminhos de diretório, strings de conexão ou stack trace do código) e aprova a transação localmente sem a confirmação de recebimento da API.
Falha Segura (Esperado) O sistema captura a exceção de forma robusta, exibe uma mensagem genérica amigável ao usuário, reverte qualquer estado de banco de dados e bloqueia a liberação do serviço até que o recebimento seja confirmado e validado com segurança.

Ferramentas de Teste de Segurança

Para as aulas práticas de laboratório, o plano de curso sugere a utilização de ferramentas consolidadas:

Ferramenta Finalidade
Wireshark Análise de protocolos de rede para capturar e inspecionar pacotes em tempo real. Permite verificar se o software transmite dados confidenciais ou credenciais em texto claro (HTTP) em vez de conexões criptografadas (HTTPS).
Nmap Varredura de portas abertas, descoberta de serviços ativos e análise preliminar de vulnerabilidades em sistemas de rede antes de testes de penetração específicos.

Dicas & Lembretes

  • Fail-Secure é o padrão: sempre que o sistema falhar, ele deve se comportar de forma segura — nunca expor dados internos ou permitir operações indevidas.
  • Sanitização de entradas: toda entrada do usuário deve ser validada e sanitizada antes de ser processada — isso previne SQL Injection, XSS e outras vulnerabilidades de injeção.
  • Casos de Abuso (Misuse Cases): ao elaborar testes negativos, pense como um atacante: qual o pior cenário que pode ocorrer se o sistema falhar ou for mal utilizado?
  • Tríade CIA: todo teste de segurança deve, direta ou indiretamente, validar pelo menos um dos três pilares (Confidencialidade, Integridade ou Disponibilidade).
  • Protocolos seguros: sempre valide se o software utiliza HTTPS/TLS para transmissão de dados sensíveis e não envia credenciais em texto claro.
