Enunciado

A empresa SecurePass está desenvolvendo um sistema web simples de Recuperação de Senha — aquele que envia um link para o e-mail do usuário quando ele esquece a senha. O módulo ainda não passou por nenhum teste de segurança e você foi contratado como testador de segurança.

Descrição do Sistema

Quando um usuário esquece a senha, ele informa seu e-mail na tela de login. O sistema gera um token de recuperação, envia um e-mail com um link para o usuário e permite que ele defina uma nova senha a partir desse link.

A URL do link de recuperação tem o seguinte formato: 

https://site.com/recuperar?id=45
  • O parâmetro id identifica o usuário que está recuperando a senha.
  • O token de recuperação é enviado por e-mail e é usado apenas uma vez.
  • O servidor de e-mails da aplicação tem recursos limitados de processamento.

Trabalhando em duplas (programação/teste em pares), vocês devem criar uma planilha de Casos de Abuso (Misuse Cases) para este sistema.

Questão 2: Caso de Abuso — Integridade

A Integridade garante que as informações e processos não sofram modificações, inserções ou adulterações não autorizadas.

Descreva como testar se alterar o ID do usuário na URL do link de recuperação (https://site.com/recuperar?id=45) permite que o atacante altere a senha de um usuário diferente (ex.: mudando o parâmetro para id=46).

Questão 3: Caso de Abuso — Disponibilidade

A Disponibilidade garante que os dados e processos estejam sempre acessíveis aos usuários autorizados, mesmo sob estresse ou tentativas de interrupção.

Descreva como testar se disparar 1.000 requisições consecutivas de "esqueci minha senha" para o mesmo e-mail gera um travamento ou exaustão de memória no servidor de e-mails da aplicação (teste de negação de serviço local).

Questão 4: Teste de Vulnerabilidades de Código

Além dos Casos de Abuso, identifique quais das vulnerabilidades abaixo poderiam estar presentes no sistema de recuperação de senha e explique como você testaria cada uma:

  • SQL Injection — poderia o campo de e-mail ser manipulado para injetar comandos SQL?
  • XSS — poderia o token ou o parâmetro id da URL ser usado para executar scripts maliciosos no navegador de outro usuário?
  • Buffer Overflow — poderia um campo receber mais dados do que suporta e corromper a memória?
  • Backdoor — existe algum acesso alternativo oculto que ignore a validação do token?

Descreva, para cada vulnerabilidade, um caso de teste negativo simples que você executaria.

Questão 5: Falha Segura (Fail-Secure)

Durante seus testes, o sistema da SecurePass apresentou duas falhas. Classifique cada uma como Falha Segura ou Falha Insegura e justifique a sua resposta:

  • Cenário A: Quando a API de envio de e-mails está indisponível, o sistema exibe na tela a mensagem de erro com o caminho completo do servidor de e-mails e a string de conexão do banco de dados, e ainda assim permite ao usuário criar uma nova senha.
  • Cenário B: Quando a API de envio de e-mails está indisponível, o sistema exibe uma mensagem genérica "Serviço temporariamente indisponível, tente novamente mais tarde", reverte qualquer alteração no banco de dados e bloqueia a criação da nova senha.

Orientações

  • Revise o conteúdo da aula antes de começar: Tríade CIA, vulnerabilidades comuns e princípio Fail-Secure.
  • Pense como um atacante: em cada Caso de Abuso, descreva o pior cenário possível e como o sistema deveria se comportar de forma segura.
  • Na Questão 1, lembre-se de que a Confidencialidade envolve a proteção dos dados em trânsito e o acesso restrito.
  • Na Questão 2, o sistema deve validar se o token usado é do usuário dono da conta referenciada pelo id da URL.
  • Na Questão 3, a Disponibilidade envolve a resistência a ataques de negação de serviço e a recuperação íntegra.
