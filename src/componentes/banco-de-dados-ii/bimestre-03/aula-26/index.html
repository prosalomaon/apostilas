Teoria & Conceitos

1. Por que tratar exceções?

Qualquer operação de banco de dados pode falhar devido a problemas de rede, permissões, violações de integridade ou erros de sintaxe. Planejar para a falha é fundamental: se você não verificar os erros, não saberá por que o programa falhou, agindo "às cegas" no desenvolvimento.

2. Os Três Valores de Erro do MySQL

Quando um erro ocorre no MySQL, ele fornece três valores cruciais para o tratamento:

Valor Descrição Exemplo
Número do Erro Código numérico específico do MySQL. 1062 (duplicata de chave)
Mensagem Descritiva Texto explicando o que aconteceu. Duplicate entry '5' for key 'PRIMARY'
SQLSTATE Código de cinco caracteres padronizado (ANSI/ODBC) que permite maior portabilidade entre diferentes SGBDs. 23000 (integridade referencial)

Por que usar SQLSTATE?

O SQLSTATE é padronizado pela ANSI/ODBC, ao contrário do número de erro que é específico do MySQL. Sempre que possível, baseie sua lógica de tratamento no código SQLSTATE, pois ele é mais estável entre diferentes versões de drivers e SGBDs.

Tratamento em Linguagens de Programação

Diferentes APIs possuem mecanismos distintos para capturar erros de banco de dados. Vejamos as três mais comuns.

A. PHP (via PDO)

O PDO pode ser configurado para lançar exceções automaticamente, o que é a prática recomendada para evitar checagens manuais após cada comando. 

<?php
try {
    $dsn = "mysql:host=localhost;dbname=cookbook";
    $dbh = new PDO($dsn, "usuario", "senha");

    // Configura o PDO para lançar exceções em caso de erro
    $dbh->setAttribute(PDO::ATTR_ERRMODE, PDO::ERRMODE_EXCEPTION);

    // Exemplo: inserção com tratamento de erro
    $stmt = $dbh->prepare("INSERT INTO receitas (nome, tempo_prep) VALUES (?, ?)");
    $stmt->execute(["Bolo de Chocolate", 45]);

} catch (PDOException $e) {
    echo "Falha na operação: " . $e->getMessage();
    // Código específico do PDO: $e->getCode()
    // Mensagem completa: $e->getMessage()
}
?>

O atributo ERRMODE_EXCEPTION faz com que o PDO lance uma PDOException sempre que uma operação falhar, unificando o tratamento em um único bloco try...catch.

B. Python (mysql.connector)

Utiliza o bloco try...except para capturar objetos da classe Error, que expõe os três valores de erro diretamente no objeto. 

import mysql.connector
from mysql.connector import Error

try:
    conn = mysql.connector.connect(
        host="localhost",
        database="cookbook",
        user="usuario",
        password="senha"
    )

    cursor = conn.cursor()
    cursor.execute("INSERT INTO receitas (nome, tempo_prep) VALUES (%s, %s)",
                   ("Bolo de Chocolate", 45))
    conn.commit()

except Error as e:
    print(f"Erro MySQL: {e.msg}")       # Mensagem descritiva
    print(f"Código: {e.errno}")         # Número do erro
    print(f"SQLSTATE: {e.sqlstate}")    # Código SQLSTATE

finally:
    if conn.is_connected():
        cursor.close()
        conn.close()

Repare que o objeto Error do Python expõe os três valores diretamente: .msg, .errno e .sqlstate.

C. Java (JDBC)

O Java utiliza a classe SQLException. Além de erros fatais, o JDBC permite capturar SQLWarnings, que são avisos não fatais que não interrompem o programa, mas fornecem metadados sobre a operação. 

import java.sql.Connection;
import java.sql.DriverManager;
import java.sql.SQLException;
import java.sql.SQLWarning;

public class ExemploExcecao {
    public static void main(String[] args) {
        String url = "jdbc:mysql://localhost:3306/cookbook";

        try (Connection conn = DriverManager.getConnection(url, "usuario", "senha")) {

            // Verifica se há avisos (warnings) na conexão
            SQLWarning warning = conn.getWarnings();
            while (warning != null) {
                System.out.println("Aviso SQL: " + warning.getMessage());
                System.out.println("SQLSTATE: " + warning.getSQLState());
                warning = warning.getNextWarning();
            }

        } catch (SQLException e) {
            // Erro numérico
            System.out.println("Código do erro: " + e.getErrorCode());
            // SQLSTATE
            System.out.println("SQLSTATE: " + e.getSQLState());
            // Mensagem descritiva
            System.out.println("Mensagem: " + e.getMessage());
        }
    }
}

A SQLException é uma exceção checked — o compilador obriga você a tratá-la ou repassá-la. Os métodos getErrorCode(), getSQLState() e getMessage() fornecem os três valores de erro do MySQL.

Comparação entre Linguagens

Linguagem Mecanismo Classe/Exceção Acesso aos Valores
PHP try...catch PDOException getMessage(), getCode()
Python try...except mysql.connector.Error .msg, .errno, .sqlstate
Java try...catch (checked) SQLException getMessage(), getErrorCode(), getSQLState()

Tratamento Interno no Banco (Stored Programs)

Dentro de Stored Procedures e Functions, utiliza-se o comando DECLARE ... HANDLER para capturar condições específicas. Existem dois tipos principais:

  • CONTINUE: Captura o erro e segue o fluxo normalmente após o tratamento.
  • EXIT: Captura o erro e encerra o bloco imediatamente.

Exemplo: DROP USER seguro com CONTINUE HANDLER

Alguns comandos não suportam a cláusula IF EXISTS e podem gerar erro se o objeto não existir. Podemos usar um handler para ignorar esse erro específico: 

DELIMITER $$

CREATE PROCEDURE drop_user_safe(user_name TEXT, host_name TEXT)
BEGIN
    -- Declara um handler para capturar o erro 1396 (usuário inexistente)
    -- CONTINUE: ignora o erro e segue o fluxo
    DECLARE CONTINUE HANDLER FOR 1396 BEGIN END;

    SET @stmt = CONCAT('DROP USER ', QUOTE(user_name), '@', QUOTE(host_name));
    PREPARE s FROM @stmt;
    EXECUTE s;
    DEALLOCATE PREPARE s;
END $$

DELIMITER ;

-- Se o usuário não existir, o procedure simplesmente não faz nada (sem erro)
CALL drop_user_safe('usuario_inexistente', 'localhost');
flowchart TD A([Início do Bloco]) --> B[Declara CONTINUE HANDLER FOR 1396] B --> C[Executa DROP USER] C --> D{Erro 1396?} D -->|Não| E[Usuário removido com sucesso] D -->|Sim| F["Handler captura o erro e ignora"] F --> G[Fluxo continua normalmente] E --> H([Fim do Bloco]) G --> H

Exemplo: EXIT Handler com ROLLBACK

Quando o erro é crítico e a operação deve ser completamente desfeita, usamos o EXIT HANDLER: 

DELIMITER $$

CREATE PROCEDURE TransacaoSegura(IN id_cliente INT, IN valor DECIMAL(10,2))
BEGIN
    -- EXIT: qualquer erro desfaz a transação e aborta
    DECLARE EXIT HANDLER FOR SQLEXCEPTION
    BEGIN
        ROLLBACK;
        SIGNAL SQLSTATE '45000'
        SET MESSAGE_TEXT = 'Erro na transação — todas as operações foram desfeitas';
    END;

    START TRANSACTION;

    INSERT INTO movimentos (id_cliente, tipo, valor, data_movimento)
    VALUES (id_cliente, 'CREDITO', valor, NOW());

    UPDATE contas SET saldo = saldo + valor WHERE id_cliente = id_cliente;

    COMMIT;
END $$

DELIMITER ;

-- Execução com sucesso
CALL TransacaoSegura(1, 500.00);

-- Execução com erro (id_cliente inexistente) → ROLLBACK automático
CALL TransacaoSegura(999, 500.00);

Lançando Erros Customizados (SIGNAL)

O desenvolvedor pode criar suas próprias exceções para validar regras de negócio complexas que as restrições (CONSTRAINTS) comuns não alcançam. O comando SIGNAL permite emitir um erro com código SQLSTATE e mensagem personalizada.

Exemplo: Rejeitando divisão por zero

DELIMITER $$

CREATE FUNCTION divide_seguro(numerador DECIMAL(10,2), denominador DECIMAL(10,2))
RETURNS DECIMAL(10,2)
DETERMINISTIC
BEGIN
    -- Validação de regra de negócio: divisor não pode ser zero
    IF denominador = 0 THEN
        SIGNAL SQLSTATE '22012'  -- Código padrão para divisão por zero
        SET MESSAGE_TEXT = 'Erro de Negócio: O divisor não pode ser zero';
    END IF;

    RETURN numerador / denominador;
END $$

DELIMITER ;

-- Funciona normalmente
SELECT divide_seguro(10, 2);   -- retorna 5.00

-- Dispara erro customizado
SELECT divide_seguro(10, 0);   -- Erro: Erro de Negócio: O divisor não pode ser zero

Exemplo: Validação de intervalo de dados

DELIMITER $$

CREATE PROCEDURE RegistraNota(
    IN p_aluno_id INT,
    IN p_nota DECIMAL(4,2)
)
BEGIN
    -- Validar que a nota está entre 0 e 10
    IF p_nota < 0 OR p_nota > 10 THEN
        SIGNAL SQLSTATE '22000'  -- constraint violation genérica
        SET MESSAGE_TEXT = 'A nota deve estar entre 0 e 10';
    END IF;

    -- Validar que o aluno existe
    IF NOT EXISTS (SELECT 1 FROM alunos WHERE id = p_aluno_id) THEN
        SIGNAL SQLSTATE '23000'  -- integrity constraint violation
        SET MESSAGE_TEXT = 'Aluno não encontrado no sistema';
    END IF;

    INSERT INTO notas (aluno_id, nota, data_registro)
    VALUES (p_aluno_id, p_nota, NOW());
END $$

DELIMITER ;

-- Validações funcionam:
CALL RegistraNota(1, 11.00);   -- Erro: A nota deve estar entre 0 e 10
CALL RegistraNota(999, 8.50);  -- Erro: Aluno não encontrado no sistema
CALL RegistraNota(1, 8.50);    -- Sucesso

Boas Práticas e Estratégias

1. Encapsulamento

Centralize o código de conexão e tratamento de erros em bibliotecas ou classes de "Camada de Persistência" para isolar o acesso direto ao banco da lógica da aplicação. Isso facilita a manutenção e torna o código mais testável.

2. Logs do Servidor

Utilize o Error Log do servidor MySQL para monitorar falhas críticas que ocorrem durante o funcionamento do daemon, como erros de configuração ou corrupção de arquivos. Não confie apenas nos erros capturados pela aplicação — o log do servidor é a fonte definitiva de diagnóstico.

3. Transações com Tratamento de Erro

Sempre use blocos de exceção ao realizar transações. Se qualquer comando falhar, o tratamento de erro deve invocar obrigatoriamente um ROLLBACK para garantir que o banco não fique inconsistente. 

-- MySQL: Padrão seguro para transações
DELIMITER $$

CREATE PROCEDURE TransacaoCompleta(IN id_pedido INT)
BEGIN
    DECLARE EXIT HANDLER FOR SQLEXCEPTION
    BEGIN
        ROLLBACK;
        SIGNAL SQLSTATE '45000'
        SET MESSAGE_TEXT = 'Falha na transação — rollback executado';
    END;

    START TRANSACTION;

    UPDATE estoque SET quantidade = quantidade - 1 WHERE produto_id = id_pedido;
    INSERT INTO movimentacoes (pedido_id, tipo, data) VALUES (id_pedido, 'SAIDA', NOW());

    -- Se algum dos comandos acima falhar, o ROLLBACK é executado automaticamente
    COMMIT;
END $$

DELIMITER ;

4. Sanitização

Use o tratamento de erros em conjunto com Placeholders (? ou %s) para prevenir ataques de SQL Injection, que muitas vezes tentam forçar erros no banco para extrair informações do esquema.

5. Warnings: o erro silencioso

Não ignore os avisos (SHOW WARNINGS). Eles podem indicar truncamento de dados que, embora não interrompam o sistema, causam perda de integridade silenciosa. 

-- Exemplo: dados truncados geram warning, não erro
CREATE TABLE testa_tamanho (nome VARCHAR(5));

INSERT INTO testa_tamanho VALUES ('Nome muito longo para a coluna');

-- O MySQL aceita a inserção (sem erro), mas TRUNCA o dado
-- Use SHOW WARNINGS para detectar o problema:
SHOW WARNINGS;

Dicas & Lembretes

  • SQLSTATE primeiro: Sempre que possível, baseie sua lógica de tratamento no código SQLSTATE, pois ele é mais estável entre diferentes versões de drivers e SGBDs.
  • Warnings importam: Não ignore SHOW WARNINGS. Truncamento silencioso de dados pode causar problemas difíceis de rastrear depois.
  • Transação + Handler: Sempre combine bloco de transação com handler de exceção. Se qualquer comando dentro do START TRANSACTION falhar, o ROLLBACK deve ser executado.
  • SIGNAL para regras de negócio: Use SIGNAL quando as constraints do banco não são suficientes para validar regras complexas.
  • EXIT vs CONTINUE: Use EXIT para erros críticos que devem interromper o bloco; use CONTINUE quando o erro pode ser ignorado seguramente.
  • Evolução: Se o projeto crescer e o tratamento de erros se tornar muito complexo, considere migrar para frameworks que oferecem tratamento centralizado (como Spring para Java ou Django ORM para Python).

Como aplicar na Prática

  • Formulários web: Capture exceções PDO/SQLException ao salvar dados de formulário e exiba mensagens amigáveis ao usuário (em vez de traces técnicos).
  • APIs REST: Retorne códigos HTTP apropriados (400, 500) baseados no tipo de exceção capturada no acesso ao banco.
  • Stored Procedures críticas: Sempre inclua um EXIT HANDLER FOR SQLEXCEPTION com ROLLBACK em procedures que executam transações.
  • Validação de dados: Use SIGNAL para criar validações de regra de negócio que não podem ser expressas apenas com CHECK constraints.
  • Monitoramento: Implemente logs estruturados que registrem o SQLSTATE, a mensagem e o contexto da operação para facilitar o diagnóstico em produção.
