Teoria & Conceitos

Enquanto a aula anterior focou nos conceitos básicos e sintaxe, esta etapa foca em como e quando utilizar gatilhos para resolver problemas reais de arquitetura e performance em ambientes MySQL e PostgreSQL.

1. Gatilhos em Visões (PostgreSQL vs. MySQL)

Uma das aplicações mais poderosas dos gatilhos é tornar as Visões (Views) atualizáveis, especialmente quando elas envolvem junções complexas.

  • PostgreSQL: Oferece o tipo de gatilho INSTEAD OF. Quando o usuário tenta um INSERT, UPDATE ou DELETE em uma visão, o PostgreSQL não executa a ação na visão (que é virtual), mas sim o código do gatilho, que redireciona os dados para as tabelas físicas corretas.
  • MySQL: Tradicionalmente, o MySQL não suporta gatilhos INSTEAD OF em visões. Para obter esse comportamento, é necessário criar gatilhos nas tabelas base ou utilizar procedimentos armazenados.

Exemplo PostgreSQL (Tornando uma View de Vendas atualizável)

CREATE OR REPLACE FUNCTION func_venda_view() RETURNS trigger AS $$
BEGIN
    IF (TG_OP = 'INSERT') THEN
        INSERT INTO fatos_vendas (id_produto, qtd) VALUES (NEW.id_produto, NEW.qtd);
        RETURN NEW;
    END IF;
END;
$$ LANGUAGE plpgsql;

CREATE TRIGGER tr_venda_view
INSTEAD OF INSERT ON vw_resumo_vendas
FOR EACH ROW EXECUTE PROCEDURE func_venda_view();

2. Simulação de Funcionalidades

Gatilhos podem ser usados para "emular" recursos que o SGBD não possui nativamente ou para automatizar metadados.

A. Índices Baseados em Funções (MySQL)

O MySQL (versões mais antigas) não indexa o resultado de funções. Para acelerar buscas complexas (ex: WHERE LOG10(valor) < 2), você pode:

  1. Criar uma coluna extra para armazenar o resultado da função.
  2. Usar um gatilho BEFORE INSERT e BEFORE UPDATE para manter essa coluna atualizada automaticamente.

B. Simulação de Auto-Update (PostgreSQL/MySQL)

Gatilhos BEFORE UPDATE são ideais para manter colunas de auditoria, como data_ultima_alteracao, garantindo que o valor mude apenas se os dados da linha forem efetivamente alterados. 

-- PostgreSQL: mantém a coluna de auditoria sempre atualizada
CREATE OR REPLACE FUNCTION func_atualiza_alteracao() RETURNS trigger AS $$
BEGIN
    IF (TG_OP = 'UPDATE') THEN
        NEW.data_ultima_alteracao := CURRENT_TIMESTAMP;
    END IF;
    RETURN NEW;
END;
$$ LANGUAGE plpgsql;

CREATE TRIGGER tr_auto_update_produtos
BEFORE UPDATE ON produtos
FOR EACH ROW EXECUTE PROCEDURE func_atualiza_alteracao();

3. Saneamento e Rejeição de Dados

Diferente das restrições (CHECK constraints), os gatilhos permitem lógica procedimental para tratar dados antes da gravação.

  • Saneamento: Um gatilho BEFORE INSERT pode converter nomes para maiúsculas ou remover espaços em branco indesejados.
  • Rejeição: Se uma regra complexa for violada (ex: um cliente não pode comprar se tiver débitos em outra tabela), o gatilho pode disparar um erro, cancelando a transação.

Exemplo MySQL (Rejeição de dados fora de faixa)

CREATE TRIGGER bi_valida_estoque
BEFORE INSERT ON item_pedido
FOR EACH ROW
BEGIN
    IF NEW.quantidade <= 0 THEN
        SIGNAL SQLSTATE '45000' SET MESSAGE_TEXT = 'Quantidade deve ser positiva';
    END IF;
END;

4. Auditoria e Logs de Alterações

Gatilhos AFTER são os mais recomendados para auditoria, pois são disparados apenas após o sucesso da operação principal, garantindo que o log reflita a realidade do banco.

  • INSERT: Registra o estado inicial (NEW).
  • UPDATE: Registra o que mudou (comparando OLD e NEW).
  • DELETE: Salva uma cópia dos dados removidos para histórico (OLD).

Estratégia de Tabela de Log: Recomenda-se criar uma tabela auditoria_log com colunas para o usuário, data/hora, tipo de operação e os valores afetados. 

CREATE TABLE auditoria_log (
    id_log INT AUTO_INCREMENT PRIMARY KEY,
    tabela VARCHAR(100) NOT NULL,
    operacao VARCHAR(10) NOT NULL,
    usuario VARCHAR(100),
    valor_antigo TEXT,
    valor_novo TEXT,
    data_hora DATETIME DEFAULT NOW()
);

-- Registra uma cópia do registro removido para histórico (MySQL)
CREATE TRIGGER ad_produto_auditoria
AFTER DELETE ON produto
FOR EACH ROW
BEGIN
    INSERT INTO auditoria_log (tabela, operacao, usuario, valor_antigo)
    VALUES ('produto', 'DELETE', CURRENT_USER(), CONCAT(OLD.codigo, ' - ', OLD.descricao_produto));
END;

UPDATE OLD vs NEW Registrar exatamente o que mudou.

5. Gatilhos de Instrução vs. Gatilhos de Linha (PostgreSQL)

O PostgreSQL permite distinguir a frequência de execução do gatilho:

  • FOR EACH ROW: Executa uma vez para cada linha. Se um comando apaga 50 linhas, o gatilho roda 50 vezes. É o padrão para auditoria detalhada.
  • FOR EACH STATEMENT: Executa apenas uma vez por comando SQL, independente de quantas linhas foram afetadas. É ideal para tarefas administrativas pesadas, como atualizar uma tabela de totais apenas uma vez após uma carga massiva de dados.
-- Executa UMA vez por comando, mesmo que milhares de linhas sejam afetadas
CREATE OR REPLACE FUNCTION func_recalcula_totais() RETURNS trigger AS $$
BEGIN
    UPDATE resumo_vendas SET total = (SELECT SUM(qtd) FROM fatos_vendas);
    RETURN NULL;
END;
$$ LANGUAGE plpgsql;

CREATE TRIGGER tr_recalcula_totais
AFTER INSERT ON fatos_vendas
FOR EACH STATEMENT EXECUTE PROCEDURE func_recalcula_totais();
Frequência Quando executa Uso ideal
FOR EACH ROW Uma vez para cada linha afetada Auditoria detalhada (registrar cada alteração).
FOR EACH STATEMENT Uma vez por comando SQL Tarefas administrativas e recálculo de totais após cargas massivas.

Dicas & Lembretes

  • Cascata de Gatilhos: Evite que o Gatilho A altere a Tabela B, que por sua vez dispara um gatilho que altera a Tabela A. Isso pode causar loops infinitos ou estouro de pilha de execução.
  • Performance: Em bancos de dados de alto tráfego (OLTP), gatilhos em excesso podem aumentar a latência das operações de escrita, pois cada comando precisa esperar a finalização de toda a lógica do gatilho antes de confirmar (COMMIT).
  • Visibilidade: No PostgreSQL, os gatilhos podem usar a cláusula WHEN para rodar apenas se uma condição específica for atendida, economizando processamento.

Como aplicar na Prática

  • Visões de relatório atualizáveis: Em vez de manter um sistema separado para escrever dados, use INSTEAD OF (PostgreSQL) para permitir gravações através de visões de resumo.
  • Normalização automática de texto: Aplique UPPER() e TRIM() em um BEFORE INSERT para garantir consistência de dados cadastrais.
  • Histórico de preços: Registre em uma tabela de histórico sempre que um preço mudar, preservando o OLD.valor para consultas futuras.
  • Totais consolidados: Após cargas em lote, use um único gatilho FOR EACH STATEMENT para recalcular tabelas de resumo em vez de executar a soma a cada linha inserida.
