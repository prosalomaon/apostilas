Cenário: Loja Virtual de Games "GameShop"

Esta demonstração pratica todos os conceitos da aula — BEFORE/AFTER, INSERT/UPDATE/DELETE, palavras-chave NEW e OLD — em um único exemplo integrado. O banco de dados gerencia clientes, pedidos e estoque de uma loja virtual de games.

Copie e execute cada bloco de código na ordem apresentada no MySQL Workbench ou terminal. Ao final, você terá um ambiente completo com 5 gatilhos funcionando.

Passo 1 — Estrutura das Tabelas

Primeiro, criamos as tabelas do banco de dados. A tabela log_auditoria será usada pelos gatilhos para registrar todas as operações realizadas. 

-- Limpeza preventiva do ambiente de teste
SET FOREIGN_KEY_CHECKS = 0;
DROP TABLE IF EXISTS itens_pedido;
DROP TABLE IF EXISTS pedidos;
DROP TABLE IF EXISTS log_auditoria;
DROP TABLE IF EXISTS produtos;
DROP TABLE IF EXISTS clientes;
SET FOREIGN_KEY_CHECKS = 1;

-- Tabela 1: Cadastro de Clientes
CREATE TABLE clientes (
    id INT PRIMARY KEY AUTO_INCREMENT,
    nome VARCHAR(100) NOT NULL,
    email VARCHAR(100) NOT NULL,
    data_cadastro DATE NOT NULL
);

-- Tabela 2: Catálogo de Produtos
CREATE TABLE produtos (
    id INT PRIMARY KEY AUTO_INCREMENT,
    nome VARCHAR(100) NOT NULL,
    preco DECIMAL(10,2) NOT NULL,
    estoque_atual INT NOT NULL DEFAULT 0
);

-- Tabela 3: Registro de Pedidos
CREATE TABLE pedidos (
    id INT PRIMARY KEY AUTO_INCREMENT,
    id_cliente INT NOT NULL,
    valor_total DECIMAL(10,2) NOT NULL DEFAULT 0.00,
    status VARCHAR(30) NOT NULL DEFAULT 'PENDENTE',
    data_pedido DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
    FOREIGN KEY (id_cliente) REFERENCES clientes(id)
);

-- Tabela 4: Itens de Cada Pedido
CREATE TABLE itens_pedido (
    id INT PRIMARY KEY AUTO_INCREMENT,
    id_pedido INT NOT NULL,
    id_produto INT NOT NULL,
    quantidade INT NOT NULL,
    preco_unitario DECIMAL(10,2) NOT NULL,
    FOREIGN KEY (id_pedido) REFERENCES pedidos(id),
    FOREIGN KEY (id_produto) REFERENCES produtos(id)
);

-- Tabela 5: Log de Auditoria (destino dos registros dos triggers)
CREATE TABLE log_auditoria (
    id INT PRIMARY KEY AUTO_INCREMENT,
    tabela_alvo VARCHAR(50) NOT NULL,
    operacao VARCHAR(10) NOT NULL,
    detalhes TEXT,
    data_operacao DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP
);

Passo 3 — Gatilho BEFORE INSERT: Validação de Dados

Conceito: BEFORE INSERT executa antes do dado ser gravado na tabela. É ideal para validar ou modificar valores que estão sendo inseridos.

Este gatilho verifica se o email do cliente contém o caractere @. Se não contiver, o inserts é bloqueado com uma mensagem de erro usando SIGNAL SQLSTATE. 

DELIMITER //

CREATE TRIGGER trg_valida_email_cliente
BEFORE INSERT ON clientes
FOR EACH ROW
BEGIN
    -- Valida se o email contém o caractere "@"
    IF NEW.email NOT LIKE '%@%' THEN
        SIGNAL SQLSTATE '45000'
        SET MESSAGE_TEXT = 'ERRO: O email informado é inválido. O campo deve conter o caractere "@".';
    END IF;
END //

DELIMITER ;

Testando o Gatilho

Execute os dois inserts abaixo. O primeiro será bloqueado pelo gatilho; o segundo será aceito:

-- ERRO ESPERADO: email sem "@"
INSERT INTO clientes (nome, email, data_cadastro)
VALUES ('Teste Erro', 'emailinvalido.com', '2026-05-01');

-- INSERÇÃO BEM-SUCEDIDA
INSERT INTO clientes (nome, email, data_cadastro)
VALUES ('Pedro Santos', 'pedro@email.com', '2026-05-01');

Por que funciona?

A palavra-chave NEW.email acessa o valor que está sendo inserido antes de ele chegar à tabela. O SIGNAL SQLSTATE '45000' é o mecanismo do MySQL para lançar uma exceção customizada e interromper a operação.

Passo 4 — Gatilho AFTER INSERT: Log de Auditoria

Conceito: AFTER INSERT executa depois do dado ser gravado com sucesso. É usado para registrar o que aconteceu, sem interferir na operação original.

Todo novo cliente inserido gera automaticamente um registro na tabela log_auditoria, capturando nome, email e data/hora. 

DELIMITER //

CREATE TRIGGER trg_log_insert_cliente
AFTER INSERT ON clientes
FOR EACH ROW
BEGIN
    INSERT INTO log_auditoria (tabela_alvo, operacao, detalhes)
    VALUES (
        'clientes',
        'INSERT',
        CONCAT(
            'Novo cliente cadastrado: ',
            NEW.nome,
            ' | Email: ',
            NEW.email,
            ' | Data: ',
            NEW.data_cadastro
        )
    );
END //

DELIMITER ;

Testando o Gatilho

Insira um novo cliente e consulte a tabela de log:

-- Inserindo um novo cliente (o trigger gera o log automaticamente)
INSERT INTO clientes (nome, email, data_cadastro)
VALUES ('Lucia Ferreira', 'lucia@email.com', '2026-05-10');

-- Consultando o log de auditoria gerado
SELECT * FROM log_auditoria;

O resultado mostrará um registro com operacao = 'INSERT' e os detalhes completos do cliente recém-cadastrado.

Passo 5 — Gatilho BEFORE UPDATE: Proteção de Status

Conceito: BEFORE UPDATE permite interceptar e modificar valores antes que a alteração seja gravada. Aqui, impedimos que um pedido com status 'CANCELADO' tenha seu status alterado para qualquer outro valor.

Este é um exemplo clássico de regra de negócio enforcement: uma vez cancelado, o pedido não pode ser reaberto. 

DELIMITER //

CREATE TRIGGER trg_bloqueia_reabertura_pedido
BEFORE UPDATE ON pedidos
FOR EACH ROW
BEGIN
    -- Se o pedido já estava CANCELADO, bloqueia qualquer alteração de status
    IF OLD.status = 'CANCELADO' AND NEW.status != 'CANCELADO' THEN
        SIGNAL SQLSTATE '45000'
        SET MESSAGE_TEXT = 'ERRO: Não é possível alterar o status de um pedido que já foi CANCELADO.';
    END IF;
END //

DELIMITER ;

Testando o Gatilho

-- Passo A: Cancele o pedido de exemplo
UPDATE pedidos SET status = 'CANCELADO' WHERE id = 1;

-- Passo B: Tente reabrir o pedido (ERRO ESPERADO)
UPDATE pedidos SET status = 'CONFIRMADO' WHERE id = 1;

-- Passo C: Verifique que o pedido continua CANCELADO
SELECT id, status FROM pedidos WHERE id = 1;

Palavra-chave OLD vs NEW

Neste trigger, usamos OLD.status para ler o valor atual (antes da alteração) e NEW.status para ler o valor novo (que está tentando ser gravado). A comparação entre os dois permite validar a transição de estados.

Passo 6 — Gatilho AFTER UPDATE: Trilha de Auditoria Completa

Conceito: AFTER UPDATE registra o que mudou, comparando OLD e NEW. Este é o padrão mais comum em sistemas empresariais: a tabela de log recebe uma linha descrevendo exatamente o que foi alterado. 

DELIMITER //

CREATE TRIGGER trg_log_update_pedido
AFTER UPDATE ON pedidos
FOR EACH ROW
BEGIN
    -- Só registra se o status realmente mudou
    IF OLD.status != NEW.status THEN
        INSERT INTO log_auditoria (tabela_alvo, operacao, detalhes)
        VALUES (
            'pedidos',
            'UPDATE',
            CONCAT(
                'Pedido #', NEW.id,
                ' | Status alterado de "', OLD.status,
                '" para "', NEW.status,
                '" | Valor: R$ ', NEW.valor_total
            )
        );
    END IF;
END //

DELIMITER ;

Testando o Gatilho

-- Criando um novo pedido para testar a auditoria
INSERT INTO pedidos (id, id_cliente, valor_total, status, data_pedido) VALUES
(2, 2, 199.90, 'PENDENTE', '2026-05-15 14:30:00');

-- Alterando o status (o trigger gera o log)
UPDATE pedidos SET status = 'CONFIRMADO' WHERE id = 2;

-- Consultando TODOS os logs de auditoria gerados até agora
SELECT id, tabela_alvo, operacao, detalhes, data_operacao
FROM log_auditoria
ORDER BY id;

Passo 7 — Gatilho BEFORE DELETE: Proteção de Integridade

Conceito: BEFORE DELETE impede a exclusão de registros que possuem dependentes. Aqui, bloqueamos a exclusão de um cliente que possui pedidos associados, garantindo a integridade referencial além da chave estrangeira. 

DELIMITER //

CREATE TRIGGER trg_bloqueia_delete_cliente_com_pedido
BEFORE DELETE ON clientes
FOR EACH ROW
BEGIN
    DECLARE total_pedidos INT;

    -- Conta quantos pedidos estão associados ao cliente
    SELECT COUNT(*) INTO total_pedidos
    FROM pedidos
    WHERE id_cliente = OLD.id;

    -- Se existir pelo menos 1 pedido, bloqueia a exclusão
    IF total_pedidos > 0 THEN
        SIGNAL SQLSTATE '45000'
        SET MESSAGE_TEXT = 'ERRO: Não é possível excluir um cliente que possui pedidos registrados.';
    END IF;
END //

DELIMITER ;

Testando o Gatilho

-- ERRO ESPERADO: Cliente 1 possui pedidos
DELETE FROM clientes WHERE id = 1;

-- SUCESSO: Cliente 3 não possui pedidos
DELETE FROM clientes WHERE id = 3;

-- Confirmando que o cliente 1 ainda existe
SELECT id, nome FROM clientes WHERE id = 1;

Palavra-chave OLD no DELETE

Em um BEFORE DELETE, apenas OLD está disponível — não existe NEW, pois o registro está sendo removido. Usamos OLD.id para acessar a chave primária do registro que está prestes a ser excluído.

Passo 8 — Validação Final: Todos os Logs

Consulte a tabela de auditoria para ver todas as operações registradas pelos gatilhos ao longo da demonstração: 

-- Relatório completo de auditoria
SELECT 
    id,
    tabela_alvo AS 'Tabela',
    operacao AS 'Operação',
    detalhes AS 'Detalhes',
    DATE_FORMAT(data_operacao, '%d/%m/%Y %H:%i:%s') AS 'Data/Hora'
FROM log_auditoria
ORDER BY id;

Bônus: Como Remover um Gatilho

Caso precise desativar ou corrigir um gatilho, utilize o comando DROP TRIGGER: 

-- Removendo um gatilho específico
DROP TRIGGER IF EXISTS trg_valida_email_cliente;

-- Listando todos os gatilhos da tabela "clientes"
SHOW TRIGGERS LIKE 'clientes';

Dicas & Lembretes

  • Ordem de execução: Sempre crie as tabelas primeiro, depois os triggers, e por último insira os dados de teste. Se criar um trigger antes da tabela existir, o SGBD retorna erro.
  • DELIMITER: No MySQL, o DELIMITER // é necessário porque o trigger contém ";" internos. Sem ele, o MySQL interpreta o ";" como o fim do comando antes do bloco terminar.
  • Depuração: Se um trigger causar comportamento inesperado, consulte SHOW TRIGGERS para listá-los e DROP TRIGGER para removê-los antes de recriá-los.
  • Performance: Evite triggers com consultas complexas em tabelas grandes. Cada INSERT/UPDATE dispara o trigger automaticamente, e queries lentas dentro dele afetam diretamente o tempo de resposta da operação.
