1. Revisão Rápida dos Fundamentos

Antes de revisarmos os conteúdos do terceiro bimestre, vamos relembrar rapidamente as bases que sustentam a programabilidade no banco de dados.

1.1 Transações e Controle de Concorrência

Uma transação é uma sequência de operações executada como uma unidade atômica. Ela deve respeitar as propriedades ACID:

Propriedade Significado
Atomicidade Tudo ou nada: ou todas as operações são aplicadas ou nenhuma delas.
Consistência A transação leva o banco de um estado válido a outro estado válido.
Isolamento Transações concorrentes não interferem umas nas outras.
Durabilidade Após o commit, as mudanças persistem mesmo em caso de falha. 
START TRANSACTION;

UPDATE contas SET saldo = saldo - 100.00 WHERE id_conta = 1;
UPDATE contas SET saldo = saldo + 100.00 WHERE id_conta = 2;

-- Se tudo der certo:
COMMIT;
-- Se algo falhar:
-- ROLLBACK;

Por que transações importam para esta revisão?

Dentro de Stored Procedures e Triggers, as transações precisam ser gerenciadas com cuidado. É um dos pontos que mais conectam o conteúdo do 2º com o 3º bimestre: uma procedure que manipula múltiplas tabelas deve garantir que todas as operações sejam atômicas.

1.2 DQL Avançada, Joins e Agregações

Consultas de leitura são a base de toda a extração de dados. Relembre os principais agrupamentos conceituais:

  • Predicados: IN, LIKE e BETWEEN para filtrar conjuntos de valores, padrões e intervalos.
  • Junções (Joins): INNER JOIN, LEFT/RIGHT JOIN e FULL JOIN para combinar dados de múltiplas tabelas.
  • Agregações: COUNT, SUM, AVG, MIN e MAX combinadas com GROUP BY e a condição HAVING.
  • Subqueries: consultas aninhadas usadas na cláusula WHERE, no FROM ou na lista de seleção.
SELECT v.nome,
       COUNT(p.id_pedido) AS total_pedidos,
       SUM(p.valor_total) AS faturamento
FROM vendedores v
LEFT JOIN pedidos p ON p.id_vendedor = v.id
WHERE v.nome LIKE 'A%'
GROUP BY v.nome
HAVING SUM(p.valor_total) > 1000.00
ORDER BY faturamento DESC;

1.3 Views e Índices

  • Views: são consultas nomeadas que se comportam como tabelas virtuais, encapsulando consultas complexas e restringindo o acesso a colunas sensíveis.
  • Índices: estruturas físicas que aceleram a busca, mas que precisam ser planejados com cuidado (colunas muito seletivas e muito consultadas).

2. Blocos de Linguagem SQL

Todo o conteúdo de programação do 3º bimestre começa pelos blocos de linguagem SQL — estruturas que agrupam uma ou mais instruções para execução procedural no servidor.

  • Bloco BEGIN...END: agrupa múltiplas instruções em uma única unidade lógica.
  • Variáveis locais: declaradas com DECLARE e usadas apenas dentro do bloco.
  • Estruturas de controle: IF...ELSE, CASE, WHILE, LOOP e REPEAT.
  • Cursores: permitem percorrer linha a linha o resultado de uma consulta dentro do programa armazenado.

2.1 Exemplo com Cursor

O cursor é usado quando precisamos processar linha por linha o resultado de um SELECT. O ciclo básico é: DECLARE cursor → OPEN → FETCH (dentro de um loop) → CLOSE. Para saber quando as linhas acabaram, usamos um CONTINUE HANDLER FOR NOT FOUND — que, seguindo a regra de posição, deve vir logo após as variáveis/locais de cursor e antes de qualquer comando executável. 

DELIMITER //

CREATE PROCEDURE AtualizarStatusPedidos()
BEGIN
    -- 1. Variáveis locais
    DECLARE v_id INT;
    DECLARE v_total DECIMAL(10,2);
    DECLARE fim_cursor BOOLEAN DEFAULT FALSE;

    -- 2. Cursor: percorre os pedidos pendentes
    DECLARE cur_pedidos CURSOR FOR
        SELECT id, valor_total FROM pedidos WHERE status = 'PENDENTE';

    -- 3. Handler: define a flag quando não houver mais linhas
    DECLARE CONTINUE HANDLER FOR NOT FOUND SET fim_cursor = TRUE;

    OPEN cur_pedidos;

    leitura: LOOP
        FETCH cur_pedidos INTO v_id, v_total;

        IF fim_cursor THEN
            LEAVE leitura;
        END IF;

        -- Marca como PAGO se o valor atender à regra de negócio
        IF v_total >= 1000.00 THEN
            UPDATE pedidos SET status = 'PAGO' WHERE id = v_id;
        END IF;
    END LOOP leitura;

    CLOSE cur_pedidos;
END //

DELIMITER ;

CALL AtualizarStatusPedidos();

Cursores: dica importante

Observe a ordem das declarações: variáveis → cursor → HANDLER. O NOT FOUND (código 02000) é fundamental: sem ele o loop em FETCH não saberia quando parar e entraria em erro ao tentar ler após a última linha. 

DELIMITER //

CREATE PROCEDURE ExemploBloco(IN p_valor INT)
BEGIN
    DECLARE v_dobro INT;

    SET v_dobro = p_valor * 2;

    IF v_dobro > 100 THEN
        SELECT 'Valor alto' AS resultado;
    ELSE
        SELECT 'Valor baixo' AS resultado;
    END IF;
END //

DELIMITER ;

CALL ExemploBloco(60);

3. Stored Procedures

Uma Stored Procedure é um objeto que agrupa comandos SQL em uma unidade lógica no servidor, sendo invocada pelo seu nome. Ela encapsula regras de negócio, melhora a segurança (concedendo apenas EXECUTE) e reduz o tráfego de rede.

3.1 Parâmetros IN, OUT e INOUT

Parâmetro Direção Uso
IN Entrada Valor enviado da aplicação para a procedure (padrão).
OUT Saída A procedure preenche o valor, lido pela aplicação após a execução.
INOUT Entrada e saída Entra com um valor, pode ser modificado e retorna o novo valor. 
DELIMITER //

CREATE PROCEDURE AplicarDesconto(INOUT valor DECIMAL(10,2), IN percentual DECIMAL(5,2))
BEGIN
    SET valor = valor - (valor * percentual / 100);
END //

DELIMITER ;

SET @preco = 1000.00;
CALL AplicarDesconto(@preco, 10);
SELECT @preco; -- 900.00

4. Stored Functions

Diferente da procedure, a Function sempre retorna um valor e pode ser usada dentro de expressões SQL. Enquanto a procedure é chamada com CALL, a função é chamada dentro de um SELECT ou em cláusulas como WHERE. 

DELIMITER //

CREATE FUNCTION CalcularImposto(valor DECIMAL(10,2)) RETURNS DECIMAL(10,2)
BEGIN
    RETURN valor * 0.20; -- 20% de imposto
END //

DELIMITER ;

SELECT CalcularImposto(1000.00) AS imposto; -- 200.00

5. Triggers (Gatilhos)

Um Trigger é um programa que é disparado automaticamente antes ou depois de um evento INSERT, UPDATE ou DELETE em uma tabela. Ele é usado para manter integridade, auditoria e regras de negócio que devem ser aplicadas "no banco".

  • BEFORE vs AFTER: BEFORE valida/ajusta dados antes da escrita; AFTER reage após a operação (ex.: auditoria).
  • NEW vs OLD: NEW referencia a nova linha (INSERT/UPDATE); OLD referencia a antiga (UPDATE/DELETE).
DELIMITER //

CREATE TRIGGER trg_audita_pedido
AFTER INSERT ON pedidos
FOR EACH ROW
BEGIN
    INSERT INTO auditoria (tabela, acao, id_registro, data)
    VALUES ('pedidos', 'INSERT', NEW.id, NOW());
END //

DELIMITER ;

Cuidado com triggers

Triggers podem causar cascatas de execução e dificultar a depuração. Use-os com moderação e sempre documente o comportamento. Encadeamentos excessivos podem degradar a performance de escrita.

6. Tratamento de Exceções

O tratamento de erros é essencial para a robustez das rotinas automatizadas. Três conceitos centrais:

  • Os três valores de erro: número do erro (ex.: 1062), mensagem descritiva e código SQLSTATE (padronizado ANSI/ODBC).
  • DECLARE ... HANDLER: captura condições dentro do stored program. CONTINUE segue o fluxo; EXIT encerra o bloco.
  • SIGNAL: lança erros customizados para validar regras de negócio que as constraints não alcançam.

6.1 A posição correta do DECLARE HANDLER

Não é possível colocar o DECLARE EXIT HANDLER em qualquer lugar do código. No MySQL, a declaração de manipuladores de erro (Handlers) segue regras bem estritas de posição dentro do bloco BEGIN ... END.

Regra de Posição Obrigatória

Dentro de um bloco BEGIN ... END, existe uma ordem exata para as declarações. O HANDLER deve obrigatoriamente ficar após as variáveis e após os cursores, mas antes de qualquer instrução SQL executável (START TRANSACTION, IF, SELECT, UPDATE, SET, etc.).

A ordem correta é:

  1. DECLARE de variáveis locais (DECLARE v_preco ...)
  2. DECLARE de condições (DECLARE condicao ...)
  3. DECLARE de cursores (DECLARE cursor ...)
  4. DECLARE HANDLER (tratamento de exceções)
  5. Comandos executáveis (START TRANSACTION, IF, INSERT, etc.)

Se você colocar o DECLARE EXIT HANDLER depois do START TRANSACTION ou de um SET, o MySQL retornará um erro de sintaxe na hora de compilar/criar a procedure.

Regra de Escopo (onde o Handler funciona)

O Handler protege apenas o bloco BEGIN ... END onde ele foi declarado e os blocos internos filhos.

  • Se você declarar o Handler no BEGIN principal da procedure, ele escutará e capturará erros de qualquer linha executada naquela procedure.
  • Se você declará-lo dentro de um bloco BEGIN ... END secundário (como dentro de um IF ou um LOOP), ele só protegerá os comandos que estiverem dentro daquele bloco específico.

DECLARE cursores\nDECLARE cursor..."] D --> E["4. DECLARE HANDLER\n(tratamento de exceções)"] E --> F["5. Comandos executáveis\nSTART TRANSACTION, IF, INSERT, UPDATE..."] F --> G([Fim do Bloco])

Exemplo corrigido com a ordem certa

Perceba que o DECLARE EXIT HANDLER fica no topo, logo abaixo das variáveis locais e antes do START TRANSACTION: 

DELIMITER //

CREATE PROCEDURE TransacaoSegura(IN id_cliente INT, IN valor DECIMAL(10,2))
BEGIN
    -- 1. Variáveis locais (sempre primeiro)
    DECLARE v_novo_saldo DECIMAL(10,2);

    -- 2. Handler de exceção (antes de qualquer comando executável)
    DECLARE EXIT HANDLER FOR SQLEXCEPTION
    BEGIN
        ROLLBACK;
        SIGNAL SQLSTATE '45000'
        SET MESSAGE_TEXT = 'Erro na transação — operações desfeitas';
    END;

    -- 3. Comandos executáveis (somente depois de TODAS as DECLAREs)
    SET v_novo_saldo = valor * 1.10;

    START TRANSACTION;
    UPDATE contas SET saldo = saldo + valor WHERE id_cliente = id_cliente;
    COMMIT;
END //

DELIMITER ;

Resumo prático

Para a sua Stored Procedure funcionar perfeitamente, o HANDLER precisa ficar no topo, logo abaixo da criação das variáveis DECLARE v_..., e antes de dar o START TRANSACTION.

7. Mapeamento ORM

O Mapeamento Objeto-Relacional (ORM) resolve a incompatibilidade de impedância semântica entre o paradigma de objetos da aplicação e o paradigma relacional do banco. Ele permite persistir objetos sem escrever SQL manualmente.

  • Entidades: classes que representam tabelas do banco.
  • Mapeamento de relacionamentos: one-to-one, one-to-many e many-to-many.
  • Persistência declarativa: o ORM gera o SQL automaticamente a partir do modelo de objetos.
  • Benefícios: produtividade e portabilidade; desafios: perda de controle sobre o SQL gerado e risco de consultas ineficientes (N+1).

ORM não substitui o SQL

Saber escrever SQL e conhecer Stored Procedures continua sendo essencial. O ORM encapsula, mas quem entende o banco consegue otimizar consultas e aproveitar recursos como procedures, funções e triggers.

Conceito Papel Comando/Exemplo

Dicas & Lembretes

  • Transação + Handler: procedures que manipulam várias tabelas devem usar transação combinada com EXIT HANDLER e ROLLBACK.
  • Posição do HANDLER: o DECLARE HANDLER deve ficar após as variáveis/cursores e antes de qualquer comando executável (inclusive o START TRANSACTION); caso contrário, ocorre erro de sintaxe.
  • Escopo do Handler: ele protege apenas o bloco BEGIN...END onde foi declarado e os blocos filhos.
  • Delimiter esquecido: no MySQL, os stored programs requerem DELIMITER // antes da criação.
  • Cursor: use o ciclo OPEN → FETCH (em LOOP) → CLOSE para processar linhas uma a uma, sempre com um CONTINUE HANDLER FOR NOT FOUND para encerrar o loop corretamente.
  • Procedure vs Function: precisa usar o retorno em um SELECT? Use Function; caso contrário, use Procedure.
  • Trigger com cautela: evite encadeamentos profundos; documente cada gatilho criado.
  • SQLSTATE: baseie o tratamento de erros no SQLSTATE, pois é mais estável entre SGBDs.
  • ORM: entenda o SQL por trás das ferramentas para identificar consultas ineficientes.

Como aplicar na Prática

  • Passo 1: Revise o esquema e as consultas que compõem a base do projeto (joins, agregações, views).
  • Passo 2: Encapsule as regras de negócio em procedures e funções, garantindo atomicidade com transações.
  • Passo 3: Adicione triggers para auditoria e integridade automática, com tratamento de exceções robusto.
  • Passo 4: Quando uma regra exigir processamento linha a linha (ex.: importar/atualizar registros em lote), implemente uma procedure com cursor + CONTINUE HANDLER FOR NOT FOUND.
  • Passo 5: Integre o modelo com a aplicação via ORM, validando o SQL gerado e a performance.
  • Passo 6: Teste todos os cenários (sucesso, falha, concorrência) antes da entrega do projeto integrador.
