Enunciado

A Livraria Horizonte, cliente da sua equipe, está redesenhando sua plataforma de e-commerce. O monolito relacional atual enfrenta três problemas conhecidos: lentidão no catálogo (milhões de livros com atributos variáveis por editora), excesso de consultas ao banco para validar sessão de usuário e relatório de recomendação que trava ao atravessar a rede social de usuários.

Sua tarefa é aplicar Persistência Poliglota: modelar cada tipo de dado no motor mais adequado e justificar tecnicamente cada decisão. Não basta dizer “MongoDB é melhor para catálogo” — é preciso explicar qual padrão de acesso motivou a escolha e qual garantia de consistência foi aceita.

Requisitos funcionais

  1. Catálogo com atributos variáveis: isbn, título, preço, editora e atributos específicos por categoria (livro físico tem num_paginas e isbn_13; e-book tem formato e tamanho_mb).
  2. Pedidos com transação financeira: múltiplos itens, pagamento, frete e baixa de estoque atômicos.
  3. Sessão de usuário e carrinho com expiração automática.
  4. “Livros recomendados para você” calculado a partir do histórico de leituras e compras.
  5. Rede social: usuários que seguem outros usuários e livros.

Ambiente sugerido

  • PostgreSQL 12+ (ou MySQL 8) para o bloco transacional.
  • MongoDB 6+ ou docker run mongo:7.
  • Redis 7+ para chave-valor.
  • Neo4j Community para grafos.

Não é obrigatório instalar os quatro motores: você pode entregar o projeto como DDL, comandos e consultas, justificando cada escolha. Mas executar ao menos o MongoDB e o Redis deixa a atividade muito mais concreta.

Orientações Finais

  • Justificativa vale mais que entrega: cada escolha de motor deve ter uma frase explicando por que o padrão de acesso daquele dado favorece aquela família. “É mais rápido” não é justificativa.
  • Consistência é uma escolha, não um bônus: toda vez que aceitar consistência eventual, registre onde está a janela de convergência e o que o usuário vê dentro dela.
  • Poliglota tem custo: cada motor adicional significa nova expertise, novo backup e novo plano de recuperação. Se o ganho de escala não for mensurável, um único banco relacional bem indexado é a melhor arquitetura.
  • Nem tudo é NoSQL: transação financeira com baixa de estoque é relacional, sempre.
