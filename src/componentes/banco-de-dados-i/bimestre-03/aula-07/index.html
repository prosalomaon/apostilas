Teoria & Conceitos

1. O Limite da FNBC

Até a Forma Normal de Boyce-Codd (FNBC), todas as regras de normalização baseavam-se em Dependências Funcionais (DFs), onde um atributo determina de forma única o valor de outro. No entanto, existem cenários onde uma tabela está na FNBC, mas ainda sofre de redundâncias graves e anomalias de atualização.

Esses problemas ocorrem quando tentamos representar dois ou mais fatos multivalorados independentes em uma única tabela. Para resolver essa falha de projeto, recorremos às formas normais superiores: a 4FN e a 5FN.

2. Dependências Multivaloradas (MVD)

Uma Dependência Multivalorada (MVD), representada por A →→ B, ocorre quando um atributo de chave A determina um conjunto de valores para o atributo B, mas esse conjunto é completamente independente de outros atributos presentes na tabela.

Uma MVD é não-trivial quando a tabela contém pelo menos três atributos (A, B e C) e os valores de B associados a um valor de A dependem apenas de A, sendo totalemente independentes dos valores de C.

3. Quarta Forma Normal (4FN)

Uma tabela está na Quarta Forma Normal (4FN) se, e somente se:

  • Estiver na 3FN (e, idealmente, na FNBC).
  • Para cada dependência multivalorada não-trivial A →→ B, o determinante A for uma superchave da tabela.

Em termos práticos: Uma tabela na 3FN também estará na 4FN se ela não contiver mais do que um fato multivalorado sobre o objeto descrito.

4. Estudo de Caso: O Caso do Fornecedor (COMPRA)

Considere uma tabela utilizada para registrar as compras de uma empresa: 

COMPRA(CodFornecedor, CodProduto, CodComprador)

Regras de Negócio

  • Um fornecedor fornece múltiplos produtos.
  • Um fornecedor atende a múltiplos compradores.
  • Os produtos fornecidos não têm relação com os compradores que negociam com ele.

Chave Primária

A chave é composta por todos os campos: {CodFornecedor, CodProduto, CodComprador} (uma tabela "all-key").

O Problema de Redundância

Se o Fornecedor 101 vende o Produto BA3 e atende aos Compradores 01 e 25, somos obrigados a registrar:

CodFornecedor CodProduto CodComprador
101 BA3 01
101 BA3 25

Se o Fornecedor 101 passar a vender também o Produto X9, teremos que inserir duas novas linhas (uma para cada comprador), mesmo que o comprador nada tenha a ver com a variedade de produtos. Se esquecermos de inserir uma combinação, criaremos uma inconsistência.

Decomposição para a 4FN

Para eliminar a MVD, isolamos os dois fatos multivalorados independentes em tabelas binárias distintas: 

FORNECEDOR_PRODUTO(CodFornecedor, CodProduto)
    PK: {CodFornecedor, CodProduto}

FORNECEDOR_COMPRADOR(CodFornecedor, CodComprador)
    PK: {CodFornecedor, CodComprador}

5. Quinta Forma Normal (5FN)

A 5FN, também conhecida como Projection-Join Normal Form (PJ/NF), é considerada o "estágio final" da normalização lógica por meio de projeções. Ela lida com casos em que um relacionamento múltiplo (geralmente ternário ou de grau maior) pode ser decomposto em relacionamentos binários menores sem perda de informação.

Uma tabela R satisfaz uma Dependência de Junção (JD) se o seu conteúdo puder ser perfeitamente reconstruído através do JOIN de suas projeções.

Definição Formal da 5FN

Uma tabela R está na 5FN se, e somente se, todas as dependências de junção (JDs) não-triviais que nela se mantêm forem implicadas pelas superchaves da tabela.

Regra de Ouro Prática

Se uma tabela estiver na FNBC/3FN e não possuir chaves compostas (todas as suas chaves candidatas são formadas por uma única coluna), ela está automaticamente na 5FN. Não é preciso se preocupar com JDs nesse cenário.

6. Estudo de Caso: A Relação de Produção (FAZ)

Considere uma indústria que projeta equipamentos. A tabela registra quais Materiais são necessários para cada Pedido de Compra que atende a uma Requisição específica: 

FAZ(Material, Pedido, Requisicao)
Material Pedido Requisição
ROTOR 1B WPC 0792 R1292
ROTOR 1B WPC 0992 R3192
CI 102 PC 0792 R3192
ROTOR 1B WPC 0792 R3192

Decomposição em Três Projeções Binárias

Pede(Material, Pedido)
Tem(Pedido, Requisicao)
Faz_Binario(Material, Requisicao)

O Teste de Junção

Se fizermos o JOIN apenas entre Pede e Tem com base no Pedido, o resultado gerará uma linha espúria: 

CI 102 | PC 0792 | R1292  ← Dado incorreto!
(O circuito integrado CI 102 nunca foi requisitado na R1292)

No entanto, ao juntar com a terceira tabela (Faz_Binario), a linha espúria é automaticamente eliminada, restando exatamente o conteúdo da tabela original.

Como a tabela original pôde ser decomposta em três tabelas menores e reconstruída perfeitamente (decomposição sem perdas), a estrutura original não estava na 5FN. Para atingi-la, devemos dividi-la nas três tabelas binárias resultantes.

Exemplo de Código

1. Implementação da 4FN (Caso do Fornecedor)

-- Tabela de Produtos (Entidade Forte)
CREATE TABLE produto (
    cod_produto VARCHAR(10) PRIMARY KEY,
    desc_produto VARCHAR(100) NOT NULL
);

-- Tabela de Compradores (Entidade Forte)
CREATE TABLE comprador (
    cod_comprador VARCHAR(10) PRIMARY KEY,
    nome_comprador VARCHAR(100) NOT NULL
);

-- Decomposição 4FN: Fornecedor x Produto
CREATE TABLE fornecedor_produto (
    cod_fornecedor INT NOT NULL,
    cod_produto VARCHAR(10) NOT NULL,
    PRIMARY KEY (cod_fornecedor, cod_produto),
    FOREIGN KEY (cod_produto) REFERENCES produto(cod_produto)
);

-- Decomposição 4FN: Fornecedor x Comprador
CREATE TABLE fornecedor_comprador (
    cod_fornecedor INT NOT NULL,
    cod_comprador VARCHAR(10) NOT NULL,
    PRIMARY KEY (cod_fornecedor, cod_comprador),
    FOREIGN KEY (cod_comprador) REFERENCES comprador(cod_comprador)
);

2. Implementação da 5FN (Caso da Produção)

-- Decomposição 5FN: três tabelas binárias
CREATE TABLE material_pedido (
    material VARCHAR(50) NOT NULL,
    pedido_compra VARCHAR(20) NOT NULL,
    PRIMARY KEY (material, pedido_compra)
);

CREATE TABLE pedido_requisicao (
    pedido_compra VARCHAR(20) NOT NULL,
    requisicao VARCHAR(20) NOT NULL,
    PRIMARY KEY (pedido_compra, requisicao)
);

CREATE TABLE material_requisicao (
    material VARCHAR(50) NOT NULL,
    requisicao VARCHAR(20) NOT NULL,
    PRIMARY KEY (material, requisicao)
);

Dicas & Lembretes

  • 4FN: Se uma tabela tem dois ou mais conjuntos de valores independentes sobre a mesma chave, cada conjunto deve ficar em uma tabela separada.
  • 5FN: Só se aplica a tabelas com chaves compostas. Se a chave é simples (uma coluna), a tabela já está em 5FN automaticamente.
  • Sequência lógica: 1FN → 2FN → 3FN → FNBC → 4FN → 5FN. Cada Forma Normal é mais rigorosa que a anterior.
  • Na prática: A maioria dos sistemas comerciais trabalha com normalização até 3FN. A 4FN e 5FN são mais relevantes em bancos de dados acadêmicos e sistemas de_planejamento de recursos (ERP).
  • MVD vs DF: Uma dependência funcional A → B é um caso especial de MVD. Toda DF é uma MVD, mas nem toda MVD é uma DF.

Como aplicar na Prática

  • Sistemas de catálogo: Quando um fornecedor tem múltiplos produtos E múltiplos clientes independentes, aplique a 4FN para evitar a explosão combinatória de linhas.
  • Gestão de projetos: Em tabelas que relacionam Materiais, Pedidos e Requisições, verifique se a decomposição binária preserva a informação (teste de junção).
  • Bancos de dados acadêmicos: Professores com múltiplas disciplinas E múltiplos alunos independentes são um caso clássico de MVD.
  • Auditoria: Antes de criar uma tabela com três ou mais chaves compostas, questione se todos os fatos são realmente dependentes entre si.
