Teoria & Conceitos

1. Definição de 1FN

Uma tabela é considerada em Primeira Forma Normal se, e somente se, todas as suas colunas possuem valores atômicos (únicos e indivisíveis) e não existem grupos repetitivos (múltiplas ocorrências de um dado em uma mesma linha) ou atributos compostos.

Na prática, estar na 1FN significa que a tabela possui uma estrutura "plana", sem colunas que funcionem como vetores ou listas internas.

2. O Conceito de Atomicidade

Todos os atributos de uma relação devem ser atômicos, ou seja, indivisíveis em termos de componentes.

  • Atributos Compostos: São aqueles que podem ser divididos em subpartes com significados independentes (ex: um campo "Endereço" que contém rua, cidade e CEP). Na 1FN, esses atributos devem ser decompostos em colunas elementares para facilitar buscas e filtros específicos.
  • Atributos Multivalorados: Ocorrem quando um único campo armazena vários valores do mesmo tipo (ex: uma coluna "Telefones" guardando três números diferentes separados por vírgula). Isso é estritamente proibido na 1FN.

3. Eliminação de Grupos Repetitivos

Grupos repetitivos são conjuntos de atributos que se repetem indefinidas vezes para uma mesma entidade. Como resolver? A aplicação da 1FN consiste em retirar os elementos repetitivos da estrutura original e criar uma nova entidade (tabela):

  1. Identifica-se o conjunto de dados que se repete.
  2. Cria-se uma segunda tabela para esses dados.
  3. A nova tabela herda a Chave Primária da tabela original (que passa a ser parte de sua chave e uma Chave Estrangeira) para manter o vínculo lógico.

4. Por que aplicar a 1FN?

  • Facilidade de Consulta: Permite usar comandos SQL simples para contar itens ou filtrar produtos, o que seria impossível se os dados estivessem "escondidos" dentro de uma lista em uma única célula.
  • Integridade: Garante que cada registro seja distinguível e que não haja perda de informação ao manipular os dados.
  • Padronização: Atende aos preceitos da Teoria Relacional de que uma tabela é um conjunto de tuplas com valores de domínios atômicos.

Exemplo de Código

1. Estrutura Não Normalizada (0FN)

Nesta fase, os itens da nota são vistos como um subgrupo repetitivo dentro da mesma linha. Note a coluna itens, que viola a atomicidade ao armazenar uma lista com vários produtos: 

-- ATENÇÃO: estrutura NÃO normalizada (0FN)
CREATE TABLE nota_fiscal_0fn (
    num_nf      INT PRIMARY KEY,
    data        DATE NOT NULL,
    cliente     VARCHAR(100) NOT NULL,
    itens       VARCHAR(255) NOT NULL -- lista com Código, Descrição e Qtd
);

INSERT INTO nota_fiscal_0fn VALUES
(456123, '2026-05-05', 'Davi B.', '{45, Limpadora, 1}, {25, Computador, 1}');

Problemas: para contar quantos produtos foram vendidos ou filtrar por um produto específico, seria necessário "quebrar" manualmente a string itens — uma operação frágil e lenta.

2. Estrutura na Primeira Forma Normal (1FN)

Os dados são desdobrados em duas tabelas distintas: o cabeçalho da nota e uma tabela de itens, cuja chave é a combinação do Num_NF (herdado) com o Cod_Produto: 

-- Tabela de Notas Fiscais: contém os dados do cabeçalho
CREATE TABLE nota_fiscal (
    num_nf  INT PRIMARY KEY,
    data    DATE NOT NULL,
    cliente VARCHAR(100) NOT NULL
);

-- Tabela de Itens de Nota: um produto por linha (chave composta)
CREATE TABLE item_nota (
    num_nf      INT NOT NULL,
    cod_produto INT NOT NULL,
    quantidade  INT NOT NULL,
    PRIMARY KEY (num_nf, cod_produto),
    FOREIGN KEY (num_nf) REFERENCES nota_fiscal(num_nf)
);

INSERT INTO nota_fiscal VALUES
(456123, '2026-05-05', 'Davi B.');

INSERT INTO item_nota VALUES
(456123, 45, 1),
(456123, 25, 1);

Agora é possível responder às consultas com SQL simples, por exemplo contando os produtos de uma nota ou filtrando pela quantidade vendida: 

-- Quantos produtos a nota 456123 possui?
SELECT COUNT(*) AS total_itens
FROM item_nota
WHERE num_nf = 456123;

-- Visão completa: cabeçalho + itens
SELECT nf.num_nf, nf.data, nf.cliente, it.cod_produto, it.quantidade
FROM nota_fiscal nf
JOIN item_nota it ON it.num_nf = nf.num_nf;

Dicas & Lembretes

  • Nulos: A 1FN ajuda a reduzir o uso excessivo de valores nulos, pois dados opcionais ou repetitivos são movidos para tabelas específicas.
  • Chave Primária: É primordial definir a Chave Primária antes de iniciar a normalização, pois ela é a âncora para todos os relacionamentos que surgirão.
  • Spartan Simplicity: Lembre-se que o modelo relacional preza pela simplicidade: sem ordem de tuplas, sem ponteiros físicos e sem duplicatas.

Exercício de Reflexão

Ao modelar uma "Ficha de Empréstimo de Livros", se um livro possui vários autores, onde essa informação deve ficar para respeitar a 1FN?

Resposta: Deve ser criada uma tabela separada para autores, vinculando-os ao ISBN do livro, eliminando a multivaloração na tabela principal de livros.

Em outras palavras: um atributo multivalorado (vários autores em uma única célula) viola a atomicidade e precisa ser desdobrado em uma nova entidade — exatamente o mesmo princípio aplicado aos itens da Nota Fiscal.

Como aplicar na Prática

  • Desconfie de listas em uma única coluna: Textos com vírgulas, ponto-e-vírgulas ou delimitadores separando "vários valores" são o sintoma clássico de multivaloração. Quebre-os em linhas de uma tabela filha.
  • Decomponha atributos compostos: Um único campo "Endereço" deve virar Rua, Número, Cidade e CEP sempre que cada parte for usada em buscas ou filtros específicos.
  • Defina a PK antes de normalizar: A Chave Primária é a âncora dos relacionamentos; sem ela, não é possível herdar a referência para a nova tabela criada na eliminação de grupos repetitivos.
  • Valide o resultado: Depois da decomposição, confira se é possível reconstruir a visão original com um JOIN entre as tabelas — se sim, nenhuma informação foi perdida.
