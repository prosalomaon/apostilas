Teoria & Conceitos

1. O que é uma Dependência Funcional (DF)?

A Dependência Funcional é uma restrição que descreve a relação entre os atributos de uma tabela. Dizemos que um conjunto de atributos B é funcionalmente dependente de um conjunto A (denotado por A→B) se, em todas as situações possíveis, o valor de A determinar de forma única o valor de B.

  • Determinante: É o lado esquerdo da seta (A); o atributo que define o outro.
  • Dependente: É o lado direito da seta (B); o atributo que é definido.

2. Exemplo Prático de Identificação

Considere uma tabela de Funcionários:

Matrícula (PK) Nome Departamento
1021 João Barros 900
1145 Pedro Silva 700
1689 Antonio Jardim 900
  • Matrícula → Nome: Se conheço a matrícula, sei exatamente quem é o funcionário.
  • Departamento ¬→ Matrícula: O departamento não determina a matrícula, pois o departamento 900 possui dois funcionários diferentes (João e Antonio).

Outro Exemplo (ISBN): Na ficha de um livro, o ISBN determina o Título. Se mudarmos o valor do ISBN, o título obrigatoriamente mudará, caracterizando a dependência funcional.

3. Tipos de Dependências Funcionais

Para aplicar as Formas Normais (2FN e 3FN), é preciso distinguir três tipos de dependências:

A. Dependência Funcional Total (Plena)

Ocorre quando um atributo depende de uma chave primária composta inteira, e não apenas de uma parte dela.

  • Exemplo: Na tabela ITEM_PEDIDO(NumPedido, CodProduto, Quantidade), a Quantidade possui dependência total da chave composta {NumPedido, CodProduto}.

B. Dependência Funcional Parcial

Ocorre quando um atributo depende de apenas uma parte de uma chave primária composta.

  • Exemplo: Se na tabela acima tivéssemos DescricaoProduto, ela dependeria apenas de CodProduto, e não do NumPedido. Isso viola a 2ª Forma Normal.

C. Dependência Funcional Transitiva

Ocorre quando um atributo depende de outro atributo que não é chave.

  • Exemplo: Na tabela NOTAS_FISCAIS(NumNF, CodCliente, NomeCliente), o NomeCliente depende do CodCliente, que por sua vez depende do NumNF. Logo, o nome tem dependência transitiva da chave via CodCliente.

Exemplo de Código

1. A tabela Funcionários e suas DFs

A estrutura DDL abaixo materializa o exemplo da tabela de Funcionários. Observe que a chave primária (matricula) determina todos os demais atributos: 

CREATE TABLE funcionarios (
    matricula    INT PRIMARY KEY,
    nome         VARCHAR(100) NOT NULL,
    departamento INT NOT NULL
);

INSERT INTO funcionarios VALUES
(1021, 'João Barros',    900),
(1145, 'Pedro Silva',    700),
(1689, 'Antonio Jardim', 900);

-- DF válida: matricula -> nome, departamento
-- DF inválida: departamento -> matricula (900 tem dois funcionários)

2. Violação de dependência parcial (contra a 2FN)

Abaixo, a tabela ITEM_PEDIDO com a chave composta {NumPedido, CodProduto}. O atributo DescricaoProduto depende apenas de CodProduto — uma dependência parcial, que precisa ser eliminada na 2ª Forma Normal: 

-- ATENÇÃO: estrutura NÃO normalizada (apenas para estudo das DFs)
CREATE TABLE item_pedido (
    num_pedido        INT NOT NULL,
    cod_produto       INT NOT NULL,
    quantidade        INT NOT NULL,        -- depende da chave TOTAL (NumPedido, CodProduto)
    descricao_produto VARCHAR(100) NOT NULL, -- depende APENAS de CodProduto (PARCIAL)
    PRIMARY KEY (num_pedido, cod_produto)
);

-- DF total:   {num_pedido, cod_produto} -> quantidade
-- DF parcial: cod_produto -> descricao_produto  (viola a 2FN)

3. Violação de dependência transitiva (contra a 3FN)

Na tabela NOTAS_FISCAIS, o NomeCliente depende da chave NumNF por intermédio do CodCliente — uma dependência transitiva, que a 3ª Forma Normal exige decompor: 

-- ATENÇÃO: estrutura NÃO normalizada (apenas para estudo das DFs)
CREATE TABLE notas_fiscais (
    num_nf       INT PRIMARY KEY,
    data_emissao DATE NOT NULL,
    cod_cliente  INT NOT NULL,
    nome_cliente VARCHAR(100) NOT NULL, -- depende de CodCliente (transitivo)
    valor_total  DECIMAL(10,2) NOT NULL
);

-- DF direta:  num_nf -> cod_cliente
-- DF direta:  cod_cliente -> nome_cliente
-- DF transitiva: num_nf -> nome_cliente  (via cod_cliente, viola a 3FN)

As Formas Normais e a Dependência Funcional

A normalização é descrita como o "senso comum formalizado". O analista utiliza as dependências funcionais para decompor tabelas "inchadas" em estruturas menores e estáveis.

Forma Normal Regra Baseada em Dependência
2FN Exige que não existam Dependências Parciais; todo atributo deve depender da chave total.
3FN Exige que não existam Dependências Transitivas; atributos só devem depender da chave primária.
FNBC Exige que todo determinante seja uma Chave Candidata.

Dicas & Lembretes

  • Chave Primária e DF: Por definição, a chave primária de uma tabela deve determinar funcionalmente todos os outros atributos dessa tabela.
  • Fatos e Tuplas: Cada linha de uma tabela representa um fato; se a dependência funcional estiver errada, o banco de dados registrará fatos contraditórios (inconsistência).
  • Superchaves: Uma superchave é qualquer conjunto de atributos que contém uma chave candidata e, por consequência, determina todos os atributos da relação.

Como aplicar na Prática

  • Antes de normalizar, liste as DFs: Ao revisar um modelo lógico, escreva explicitamente todas as dependências funcionais do tipo X → Y identificadas nos dados. Essa lista é o "mapa" que guia todas as decomposições.
  • Chaves compostas → verifique a 2FN: Quando uma tabela possui chave primária composta, confira se todo atributo não chave depende da chave inteira. Se algum depender só de uma parte, há uma dependência parcial a corrigir.
  • Atributos "de outra entidade" → verifique a 3FN: Nome de cliente dentro de uma tabela de notas fiscais é um sinal clássico de dependência transitiva. Pergunte-se: "esse atributo depende da chave ou de outro atributo não chave?"
  • Audite determinantes: Na FNBC, verifique se todos os determinantes encontrados são chaves candidatas. Um determinante que não é chave indica que a relação ainda precisa ser decomposta.
