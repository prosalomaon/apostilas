Teoria & Conceitos

1. O que é a Segunda Forma Normal (2FN)?

Uma tabela/relação está na Segunda Forma Normal (2FN) quando atende a duas condições fundamentais:

  • Estar na Primeira Forma Normal (1FN) (não conter atributos multivalorados, compostos ou repetitivos).
  • Todos os atributos não-chave dependerem TOTALMENTE de toda a Chave Primária (PK), e não apenas de parte dela.

Atenção

  • A 2FN aplica-se essencialmente a tabelas que possuem Chave Primária Composta (formada por duas ou mais colunas).
  • Se a Chave Primária de uma tabela for simples (apenas uma coluna), e a tabela já estiver na 1FN, ela estará automaticamente na 2FN.

2. Dependência Funcional Total vs. Dependência Funcional Parcial

Dependência Funcional Total

Ocorre quando um atributo não-chave depende de todos os componentes de uma chave primária composta para ter um sentido completo e único. 

(Chave_A, Chave_B) → Atributo_X

Dependência Funcional Parcial

Ocorre quando um atributo não-chave depende de apenas uma parte da chave primária composta. 

Chave_A → Atributo_Y
Chave_B → Atributo_Z

A presença de dependências parciais gera anomalias de inserção, alteração e exclusão.

3. Resolução e o Conceito de Tabelas Associativas

Quando identificamos atributos com dependência parcial em uma chave composta:

  1. Removemos esses atributos com dependência parcial da tabela original.
  2. Criamos novas tabelas para armazenar esses atributos juntamente com o pedaço da chave do qual eles dependem funcionalmente.
  3. A tabela resultante do relacionamento original passa a atuar como uma Tabela Associativa (ou tabela de junção/pivô), mantendo a chave composta e os atributos que possuem Dependência Funcional Total dessa chave.

Exemplo de Código

1. Tabela Original (na 1FN) — versão NÃO normalizada

Considere a seguinte estrutura de dados onde um mesmo pedido pode conter vários produtos. A tabela possui chave primária composta (ID_Pedido, ID_Produto): 

CREATE TABLE ITEM_PEDIDO(
    ID_Pedido      INT,
    ID_Produto     INT,
    Nome_Produto   VARCHAR(100),
    Preco_Unitario DECIMAL(10,2),
    Quantidade     INT,
    Subtotal       DECIMAL(10,2),

    PRIMARY KEY (ID_Pedido, ID_Produto)
)

2. Versão NORMALIZADA — decomposta para a 2FN

Os atributos com dependência parcial (Nome_Produto e Preco_Unitario) são isolados em uma nova tabela PRODUTO. A tabela original torna-se a Tabela Associativa ITEM_PEDIDO: 

-- 1. Criação da tabela PRODUTO (Atributos com dependência parcial foram isolados aqui)
CREATE TABLE PRODUTO (
    ID_Produto INT PRIMARY KEY,
    Nome_Produto VARCHAR(100) NOT NULL,
    Preco_Unitario DECIMAL(10, 2) NOT NULL
);

-- 2. Criação da tabela PEDIDO (Entidade relacionada)
CREATE TABLE PEDIDO (
    ID_Pedido INT PRIMARY KEY,
    Data_Pedido DATE NOT NULL,
    ID_Cliente INT NOT NULL
);

-- 3. Criação da Tabela Associativa (Garante Dependência Funcional Total na 2FN)
CREATE TABLE ITEM_PEDIDO (
    ID_Pedido INT NOT NULL,
    ID_Produto INT NOT NULL,
    Quantidade INT NOT NULL,
    Subtotal DECIMAL(10, 2) NOT NULL,

    -- Definindo a Chave Primária Composta
    PRIMARY KEY (ID_Pedido, ID_Produto),

    -- Restrições de Chave Estrangeira (Integridade Referencial)
    FOREIGN KEY (ID_Pedido) REFERENCES PEDIDO(ID_Pedido),
    FOREIGN KEY (ID_Produto) REFERENCES PRODUTO(ID_Produto)
);

3. Inserção de Dados e Consulta com JOIN

INSERT INTO PRODUTO VALUES
(1, 'Limpadora',  600.00),
(2, 'Computador', 1800.00),
(3, 'Rádio',      150.00);

INSERT INTO PEDIDO VALUES
(1458, '2026-05-05', 1),
(2730, '2026-06-05', 2);

INSERT INTO ITEM_PEDIDO VALUES
(1458, 1, 2, 1200.00),
(2730, 2, 1, 1800.00),
(1458, 3, 1,  150.00);

-- Reconstrói a visão original a partir das tabelas normalizadas
SELECT I.ID_Pedido,
       P.Nome_Produto,
       P.Preco_Unitario,
       I.Quantidade,
       I.Subtotal
FROM ITEM_PEDIDO I
JOIN PRODUTO P ON P.ID_Produto = I.ID_Produto;

Análise das Dependências Funcionais

Dependência Tipo Explicação
(ID_Pedido, ID_Produto) → Quantidade TOTAL Para saber a quantidade vendida, precisamos saber qual é o pedido e qual é o produto.
(ID_Pedido, ID_Produto) → Subtotal TOTAL Depende de ambos.
ID_Produto → Nome_Produto PARCIAL O nome do produto depende apenas do ID_Produto, independentemente do pedido em que foi vendido.
ID_Produto → Preco_Unitario PARCIAL O preço base do produto depende apenas do ID_Produto.

Dicas & Lembretes

  • Regra prática: Se a tabela tem chave composta e algum atributo não-chave depende de apenas uma coluna da PK, ela não está na 2FN.
  • Dependência Parcial = problema: Gera redundância e anomalias, assim como na tabela não normalizada.
  • Tabela Associativa: É o resultado natural de um relacionamento M:N normalizado — mantém apenas os atributos que dependem de toda a chave composta.
  • Chave simples: Se a PK tem apenas uma coluna e a tabela está na 1FN, ela já está na 2FN automaticamente.
  • Próxima aula: Aula 25 — Terceira Forma Normal (3FN): dependências transitivas e eliminação de atributos não-chave dependentes de outros não-chave.

Como aplicar na Prática

  • E-commerce: Separe Produtos (nome, preço) da tabela de Itens do Pedido (quantidade, subtotal). Assim, um mesmo produto pode aparecer em vários pedidos sem duplicar nome e preço.
  • Universidade: Cadastre Disciplinas (nome, carga horária) e Professores separadamente da tabela de Alocação (semestre/ano). Evita repetir dados de disciplina a cada alocação.
  • Revisão de modelos legados: Use a normalização como checklist para auditar tabelas existentes — identifique chave composta e verifique se há atributos que dependem de apenas uma parte dela.
  • Data Warehouse: Ao construir cubos analíticos, avalie conscientemente a desnormalização (tabelas fato e dimensão) para priorizar a performance de leitura.
