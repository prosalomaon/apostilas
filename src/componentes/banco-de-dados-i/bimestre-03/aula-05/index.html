Teoria & Conceitos

1. O que é a Terceira Forma Normal (3FN)?

Uma tabela/relação está na Terceira Forma Normal (3FN) quando e somente quando, atende a duas condições fundamentais:

  • Estar na Segunda Forma Normal (2FN) (todos os atributos não-chave dependem totalmente de toda a chave primária).
  • Não possuir Dependências Transitivas: todos os atributos não-chave devem ser dependentes funcionalmente apenas da chave primária, e não de outros atributos que também não são chaves.

Atenção

  • O objetivo central da 3FN é evitar a "mistura de fatos" dentro de uma mesma tabela.
  • Cada informação deve ser armazenada em seu local lógico correto, sem redundância decorrente de dependências indiretas.

2. O Conceito de Dependência Transitiva

Dizemos que um atributo C possui uma dependência transitiva de uma chave A se ele depende de um atributo B, que por sua vez depende de A. 

A → B → C

Embora A determine C indiretamente, a relação direta é B → C. Na 3FN, o atributo C deve ser movido para uma estrutura onde B seja a chave primária.

3. Exemplo Prático: Tabela de Notas Fiscais

Considere a seguinte estrutura que já está na 2FN (não possui dependências parciais — a PK é simples): 

NOTA_FISCAL(
    NumNF          INT,
    Data_Emissao   DATE,
    Cod_Cliente    INT,
    Nome_Cliente   VARCHAR(100),
    Cidade_Cliente VARCHAR(50)
)

Análise das Dependências

Dependência Tipo Explicação
NumNF → Data_Emissao Direta da PK A data de emissão depende diretamente da nota fiscal.
NumNF → Cod_Cliente Direta da PK O cliente que fez a compra depende da nota fiscal.
Cod_Cliente → Nome_Cliente, Cidade_Cliente TRANSITIVA O nome e a cidade do cliente dependem de Cod_Cliente, que por sua vez depende de NumNF. Forma-se a cadeia: NumNF → Cod_Cliente → Nome_Cliente.

O Problema

Se o mesmo cliente fizer 50 compras, seu nome e cidade serão repetidos 50 vezes, gerando redundância e risco de inconsistência se ele mudar de cidade.

4. Resolução e Decomposição (3FN)

Para normalizar, removemos os atributos com dependência transitiva e criamos uma nova tabela:

Tabela Atributos PK FK
NOTA_FISCAL NumNF, Data_Emissao, Cod_Cliente NumNF Cod_Cliente → CLIENTE
CLIENTE Cod_Cliente, Nome_Cliente, Cidade_Cliente Cod_Cliente —

Agora, cada fato (o pedido e o cadastro do cliente) reside em sua própria tabela, eliminando a redundância de dados cadastrais no histórico de vendas.

Exemplo de Código

1. Criação das Tabelas Normalizadas (3FN)

A criação das tabelas normalizadas segue o padrão ANSI, sendo compatível com MySQL e PostgreSQL: 

-- 1. Criando a tabela de Clientes (PK necessária para referência)
CREATE TABLE cliente (
    cod_cliente INTEGER NOT NULL,
    nome_cliente VARCHAR(100) NOT NULL,
    cidade_cliente VARCHAR(50),
    PRIMARY KEY (cod_cliente)
);

-- 2. Criando a tabela de Notas Fiscais (Com FK para evitar dependência transitiva)
CREATE TABLE nota_fiscal (
    num_nf INTEGER NOT NULL,
    data_emissao DATE NOT NULL,
    cod_cliente INTEGER NOT NULL,
    PRIMARY KEY (num_nf),
    -- Restrição de Integridade Referencial
    FOREIGN KEY (cod_cliente) REFERENCES cliente(cod_cliente)
);

2. Inserção de Dados e Consulta com JOIN

INSERT INTO cliente VALUES
(55, 'João Silva',   'São Paulo'),
(12, 'Maria Souza',  'Jundiaí');

INSERT INTO nota_fiscal VALUES
(1001, '2026-08-18', 55),
(1002, '2026-08-19', 12);

-- Reconstrói a visão original a partir das tabelas normalizadas
SELECT N.num_nf,
       N.data_emissao,
       C.nome_cliente,
       C.cidade_cliente
FROM nota_fiscal N
JOIN cliente C ON C.cod_cliente = N.cod_cliente;

3. Decomposição de Tabela Existente (ALTER TABLE)

Caso precise adicionar a restrição de 3FN em uma tabela já existente que foi desmembrada: 

-- Remove-se a coluna redundante da tabela original após migrar os dados
ALTER TABLE nota_fiscal DROP COLUMN nome_cliente;
ALTER TABLE nota_fiscal DROP COLUMN cidade_cliente;

Dicas & Lembretes

  • Regra do "Determinante": Em uma tabela 3FN, cada coluna deve depender "da chave, de toda a chave, e de nada mais que a chave".
  • Performance vs. Integridade: A 3FN pode exigir mais JOINs em consultas, mas protege o banco de dados contra anomalias de atualização.
  • Data Warehouse: Em ambientes analíticos (OLAP), a 3FN é frequentemente revertida (desnormalização) para acelerar a leitura de grandes massas de dados.
  • Sequência lógica: 1FN (elimina multivalorados) → 2FN (elimina dependências parciais) → 3FN (elimina dependências transitivas).
  • Próxima aula: Aula 26 — Boyce-Codd Normal Form (BCNF): fortalecimento da 3FN para determinantes que são superchaves.

Como aplicar na Prática

  • E-commerce: Separe Cadastros de Clientes (nome, endereço, cidade) do histórico de Pedidos. Evite repetir dados cadastrais a cada nova compra.
  • Universidade: Cadastre Alunos (matrícula, nome, curso) separadamente da tabela de Matérias Cursei. O nome do aluno não deve aparecer em cada registro de nota.
  • Revisão de modelos legados: Ao auditir tabelas existentes, verifique se há colunas que dependem de outra coluna não-chave. Se sim, extraia-as para uma tabela de domínio.
  • Data Warehouse: Ao construir cubos analíticos, avalie conscientemente a desnormalização (tabelas fato e dimensão) para priorizar a performance de leitura.
