Teoria & Conceitos

Definir a estrutura de uma tabela é fácil. O que separa um banco de dados artesanal de um banco de dados bem projetado é a qualidade das decisões tomadas na definição dos tipos de dados. Um VARCHAR(255) usado para todo lugar parece inofensivo — até que o relatório de vendas de dezembro deixe de caber na memória do servidor.

Nesta aula, vamos fechar o ciclo entre o modelo lógico (onde a 3FN define atributos atômicos e bem relacionados) e o modelo físico (onde cada SGBD materializa esses atributos em tipos concretos com custo de armazenamento, velocidade e semântica próprios).

1. Domínios e Atomicidade

Na teoria relacional de Edgar F. Codd, uma relação é um conjunto de tuplas (linhas) onde cada atributo (coluna) representa um papel desempenhado por um domínio.

O domínio é o conjunto de todos os valores atômicos e admissíveis que uma determinada coluna pode conter. Por exemplo, o domínio da coluna idade_empregado pode ser restrito ao intervalo numérico de 16 a 70, enquanto o domínio de telefone pode ser um conjunto numérico com máscara de 10 dígitos.

O requisito de atomicidade (base da 1FN) exige que todos os valores inseridos em uma coluna sejam indivisíveis em termos de componentes. Não é admissível gravar (11) 98765-4321 em uma coluna de telefone se você pretende filtrar por DDD depois: o valor é uma estrutura disfarçada de átomo.

Comparação entre Domínios

Do ponto de vista conceitual, operações de comparação (WHERE coluna_A = coluna_B) ou junções entre tabelas só são semanticamente válidas se ambas as colunas pertencerem ao mesmo domínio de dados. Comparar um VARCHAR com um INT não é um erro de sintaxe — é um erro de modelo que o SGBD aceita silenciosamente.

Na prática, o domínio é especificado por meio de tipos primitivos (inteiros, ponto flutuante, caracteres, datas e horas), complementados por restrições de integridade, listas enumeradas ou regras de validação. É aqui que entra a decisão técnica: o tipo escolhido define o espaço ocupado em disco, o consumo de memória RAM para os índices e a precisão dos cálculos.

2. Tipos Numéricos: Inteiros, Decimais e Ponto Flutuante

2.1. Inteiros e Auto-incremento

Os tipos inteiros almacenam valores numéricos exatos, sem casas decimais:

Tipo SQL Espaço em Disco Faixa (com sinal) Faixa UNSIGNED
TINYINT 1 byte (8 bits) -128 a +127 0 a 255
SMALLINT 2 bytes (16 bits) -32.768 a +32.767 0 a 65.535
INT / INTEGER 4 bytes (32 bits) -2.147.483.648 a +2.147.483.647 0 a 4.294.967.295
BIGINT 8 bytes (64 bits) ± 9,22 × 10¹⁸ 0 a ≈ 1,84 × 10¹⁹

O MySQL suporta a especificação UNSIGNED, que descarta o bit reservado ao sinal e dobra a capacidade positiva do inteiro. O PostgreSQL não possui o modificador UNSIGNED nativo: a mesma faixa é obtida declarando o tipo NUMERIC(p, 0) CHECK (coluna >= 0).

Para chaves primárias numéricas sequenciais, o MySQL utiliza a propriedade AUTO_INCREMENT. O PostgreSQL oferece a pseudo-família SERIAL (SMALLSERIAL = 2 bytes, SERIAL = 4 bytes, BIGSERIAL = 8 bytes), que cria um objeto SEQUENCE independente no plano de fundo e atribui nextval() como valor padrão. Em versões modernas, o padrão ANSI GENERATED ALWAYS AS IDENTITY é o mais recomendado.

2.2. Numéricos Exatos (DECIMAL) vs. Aproximados (FLOAT)

Ao lidar com valores financeiros ou métricas de alta precisão, a escolha entre numéricos exatos e aproximados é crítica.

  • DECIMAL(p, s) / NUMERIC(p, s): permitem armazenar dados exatos, sem perdas causadas por arredondamento em base binária. Define-se a precisão (p) como o total de dígitos e a escala (s) como o número de dígitos à direita da vírgula. DECIMAL(9, 2) armazena até 7 dígitos inteiros e 2 decimais (máximo 9.999.999,99).
  • FLOAT / REAL / DOUBLE: armazenam dados com ponto flutuante em representação binária aproximada. Ocupam menos espaço (4 a 8 bytes), mas nem sempre mantêm a precisão exata para números de múltiplos dígitos, devendo ser evitados em cálculos financeiros. 
-- Literais exatos: o resultado é 0.3 (sem erro de arredondamento)
-- Vale nos dois SGBDs, pois 0.1 e 0.2 são interpretados como DECIMAL/NUMERIC
SELECT 0.1 + 0.2 AS resultado_exato;

-- Mesma soma forçada para ponto flutuante binário
-- PostgreSQL: retorna 0.30000000000000004
SELECT CAST(0.1 AS DOUBLE PRECISION) + CAST(0.2 AS DOUBLE PRECISION);

-- MySQL: o valor interno também é 0.30000000000000004,
-- mas a formatação padrão do MySQL o exibe como 0.3
SELECT CAST(0.1 AS DOUBLE) + CAST(0.2 AS DOUBLE);

O erro não é do SGBD, mas da representação: 0,1 não tem representação exata em base binária, assim como 1/3 não é finito em base 10. Como valores monetários exigem que a soma de dez notas de R$ 0,10 resulte exatamente em R$ 1,00, a representação binária é inaceitável.

3. Tipos de Caracteres e Texto

3.1. CHAR(n) vs. VARCHAR(n) vs. TEXT

O armazenamento de strings é dividido entre tamanho fixo e tamanho variável:

Tipo Comportamento de Armazenamento MySQL PostgreSQL
CHAR(n) Tamanho fixo. Preenche com espaços em branco à direita até completar n caracteres. Máximo de 255 caracteres. Os espaços de preenchimento são removidos na leitura. Máximo fixo. O preenchimento com espaços ocorre na gravação e na exibição, consumindo mais disco se subutilizado.
VARCHAR(n) Tamanho variável. Armazena apenas a quantidade real informada, mais os bytes de tamanho. Até 65.535 bytes por linha. Preserva espaços finais. Tamanho limite n. O desempenho do VARCHAR é idêntico ao do TEXT.
TEXT Tamanho variável para grandes blocos de texto. Divisões: TINYTEXT, TEXT (64 KB), MEDIUMTEXT (16 MB) e LONGTEXT (4 GB). Tipo TEXT ilimitado (até 1 GB por campo). Dados longos são movidos automaticamente para a estrutura TOAST, sem perda de desempenho.

CHAR é uma armadilha de custo constante

Como o CHAR(50) reserva 50 posições de caracteres independentemente do conteúdo, gravar 'A' em uma coluna desses consome o mesmo espaço que gravar 'ADMINISTRADOR'. Use-o apenas quando o comprimento for de fato invariável (CPF, código ISO, código de barras) e o argumento de alinhamento justificá-lo.

3.2. Strings Binárias e Codificação de Caracteres

  • Strings não-binárias (CHAR, VARCHAR, TEXT): associadas a um conjunto de caracteres (Character Set) e a uma ordenação (Collation). A collation define a sensibilidade a maiúsculas/minúsculas — no MySQL, os sufixos _ci (case-insensitive) e _cs (case-sensitive).
  • Strings binárias (BINARY, VARBINARY, BLOB / BYTEA): armazenam sequências de bytes brutos (imagens, arquivos compactados, dados criptografados) sem qualquer interpretação de conjunto de caracteres ou collation.

Essa distinção tem consequência prática de segurança: uma busca binária LIKE é sensível a case e ignora acentuação; uma busca não-binária sob a collation _ci pode considerar 'joao' e 'JOÃO' como o mesmo registro — o que afeta diretamente contagens e índices únicos.

4. Tipos Temporais: Datas, Horas e Fusos Horários

O manuseio de dados temporais é onde MySQL e PostgreSQL divergem de forma mais evidente.

Tipo Semântica Observações
DATE Apenas dia, mês e ano (YYYY-MM-DD). MySQL: intervalo de 1000-01-01 a 9999-12-31.
TIME Apenas hora (hh:mm:ss). MySQL: representa tempo decorrido, aceitando valores negativos e superiores a 24 horas (de -838:59:59 a 838:59:59).
DATETIME Data e hora combinadas, sem nenhuma conversão de fuso. MySQL: válido de 1000 a 9999, sem conversão automática.
TIMESTAMP Instante no tempo, normalizado. MySQL: convertido para UTC na gravação e reconvertido para o fuso da sessão na leitura. Limitado ao sistema Unix (1970 a 2038). Suporta DEFAULT CURRENT_TIMESTAMP e ON UPDATE CURRENT_TIMESTAMP.
TIMESTAMPTZ Instante com fuso, armazenado em UTC. PostgreSQL: converte o valor inserido para UTC e o armazena internamente em UTC; na consulta, exibe o valor ajustado ao fuso do servidor/sessão. É o tipo recomendado para aplicações globais.

O limite de 2038 no TIMESTAMP do MySQL

O TIMESTAMP do MySQL é limitado ao valor máximo Signed 32-bit (2038-01-19 03:14:07). Sistemas com previsão de eventos além dessa data (contratos de longo prazo, planos de assinatura vitalícios) devem usar DATETIME ou, no PostgreSQL, TIMESTAMPTZ, que não sofre dessa limitação.

5. Tipos Especiais e Customizados

5.1. Valores Booleanos

  • MySQL: não possui um tipo booleano nativo distinto. O comando BOOLEAN é um alias para TINYINT(1), onde 0 é falso e 1 (ou qualquer valor não-zero) é verdadeiro.
  • PostgreSQL: possui o tipo BOOLEAN nativo do padrão ANSI, aceitando 'true'/'false', 'yes'/'no', '1'/'0' ou TRUE/FALSE.

5.2. Coleções, JSON e Estruturas Complexas

  • MySQL: oferece os tipos enumerados ENUM e SET, além do suporte nativo a colunas JSON (a partir da versão 5.7).
  • PostgreSQL: oferece suporte avançado a Arrays (qualquer tipo pode ter uma dimensão de array, no formato tipo[]), documentos JSON / JSONB (JSON binário indexável via GIN / GiST), XML, chave-valor (hstore) e tipos compostos via CREATE TYPE.

6. Restrições de Domínio e Validação Física

As restrições de domínio garantem que apenas dados válidos, segundo as regras de negócio, entrem na tabela. Elas são a tradução física do domínio que estudamos na seção 1.

  • Nulo (NULL / NOT NULL): NOT NULL exige a presença obrigatória de valor. Chaves primárias são implicitamente NOT NULL nos dois SGBDs.
  • Restrição CHECK: adiciona uma expressão de validação diretamente sobre a coluna ou sobre a tabela inteira. 
-- Garantia de que o domínio da comissão seja apenas A, B ou C
CREATE TABLE vendedores_faixa (
    codigo_vendedor   SMALLINT      NOT NULL,
    nome_vendedor     VARCHAR(80),
    salario_fixo      DECIMAL(10,2),
    faixa_comissao    CHAR(1),
    data_admissao     DATE          NOT NULL,
    CONSTRAINT PK_vendedores PRIMARY KEY (codigo_vendedor),
    CONSTRAINT CH_faixa_comissao CHECK (faixa_comissao IN ('A', 'B', 'C')),
    CONSTRAINT CH_salario CHECK (salario_fixo >= 0)
);

Tabela de Domínio vs. Restrição CHECK

Cenário Abordagem indicada Justificativa
Lista estável e pequena (estados brasileiros, sexo biológico, tipo de pessoa) Restrição CHECK Não exige estrutura adicional; a regra é verificada no próprio motor.
Lista volátil ou extensa (cidades, categorias de produtos, cargos) Tabela de domínio separada + chave estrangeira Atualizar a lista não exige alterar o esquema DDL das tabelas consumidoras.

7. Matriz de Decisão Técnica

Requisito de Negócio MySQL PostgreSQL Justificativa
Identificador único (PK) INT UNSIGNED AUTO_INCREMENT INT GENERATED ALWAYS AS IDENTITY Sequências nativas e controle preciso de ciclo de vida
Texto de tamanho fixo CHAR(n) CHAR(n) Ideal para hashes, códigos ISO e máscaras fixas
Texto de tamanho variável VARCHAR(n) VARCHAR(n) ou TEXT No PostgreSQL o TEXT não tem penalidade de velocidade frente ao VARCHAR
Valores monetários DECIMAL(15,2) NUMERIC(15,2) ou MONEY Evita erros de arredondamento do ponto flutuante binário
Data e hora com fuso TIMESTAMP (ou DATETIME se não houver fuso) TIMESTAMPTZ Apenas TIMESTAMP/TIMESTAMPTZ gravam em UTC e reconvertem pela sessão; o DATETIME guarda o texto literal
Documentos dinâmicos JSON JSONB Permite indexação GIN para buscas dentro das chaves internas

Exemplo de Código

Vamos materializar as decisões de tipo em DDL equivalente nos dois SGBDs. Todos os blocos devem ser executados no ambiente da aula e comparados com information_schema.columns para inspecionar tamanho real e domínios declarados.

Exemplo 1: Chave Primária Auto-incrementável

-- ============ MySQL ============
CREATE TABLE categoria_mysql (
    id_categoria INT UNSIGNED AUTO_INCREMENT PRIMARY KEY,
    nome         VARCHAR(50) NOT NULL,
    CONSTRAINT UQ_categoria_nome UNIQUE (nome)
);

-- ============ PostgreSQL ============
CREATE TABLE categoria_postgres (
    id_categoria INT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    nome         VARCHAR(50) NOT NULL,
    CONSTRAINT UQ_categoria_nome UNIQUE (nome)
);

Diferença estrutural importante: no MySQL, AUTO_INCREMENT é um atributo da coluna e fica registrado em metadados internos da tabela. No PostgreSQL, tanto IDENTITY quanto SERIAL criam uma sequence que pode ser inspecionada em pg_sequences, mas a IDENTITY fica acoplada à coluna enquanto a SERIAL cria um objeto independente, ligado apenas por OWNED BY.

Exemplo 2: Valores Monetários e o Erro do Ponto Flutuante

-- ============ MySQL ============
CREATE TABLE precos_mysql (
    id_produto   INT UNSIGNED AUTO_INCREMENT PRIMARY KEY,
    valor_unitario DECIMAL(10,2) NOT NULL,
    taxa_percentual  FLOAT         NULL   -- Métrica aproximada: aceitável
);

-- ============ PostgreSQL ============
CREATE TABLE precos_postgres (
    id_produto     INT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    valor_unitario NUMERIC(10,2)  NOT NULL,
    taxa_percentual REAL          NULL   -- Equivalente ao FLOAT do MySQL
);

-- Demonstração do erro de arredondamento binário
-- PostgreSQL
SELECT CAST(0.1 AS DOUBLE PRECISION) + CAST(0.2 AS DOUBLE PRECISION) AS soma_aproximada; -- 0.30000000000000004
SELECT CAST(0.1 AS DECIMAL(4,2))    + CAST(0.2 AS DECIMAL(4,2))    AS soma_exata;      -- 0.30

-- MySQL
SELECT CAST(0.1 AS DOUBLE) + CAST(0.2 AS DOUBLE) AS soma_aproximada;  -- 0.30000000000000004
SELECT CAST(0.1 AS DECIMAL(4,2)) + CAST(0.2 AS DECIMAL(4,2)) AS soma_exata; -- 0.30

Exemplo 3: Texto Fixo, Variável e Longo

-- ============ MySQL ============
CREATE TABLE produto_mysql (
    codigo_barras CHAR(13)     NOT NULL,  -- Tamanho fixo exato (EAN-13)
    nome          VARCHAR(100) NOT NULL,  -- Tamanho variável
    descricao     TEXT         NULL       -- Até 64 KB
);

-- ============ PostgreSQL ============
CREATE TABLE produto_postgres (
    codigo_barras CHAR(13)     NOT NULL,  -- Atenção: no Postgres o espaço é preservado
    nome          VARCHAR(100) NOT NULL,
    descricao     TEXT         NULL       -- Até 1 GB, via TOAST
);

-- Verificando o domínio efetivo (funciona nos dois SGBDs)
SELECT column_name, data_type, character_maximum_length
  FROM information_schema.columns
 WHERE table_name IN ('produto_mysql', 'produto_postgres')
 ORDER BY table_name, ordinal_position;

Exemplo 4: Auditoria Temporal no MySQL

CREATE TABLE auditoria_mysql (
    id              INT UNSIGNED AUTO_INCREMENT PRIMARY KEY,
    dado            VARCHAR(50)    NOT NULL,
    data_criacao    TIMESTAMP      NOT NULL DEFAULT CURRENT_TIMESTAMP,
    data_modificacao TIMESTAMP     NOT NULL DEFAULT CURRENT_TIMESTAMP
                                    ON UPDATE CURRENT_TIMESTAMP
) ENGINE = InnoDB;

-- Rastreamento automático: o SGBD preenche os dois campos
INSERT INTO auditoria_mysql (dado) VALUES ('Pedido #1042 criado');
SELECT id, dado, data_criacao, data_modificacao FROM auditoria_mysql;

ON UPDATE CURRENT_TIMESTAMP é exclusivo do MySQL

A cláusula ON UPDATE CURRENT_TIMESTAMP é uma extensão do MySQL e será rejeitada pelo PostgreSQL. No PostgreSQL, a mesma lógica é implementada com uma trigger sobre a tabela ou, mais elegantemente, mantida apenas pelo aplicativo em tempo de execução.

Exemplo 5: Aritmética Temporal no PostgreSQL

-- O tipo INTERVAL evita o aninhamento de funções como DATE_ADD / DATE_SUB
SELECT
    NOW()                                        AS momento_atual,
    NOW() + INTERVAL '15 days'                   AS vencimento,
    '2026-12-31'::date - '2026-01-01'::date      AS dias_no_ano,
    TIMESTAMPTZ '2026-03-15 10:00:00-03'         AS instante_com_fuso;

-- No MySQL, o mesmo resultado exige funções específicas do dialeto:
SELECT
    NOW()                                  AS momento_atual,
    DATE_ADD(NOW(), INTERVAL 15 DAY)       AS vencimento,
    DATEDIFF('2026-12-31', '2026-01-01')   AS dias_no_ano;

Exemplo 6: Tipos Compostos no PostgreSQL

-- Exclusivo do PostgreSQL: tipo composto definido pelo usuário
CREATE TYPE endereco_completo AS (
    rua    VARCHAR(100),
    cidade VARCHAR(50),
    cep    CHAR(8)
);

CREATE TABLE cliente_custom (
    id                 INT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    nome               VARCHAR(100)  NOT NULL,
    endereco_comercial endereco_completo,
    tags               TEXT[]         -- Array nativo do PostgreSQL
);

-- Acesso ao campo composto
SELECT nome, (endereco_comercial).cidade AS cidade FROM cliente_custom;

No MySQL, não existe tipo composto. A aproximação mais próxima seria uma coluna JSON com validação por CHECK, ou a extração para uma tabela endereco relacionada por chave estrangeira — o que, na prática, descarrega para a modelagem relacional justamente aquilo que o tipo composto resolveu.

Dicas & Lembretes

  • Dinheiro nunca vira float: valores monetários exigem DECIMAL/NUMERIC. Ponto flutuante serve para métricas tolerantes a erro (percentuais, médias, trigonometria), nunca para valores que serão somados.
  • A largura da coluna é uma promessa: declarar VARCHAR(50) para um campo que em breve será substituído por VARCHAR(255) é uma migração de dados disfarçada de detalhe.
  • Portabilidade não é portabilidade de dialeto: o padrão ANSI cobre INT e VARCHAR. Recursos como AUTO_INCREMENT, UNSIGNED, ENUM e ON UPDATE são proprietários do MySQL e exigem camada de abstração se o projeto pretende migrar.
  • UNSIGNED no PostgreSQL: não existe o modificador. A alternativa idiomática é NUMERIC(p, 0) CHECK (coluna >= 0), que preserva o domínio sem poluir o DDL com dialeto.
  • Índices são feitos de tipos: uma chave primária BIGINT ocupa 8 bytes por entrada em cada índice secundário que a referencia — o tipo errado se propaga para toda a base.
  • Próxima aula: Aula 32 — Indexação e Estruturas Físicas (B-Tree, Hash, GiST e GIN), para entender como o tipo escolhido impacta o tamanho e a velocidade dos índices nos dois SGBDs.

Como aplicar na Prática

  • Projeto de e-commerce: INT UNSIGNED AUTO_INCREMENT para o id_produto, CHAR(13) para o código de barras EAN, VARCHAR(120) para o nome e DECIMAL(12,2) para o preço — sem exceção de FLOAT.
  • Sistema de auditoria: use TIMESTAMP DEFAULT CURRENT_TIMESTAMP no MySQL para preenchimento automático, ou um trigger no PostgreSQL. Para eventos com prazo superior a 2038, migre para DATETIME ou TIMESTAMPTZ.
  • Aplicação multi-timezone (SaaS): adote TIMESTAMPTZ no PostgreSQL e converta apenas na camada de apresentação. Armazenar a hora já convertida destrói a informação original.
  • Listas de valores: ENUM do MySQL é rápido, porém altera o DDL para cada novo item. Em esquemas que precisam evoluir sem janela de manutenção, prefira tabela de domínio com FK.
  • Dados semiestruturados: JSONB com índice GIN resolve consultas por chave interna com desempenho aceitável. Em MySQL, avalie a alternativa de colunas geradas (generated columns) indexáveis.
  • Auditoria de bases legadas: rode SELECT table_name, column_name, data_type FROM information_schema.columns e procure por FLOAT em colunas monetárias, VARCHAR(255) em toda parte e CHAR superdimensionado.
