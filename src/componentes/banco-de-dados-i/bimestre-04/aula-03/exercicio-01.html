Enunciado

A Loja do Bairro está implantando sua base de dados e o responsável técnico exige que nenhuma configuração de texto dependa do default da máquina. Você vai criar os bancos nos dois SGBDs com charset e colação explícitos, inventariar as regras de cada servidor e comprovar, na prática, o que muda quando a colação muda.

O grande diferencial desta atividade é a comparação experimental: os mesmos dados e as mesmas consultas serão executados sob colações diferentes, para que você registre os resultados divergentes.

Preparação

  1. Ambiente: MySQL 8.0+ e PostgreSQL 12+ disponíveis (XAMPP, WampServer ou Docker), acessíveis por MySQL Workbench, pgAdmin ou terminal.
  2. Bancos: crie loja_mysql e loja_postgres seguindo os blocos abaixo.
  3. Registro: anote literalmente cada comando executado e o resultado obtido — a entrega é um parecer com os comandos e as respostas colados.

  • 01_criacao.sql — criação de databases com configuração explícita.
  • 02_inventario.sql — inspeção de charsets e colações disponíveis.

2. Desafios de Prática

Bloco 1: Criação com Configuração Explícita

  1. Crie os bancos com charset e colação declarados nos dois SGBDs: 
    -- MySQL
CREATE DATABASE loja_mysql
    CHARACTER SET utf8mb4
    COLLATE utf8mb4_0900_ai_ci;

-- PostgreSQL (locale de Português/Brasil)
CREATE DATABASE loja_postgres
    WITH
    ENCODING = 'UTF8'
    LC_COLLATE = 'pt_BR.UTF-8'
    LC_CTYPE    = 'pt_BR.UTF-8'
    TEMPLATE    = template0;
  2. Se o PostgreSQL recusar a criação, anote a mensagem de erro e explique o que ela diz sobre template1 e sobre o locale do servidor. Tente novamente sem a cláusula TEMPLATE e compare.
  3. Sem declarar charset nenhum, crie loja_default nos dois SGBDs e descubra quais regras ela herdou: 
    -- MySQL: qual charset/colação o banco recebeu?
SELECT DEFAULT_CHARACTER_SET_NAME, DEFAULT_COLLATION_NAME
  FROM information_schema.SCHEMATA
 WHERE SCHEMA_NAME = 'loja_default';

-- PostgreSQL: encoding e locales herdados
SELECT datname, pg_encoding_to_char(encoding),
       datcollate, datctype
  FROM pg_database
 WHERE datname = 'loja_default';
    Os dois ambientes herdaram o mesmo? Justifique a importância disso para um script de implantação.

Bloco 3: ALTER DATABASE e o que ele (não) muda

  1. Crie uma tabela cliente em loja_mysql, insira três nomes com caixas diferentes e execute: 
    USE loja_mysql;
CREATE TABLE cliente (
    id    INT UNSIGNED AUTO_INCREMENT PRIMARY KEY,
    nome  VARCHAR(60) NOT NULL
);
INSERT INTO cliente (nome) VALUES ('Carlos'), ('carlos'), ('CARLOS');

SELECT * FROM cliente WHERE nome = 'carlos';
    Quantos registros retornaram? Por quê?
  2. Execute ALTER DATABASE loja_mysql COLLATE utf8mb4_bin; e repita a consulta da questão anterior sem recriar a tabela. O resultado mudou? Explique observando a colação efetiva da coluna: 
    SELECT COLUMN_NAME, COLLATION_NAME
  FROM information_schema.COLUMNS
 WHERE TABLE_SCHEMA = 'loja_mysql'
   AND TABLE_NAME = 'cliente';
  3. Converta a tabela para a nova colação com ALTER TABLE cliente CONVERT TO CHARACTER SET utf8mb4 COLLATE utf8mb4_bin;, repita a consulta e explique por que o comportamento mudou agora. Que cuidado esse comando exige em bases grandes?
  4. No PostgreSQL, crie um segundo banco com LC_COLLATE = 'C' (ordem por código de bytes) e compare a saída de ORDER BY nome em um banco pt_BR.UTF-8. Anote as duas sequências obtidas.

Bloco 4: Colisões Silenciosas sob Diferentes Colações

  1. Teste a busca por e-mail exigindo distinção de caixa, sem alterar o DDL da tabela: 
    CREATE TABLE usuarios (
    id    INT UNSIGNED AUTO_INCREMENT PRIMARY KEY,
    email VARCHAR(120) NOT NULL
) CHARACTER SET utf8mb4 COLLATE utf8mb4_0900_ai_ci;

INSERT INTO usuarios (email) VALUES ('USER@EMAIL.COM'), ('user@email.com');

-- Sob _ci: quantos registros?
SELECT * FROM usuarios WHERE email = 'user@email.com';

-- Forçando a comparação binária na consulta:
SELECT * FROM usuarios
 WHERE email COLLATE utf8mb4_bin = 'user@email.com';
    Registre os dois resultados.
  2. Com a tabela usuarios ainda sob _ci, tente inserir o e-mail duplicado em caixa diferente. O que a chave única (se houver) ou a segunda INSERT revelam sobre o custo silencioso da colação _ci?
  3. Modele no PostgreSQL o mesmo cenário com citext (extensão CREATE EXTENSION citext;) e compare: o PostgreSQL resolve case-insensitivity por colação ou por tipo de dado? Essa diferença é uma questão de portabilidade?
  4. Ordene os mesmos nomes ('Carlos', 'carlos', 'CH', 'Ch', 'casa') sob utf8mb4_0900_ai_ci e sob utf8mb4_bin. Cole as duas saídas e explique a diferença observada.

Bloco 6: Refletindo sobre a Prática

  2. Sua equipe usa MySQL em produção e o cliente exige migração futura para PostgreSQL. Liste os 3 pontos desta aula que exigem decisão na migração (charset, colação e locale) e proponha como documentá-los.
  3. Justifique tecnicamente por que comparar colunas de colações diferentes em um JOIN impede o uso de índice B-Tree, lembrando que a árvore foi construída na ordem de uma colação específica.

Orientações Finais

  • Experimento controlado: toda diferença afirmada na entrega deve vir de um comando executado nos dois servidores, com o resultado colado.
  • Charset não é colação: ao registrar resultados, diga sempre qual dos dois está variando — a codificação dos bytes ou a régua de comparação.
  • Alterar colação é migração: antes de recomendar CONVERT TO CHARACTER SET, avalie o lock e o risco de duplicatas decorrentes da nova regra de unicidade.
