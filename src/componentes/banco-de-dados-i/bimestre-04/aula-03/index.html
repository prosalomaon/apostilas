Teoria & Conceitos

A Linguagem de Definição de Dados (Data Definition Language — DDL) é a sublinguagem da SQL utilizada por administradores de banco de dados (DBAs) e projetistas para definir, modificar e estruturar o esquema do banco de dados no catálogo do SGBD. Enquanto a DML manipula o conteúdo das tabelas, a DDL constrói o próprio contêiner que as armazena.

No ciclo de implementação do modelo físico, antes de criar tabelas, chaves primárias e relacionamentos, o primeiro passo lógico e operacional consiste em inicializar a área de armazenamento onde residirão todos os objetos da aplicação: o Database (Banco de Dados). O comando responsável por essa etapa é o CREATE DATABASE. Durante sua execução, define-se não apenas o nome lógico do banco de dados, mas também suas regras de codificação de texto e ordenação — regras que, como veremos, acompanham todas as colunas de texto criadas dentro dele.

1. Fundamentos de Conjunto de Caracteres (Character Set) e Colação (Collation)

Ao armazenar informações de texto (strings) em um banco de dados relacional, o SGBD precisa saber como converter caracteres humanos em bytes fisicamente e como comparar duas sequências de texto entre si. São duas responsabilidades distintas, que costumam ser confundidas: 

1. Character Set (Encoding) --> Define COMO os caracteres viram bytes.
2. Collation (Colação)      --> Define COMO as strings são comparadas.

1.1. Character Set (Conjunto de Caracteres)

O Character Set (ou charset) é a tabela de mapeamento que associa cada símbolo, letra ou número a um código numérico binário bruto. Ele responde à pergunta: "que byte devo gravar em disco para representar a letra 'ç'?"

  • Latin1 (cp1252 / ISO-8859-1): codifica caracteres da Europa Ocidental ocupando 1 byte por caractere. Cobre o português, mas não representa a maior parte dos símbolos globais.
  • UTF-8 / UTF8MB3: codificação Unicode de tamanho variável (de 1 a 3 bytes) para caracteres da camada básica multilíngue (Basic Multilingual Plane).
  • UTF8MB4: codificação Unicode completa, de até 4 bytes por caractere. É o padrão recomendado modernamente, pois suporta todos os símbolos mundiais, ideogramas complexos e emojis sem perda ou corrupção de dados — inclusive os caracteres fora do plano básico, que o UTF8MB3 simplesmente descarta.

Por que 4 bytes fazem diferença

Um emoji como 😀 ocupa 4 bytes em UTF8MB4. Gravá-lo em uma coluna VARCHAR(10) sob UTF8MB3 faz o SGBD truncar ou recusar o caractere, porque o UTF8MB3 não possui representação para ele. O limite de VARCHAR(n) é contado em caracteres, mas o espaço físico é medido em bytes: 1 caractere UTF8MB4 pode consumir 4 bytes.

1.2. Collation (Colação / Regra de Ordenação)

A Collation é o conjunto de regras lógicas que determina a ordenação e a comparação de igualdade entre caracteres dentro de um determinado Character Set. Ela responde a perguntas como:

  • 'A' é igual a 'a'?
  • 'á' é igual a 'a'?
  • O caractere 'ch' vem depois de 'c' ou é tratado como uma letra simples (como no espanhol tradicional)?

Uma mesma colação só pode ser aplicada sobre um Character Set compatível: não existe utf8mb4_0900_ai_ci sobre Latin1, porque as regras de comparação pressupõem o alfabeto que o charset consegue representar.

1.3. Convenções de Nomenclatura de Collations (Sufixos)

Nos SGBDs relacionais (especialmente no MySQL), o nome da colação indica seu comportamento por meio de sufixos padronizados. Decifrar o nome é ler a semântica da comparação:

Sufixo Significado Comportamento na Comparação Exemplo
_ci Case-Insensitive Insensível a maiúsculas e minúsculas ('A' = 'a'). utf8mb4_0900_ai_ci
_cs Case-Sensitive Sensível a maiúsculas e minúsculas ('A' ≠ 'a'). latin1_general_cs
_bin Binary Compara estritamente os valores numéricos dos bytes, sem interpretação linguística. utf8mb4_bin
_ai Accent-Insensitive Insensível a acentos ('á' = 'a'). utf8mb4_0900_ai_ci
_as Accent-Sensitive Sensível a acentos ('á' ≠ 'a'). utf8mb4_0900_as_cs

Note que o nome pode combinar sufixos: utf8mb4_0900_ai_ci é accent-insensitive e case-insensitive, enquanto utf8mb4_0900_as_cs é sensível nos dois eixos.

2. Implementação Prática no MySQL

No MySQL, a criação do banco de dados permite especificar explicitamente o Character Set e a Collation padrão. Caso não sejam informados, o servidor adotará suas configurações globais (character_set_server e collation_server), o que significa que o comportamento do seu DDL pode variar de uma máquina para outra. 

-- Criando um banco de dados com configurações padrão do servidor
CREATE DATABASE comercial;

-- Criando um banco de dados garantindo codificação UTF-8 completa
-- e colação insensível a maiúsculas/acentos
CREATE DATABASE loja_virtual
    CHARACTER SET utf8mb4
    COLLATE utf8mb4_0900_ai_ci;

-- Listar todos os conjuntos de caracteres suportados pelo MySQL
SHOW CHARACTER SET;

-- Listar as colações disponíveis para o charset utf8mb4
SHOW COLLATION LIKE 'utf8mb4%';

Alterando e Verificando o Database Atual

Se as necessidades da aplicação mudarem, é possível alterar o conjunto padrão de caracteres de um banco existente com o comando ALTER DATABASE: 

-- Selecionando o banco de dados para uso
USE loja_virtual;

-- Alterando a colação padrão do banco existente
ALTER DATABASE loja_virtual
    CHARACTER SET utf8mb4
    COLLATE utf8mb4_bin;

ALTER DATABASE muda a régua, não as fichas já gravadas

A alteração afeta o padrão aplicado a novos objetos (tabelas e colunas criadas a partir daquele momento). As colunas já existentes não são convertidas automaticamente: para isso seria preciso um ALTER TABLE ... CONVERT TO CHARACTER SET ... sobre cada tabela — uma operação de migração de dados, com lock e tempo proporcional ao volume.

3. Implementação Prática no PostgreSQL

O PostgreSQL lida com codificação de texto por meio dos parâmetros de Locale do sistema operacional (LC_COLLATE e LC_CTYPE) e utiliza o conceito de Template Databases durante o CREATE DATABASE.

3.1. O Conceito de Template Database

Quando um banco de dados é criado no PostgreSQL, ele é gerado a partir de uma cópia de um banco de dados modelo existente (por padrão, o template1 ou template0). O template1 é o "molde vivo" do servidor: se você instalar extensões ou objetos nele, todo banco criado depois já os herdará. O template0 é a cópia pristine, intocada, usada quando é preciso controlar encoding e locale explicitamente. 

-- Criando um banco de dados básico (herda encoding e locale do template1)
CREATE DATABASE gestao_db;

-- Criando um banco de dados com Encoding UTF8 e Locales específicos de Português/Brasil
CREATE DATABASE escolar_db
    WITH
    OWNER = postgres
    ENCODING = 'UTF8'
    LC_COLLATE = 'pt_BR.UTF-8'
    LC_CTYPE = 'pt_BR.UTF-8'
    TEMPLATE = template0;
  • ENCODING: define a codificação de caracteres armazenados — o equivalente ao CHARACTER SET do MySQL.
  • LC_COLLATE: define a regra de ordenação de strings (alfabetização) segundo a cultura regional (pt_BR).
  • LC_CTYPE: define a classificação de tipos de caracteres — o que é letra maiúscula, minúscula ou dígito.
  • TEMPLATE: indica qual banco será copiado. Ao especificar LC_COLLATE diferente do locale do servidor, é obrigatório usar o template0, pois o template1 já está inicializado com o locale do servidor: usá-lo como molde resultaria em erro, porque o locale do novo database divergiria do locale já gravado na cópia.

4. Impacto Prático da COLLATION nas Aplicações

A escolha da Collation afeta diretamente o comportamento das consultas SQL cotidianas — não é um detalhe de configuração "de infraestrutura".

4.1. Comparações e Filtros (WHERE)

Considere uma tabela com os nomes 'Carlos', 'carlos' e 'CARLOS':

  • Com colação utf8mb4_0900_ai_ci: a consulta SELECT * FROM cliente WHERE nome = 'carlos' retornará os 3 registros.
  • Com colação utf8mb4_bin ou _cs: a mesma consulta retornará apenas o registro 'carlos'.

4.2. Ordenação (ORDER BY)

Em línguas diferentes, a ordem alfabética varia. Por exemplo, em espanhol tradicional, a colação utf8_spanish2_ci ordena a sequência 'ch' depois da letra 'c', diferentemente da colação genérica utf8_general_ci, que trata 'ch' como qualquer dígrafo — c seguido de h.

4.3. Índices e Desempenho

A ordenação dos dados em índices B-Tree depende diretamente da colação escolhida: a árvore é construída na ordem em que a colação compara. Comparar strings com colações diferentes em comandos de junção (JOIN) impede o uso de índices e força a conversão explícita de tipos, reduzindo a velocidade de resposta do SGBD.

5. Alteração e Exclusão de Databases

A remoção de um banco de dados é uma instrução DDL irreversível que apaga permanentemente o catálogo, suas tabelas e todos os dados gravados. Não há lixeira: a partir do commit da transação DDL, os dados não existem mais. 

-- Sintaxe para exclusão permanente do banco de dados
DROP DATABASE loja_virtual;

-- Prevenção de erro caso o banco não exista
DROP DATABASE IF EXISTS loja_virtual;

Exemplo de Código

Vamos materializar a criação de bancos com regras de codificação explícitas nos dois SGBDs. Todos os blocos devem ser executados no ambiente da aula e verificados com os comandos de inspeção ao final de cada um.

Exemplo 1: Criação de Database no MySQL com Charset Explícito

-- Banco com padrões do servidor (atenção: pode variar entre máquinas!)
CREATE DATABASE comercial;

-- Banco com UTF8MB4 completo e colação insensível a caixa e acentos
CREATE DATABASE loja_virtual
    CHARACTER SET utf8mb4
    COLLATE utf8mb4_0900_ai_ci;

-- Verificando qual charset/collation o banco realmente recebeu
SELECT DEFAULT_CHARACTER_SET_NAME AS charset,
       DEFAULT_COLLATION_NAME     AS collation
  FROM information_schema.SCHEMATA
 WHERE SCHEMA_NAME = 'loja_virtual';

Exemplo 2: Inspecionando Charsets e Collations Disponíveis

-- Listar todos os conjuntos de caracteres suportados pelo MySQL
SHOW CHARACTER SET;

-- Listar as colações disponíveis para o charset utf8mb4
SHOW COLLATION LIKE 'utf8mb4%';

-- Descobrir qual colação está em vigor nesta sessão, neste momento
SELECT @@character_set_database AS charset_atual,
       @@collation_database     AS collation_atual;

Exemplo 3: Alterando a Colação de um Banco Existente

USE loja_virtual;

-- Passando o banco para colação binária (sensível a caixa e acentos)
ALTER DATABASE loja_virtual
    CHARACTER SET utf8mb4
    COLLATE utf8mb4_bin;

-- Atenção: tabelas JÁ existentes não mudaram. Converta-as explicitamente:
ALTER TABLE cliente
    CONVERT TO CHARACTER SET utf8mb4
    COLLATE utf8mb4_bin;

Conversão de tabela existente é migração de dados

O ALTER TABLE ... CONVERT TO CHARACTER SET reescreve as colunas de texto da tabela inteira. Em bases grandes, isso exige janela de manutenção — e pode até alterar o resultado de chaves únicas, porque valores que colidiam sob a colação antiga deixam de colidir sob a nova (ou vice-versa).

Exemplo 4: Criação de Database no PostgreSQL com Locale Regional

-- Banco básico: herda encoding e locale do template1
CREATE DATABASE gestao_db;

-- Banco com Encoding UTF8 e Locales de Português/Brasil.
-- O TEMPLATE = template0 é obrigatório quando LC_COLLATE/LC_CTYPE
-- diferem dos valores já gravados no template1.
CREATE DATABASE escolar_db
    WITH
    OWNER = postgres
    ENCODING = 'UTF8'
    LC_COLLATE = 'pt_BR.UTF-8'
    LC_CTYPE    = 'pt_BR.UTF-8'
    TEMPLATE    = template0;

-- Verificando as regras do banco criado
SELECT datname, pg_encoding_to_char(encoding) AS encoding,
       datcollate AS lc_collate, datctype AS lc_ctype
  FROM pg_database
 WHERE datname = 'escolar_db';

-- Listando colações conhecidas pelo servidor
SELECT collname, collencoding
  FROM pg_collation
 WHERE collname LIKE '%pt_BR%'
 LIMIT 10;

Exemplo 5: Forçando uma Colação em Tempo de Consulta (MySQL)

-- Tabela criada sob a colação padrão case-insensitive
CREATE TABLE usuarios (
    id     INT UNSIGNED AUTO_INCREMENT PRIMARY KEY,
    email  VARCHAR(120) NOT NULL
) CHARACTER SET utf8mb4 COLLATE utf8mb4_0900_ai_ci;

INSERT INTO usuarios (email) VALUES ('USER@EMAIL.COM'), ('user@email.com');

-- Sob _ci, o filtro encontra os DOIS registros (maiusculas ignoradas)
SELECT * FROM usuarios WHERE email = 'user@email.com';

-- Forçando comparação binária na consulta, sem alterar a tabela
SELECT * FROM usuarios
 WHERE email COLLATE utf8mb4_bin = 'user@email.com';
-- Resultado: apenas 'user@email.com'

O operador COLLATE dentro da consulta sobrepõe a colação da coluna para aquela expressão específica. É a solução pontual quando a regra da tabela não serve para um filtro determinado — sem exigir ALTER TABLE.

Dicas & Lembretes

  • Charset é a régua, collation é a comparação: o Character Set decide o byte gravado; a Collation decide se dois bytes diferentes "contam" como o mesmo texto.
  • Padrão moderno é UTF8MB4: qualquer banco novo sem charset explícito herda a configuração global do servidor — que pode ser antiga. Especifique sempre CHARACTER SET e COLLATE no script de implantação.
  • _ci tem custo silencioso em unicidade: sob _ci, uma chave única sobre e-mail recusa 'USER@X.COM' depois de 'user@x.com' — o que pode ser desejável (e-mail é case-insensitive no domínio local) ou um bug de negócio.
  • Colação não é só MySQL: no PostgreSQL a ordenação vem do locale do sistema (LC_COLLATE), por isso a criação do banco usa TEMPLATE = template0 quando o locale precisa ser controlado.
  • Altere a colação antes de popular: converter a colação de uma tabela cheia é uma migração com lock, e pode quebrar ou criar chaves duplicadas conforme a nova régua de comparação.
  • Próxima aula: Aula 34 — Criação de tabelas com restrições de integridade (NOT NULL, UNIQUE), para aplicar dentro do database recém-criado as regras que garantem a qualidade dos dados gravados.

Como aplicar na Prática

  • Script de implantação versionado: o CREATE DATABASE deve entrar no repositório junto com o DDL das tabelas, com charset e collation explícitos — nunca depender do default da máquina do desenvolvedor.
  • Multi-idioma desde o início: para sistemas com comentários de usuário, catálogo com produtos internacionais ou suporte a emoji, adote utf8mb4 + colação _ai_ci no MySQL e ENCODING 'UTF8' no PostgreSQL.
  • Identificadores estritos: para colunas como código de barras, chaves de acesso ou tokens, use colação utf8mb4_bin — comparação byte a byte, sem normalização inesperada.
  • Auditoria de bases legadas: rode SELECT SCHEMA_NAME, DEFAULT_CHARACTER_SET_NAME, DEFAULT_COLLATION_NAME FROM information_schema.SCHEMATA (MySQL) e SELECT datname, datcollate, datctype FROM pg_database (PostgreSQL) para inventariar quais bancos herdaram charset antigo.
  • Filtro pontual sem DDL: quando apenas uma consulta precisa de outra regra, use o operador COLLATE na expressão, em vez de alterar a coluna para todos os consumidores.
  • Cuidado com DROP DATABASE em scripts: use IF EXISTS para idempotência, mas mantenha a execução do script destrutivo separada do deploy rotineiro.
