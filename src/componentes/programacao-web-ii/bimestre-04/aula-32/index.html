Teoria & Conceitos

Na aula anterior, vimos que os cookies resolvem a ausência de estado do HTTP armazenando preferências e histórico no navegador do cliente. Para um sistema de autenticação, porém, essa abordagem é insuficiente: como qualquer dado gravado no computador do usuário pode ser inspecionado e editado pelas ferramentas de desenvolvimento (ou por um atacante), nunca se deve confiar no cliente para decidir quem é o usuário.

Nesta aula do componente de Programação Web II, estudaremos o uso de Sessões no PHP: moveremos a lógica de autenticação para o servidor, criaremos uma "área restrita" controlada e aplicaremos as contramedidas contra os dois ataques clássicos de sessão, o Session Fixation (fixação de sessão) e o Session Hijacking (sequestro de sessão).

1.1. O Conceito de Sessão no Lado do Servidor

Como o protocolo HTTP é stateless (não guarda memória entre uma requisição e outra), o servidor trata cada página como uma transação isolada. As sessões existem justamente para preservar o estado do usuário ao longo de múltiplas páginas sem violar essa característica do protocolo.

A diferença essencial em relação aos cookies tradicionais é onde os dados ficam: em uma sessão do PHP, as informações reais (identificador do usuário, nível de permissão, carrinho, etc.) são gravadas em arquivos privados no disco do servidor. No computador do cliente, o navegador guarda apenas um único cookie temporário com a chave de identificação da sessão, normalmente chamado PHPSESSID. 

+--------------------------+                     +--------------------------+
|   Navegador (Cliente)    |                     |     Servidor Web PHP     |
+--------------------------+                     +--------------------------+
| Cookie:                  |                     | /tmp/sess_a1b2c3d4e5f6.. |
| PHPSESSID=a1b2c3d4e5f6.. | --- Envia a chave --> | ------------------------ |
|                          |                     | $_SESSION['usuario_id']=5|
| (Apenas o identificador) |                     | $_SESSION['nome'] = 'Ana'|
+--------------------------+                     +--------------------------+
  • Se o cliente adulterar o cookie e enviar um PHPSESSID inexistente, o PHP simplesmente cria uma nova sessão vazia: nenhuma variável de permissão é inventada.
  • Se o arquivo de sessão no servidor for apagado (ou expirar), o usuário perde o estado e precisa se autenticar novamente.
  • O cookie do cliente é apenas o elo: por isso ele precisa ser protegido com as flags httponly e secure, estudadas na aula 31.

1.2. O Ciclo de Vida da Sessão (session_start())

A função session_start() faz as duas coisas necessárias ao início do ciclo: lê o PHPSESSID enviado pelo navegador, carrega o arquivo de sessão correspondente no servidor (ou cria um novo, se o ID não existir) e popula a superglobal $_SESSION, pronta para leitura e gravação.

  1. Regra de ouro: session_start() envia o cabeçalho HTTP Set-Cookie: PHPSESSID=.... Por isso ela deve ser executada no início do script PHP, antes de qualquer saída de texto, espaço em branco ou tag HTML — caso contrário aparece o aviso Cannot modify header information - headers already sent.
  2. Uma chamada por requisição: chamar session_start() duas vezes gera o aviso session_start(): Session cannot be started after headers have already been sent (ou o aviso de reabertura). O padrão defensivo é: if (session_status() === PHP_SESSION_NONE) { session_start(); }.
  3. Estado em memória: as variáveis gravadas em $_SESSION persistem enquanto a sessão estiver ativa, mesmo que o usuário navegue por dezenas de páginas.
  4. Encerramento: o ciclo termina com session_destroy() (logout), com o tempo de inatividade configurado em session.gc_maxlifetime ou com o fechamento do navegador, quando o cookie é de sessão.

1.3. Autenticação Segura de Usuários

Autenticar significa verificar a identidade a partir de credenciais (e-mail/usuário e senha) e, em caso de sucesso, registrar esse estado na sessão. A sequência correta tem quatro etapas:

  1. Validação da entrada: leitura do $_POST com operador de coalescência, remoção de espaços e verificação de campos vazios antes de qualquer consulta.
  2. Consulta parametrizada: busca do usuário com PDO e prepared statements (bindValue()), neutralizando ataques de SQL Injection.
  3. Verificação da senha com password_verify(): a senha digitada é comparada com o hash criptográfico (Bcrypt/Argon2) armazenado no banco. Nunca com == e nunca com a senha em texto puro.
  4. Registro do estado na sessão: apenas em caso de sucesso, grava-se $_SESSION['usuario_id'] — é essa variável, e não o cookie, que passa a decidir o acesso às páginas restritas.

1.4. Proteção contra Vulnerabilidades Críticas de Sessão

A. Session Fixation (Fixação de Sessão)

O ataque ocorre quando o invasor força a vítima a usar um ID de sessão já conhecido por ele — por exemplo, enviando um link com ?PHPSESSID=12345 ou um cookie plantado no navegador da vítima. Se a vítima fizer login sem que o ID mude, o atacante simplesmente passa a usar o mesmo ID e acessa a conta já autenticada.

Solução: toda vez que o nível de privilégio do usuário mudar (login bem-sucedido, troca de perfil, elevação de permissão), chame session_regenerate_id(true). A função gera uma nova chave randômica para a sessão e deleta o arquivo da sessão antiga, invalidando o token que o atacante conhecia. 

<?php
// Depois de confirmar as credenciais com password_verify():
session_regenerate_id(true); // novo ID + destrói a sessão antiga
$_SESSION['usuario_id'] = (int) $usuario['id'];

B. Session Hijacking (Sequestro de Sessão)

Neste ataque, o cibercriminoso rouba o cookie PHPSESSID do usuário legítimo — por escuta de rede (HTTP sem TLS), por um código XSS injetado na página ou por acesso físico ao computador — e simplesmente o reutiliza: para o servidor, ele é o usuário.

Medidas de proteção combinadas:

  • Cookie httponly : impede que o JavaScript de um eventual XSS leia o token via document.cookie.
  • Cookie secure + samesite: força a transmissão apenas por HTTPS e limita o envio cruzado de origens externas.
  • Impressão digital da sessão: grava-se no login o cabeçalho HTTP_USER_AGENT (e, com cautela, o IP) e compara-se a cada nova requisição. Havendo divergência, a sessão é destruída e o usuário é levado ao login.
  • Tempo de inatividade: limita a janela de aproveitamento de um token roubado.

1.5. O Mecanismo de Controle de "Área Restrita"

Para proteger qualquer página de acesso privado (painel.php, perfil.php, relatorios.php), cria-se uma verificação de autorização no topo do script, antes de qualquer HTML:

  1. Inicia (ou reaproveita) a sessão com session_start().
  2. Verifica se a variável de autenticação está definida e é válida (isset($_SESSION['usuario_id'])).
  3. Se a variável não existir, interrompe o carregamento: envia header('Location: login.php') e encerra o script com exit;.

Por que o exit; é obrigatório?

O header('Location: ...') apenas declara o redirecionamento no cabeçalho da resposta; o PHP continua executando o restante do arquivo. Sem o exit;, todo o conteúdo da página restrita seria gerado (e até enviado) antes de o navegador cumprir o redirecionamento — o que também libera o aviso de cabeçalhos já enviados e pode vazar a saída para quem inspeciona a resposta.

1.6. Encerrando a Sessão com Segurança (Logout Limpo)

Um logout completo não se resume a apagar a variável da memória. É preciso eliminar os resíduos no servidor e no cliente, sempre nesta ordem: 

<?php
declare(strict_types=1);

session_start();

// 1. Limpa todas as variáveis da sessão em memória
$_SESSION = [];

// 2. Destrói o cookie PHPSESSID no navegador do cliente
if (ini_get('session.use_cookies')) {
    $params = session_get_cookie_params();
    setcookie(session_name(), '', [
        'expires'  => time() - 42000,
        'path'     => $params['path'],
        'domain'   => $params['domain'],
        'secure'   => $params['secure'],
        'httponly' => $params['httponly'],
        'samesite' => $params['samesite'] ?? 'Lax'
    ]);
}

// 3. Destrói o arquivo de sessão gravado no servidor
session_destroy();

header('Location: login.php');
exit;

Pular o passo 2 é o erro mais comum: o navegador continuaria enviando um PHPSESSID válido cujo arquivo ainda existiria no disco até a expiração por inatividade.

Exemplos de Código

Os três scripts abaixo formam um sistema de autenticação completo e funcional: login.php valida as credenciais e regenera a sessão, autenticacao.php funciona como guardião reutilizável e painel.php é a página protegida, encerrada pelo logout.php.

Exemplo 1: login.php — Processamento de Login com Segurança

Recebe os dados via formulário POST, consulta o banco com PDO e prepared statements, valida a senha com password_verify(), regenera o ID da sessão e grava o estado de autenticação. 

<?php
declare(strict_types=1);

// 1. A sessão é iniciada ANTES de qualquer saída HTML
session_start();

$mensagemErro = '';

if ($_SERVER['REQUEST_METHOD'] === 'POST') {
    // 2. Validação/sanitização da entrada
    $email = trim($_POST['email'] ?? '');
    $senha = $_POST['senha'] ?? '';

    if ($email === '' || $senha === '') {
        $mensagemErro = 'Preencha todos os campos corretamente.';
    } else {
        try {
            $dsn = 'mysql:host=localhost;dbname=escola;charset=utf8mb4';
            $pdo = new PDO($dsn, 'root', '', [
                PDO::ATTR_ERRMODE            => PDO::ERRMODE_EXCEPTION,
                PDO::ATTR_DEFAULT_FETCH_MODE => PDO::FETCH_ASSOC,
            ]);

            // 3. Consulta parametrizada: previne SQL Injection
            $stmt = $pdo->prepare(
                'SELECT id, nome, senha_hash FROM usuarios WHERE email = :email LIMIT 1'
            );
            $stmt->bindValue(':email', $email, PDO::PARAM_STR);
            $stmt->execute();
            $usuario = $stmt->fetch();

            // 4. Verificação do hash da senha (Bcrypt/Argon2)
            if ($usuario && password_verify($senha, $usuario['senha_hash'])) {

                // 5. PREVENÇÃO DE SESSION FIXATION
                session_regenerate_id(true);

                // 6. Registro do estado autenticado
                $_SESSION['usuario_id']   = (int) $usuario['id'];
                $_SESSION['usuario_nome'] = $usuario['nome'];
                $_SESSION['user_agent']   = $_SERVER['HTTP_USER_AGENT'] ?? '';
                $_SESSION['ultimo_acesso'] = time();

                // 7. Redirecionamento para a área restrita
                header('Location: painel.php');
                exit;
            }

            // Mensagem genérica: não revela qual campo está errado
            $mensagemErro = 'E-mail ou senha incorretos.';
        } catch (PDOException $e) {
            error_log('Erro de login: ' . $e->getMessage());
            $mensagemErro = 'Ocorreu um erro ao processar o acesso.';
        }
    }
}
?>
<!DOCTYPE html>
<html lang="pt-BR">
<head>
    <meta charset="UTF-8">
    <title>Acesso ao Sistema</title>
</head>
<body>
    <h2>Acesso ao Sistema</h2>

    <?php if ($mensagemErro !== ''): ?>
        <p style="color:#b00020;">
            <?= htmlspecialchars($mensagemErro, ENT_QUOTES, 'UTF-8') ?>
        </p>
    <?php endif; ?>

    <form method="POST" action="">
        <label for="email">E-mail</label>
        <input type="email" name="email" id="email" required>

        <label for="senha">Senha</label>
        <input type="password" name="senha" id="senha" required>

        <button type="submit">Entrar</button>
    </form>
</body>
</html>

Detalhes de segurança deste script

  • A mensagem de erro é deliberadamente genérica: dizer "e-mail não cadastrado" permitiria enumeração de usuários.
  • session_regenerate_id(true) é chamado depois da confirmação e antes de gravar as permissões — é o momento exato em que o privilégio muda.
  • Toda a saída dinâmica passa por htmlspecialchars(), neutralizando XSS refletido na mensagem de erro.

Exemplo 2: autenticacao.php & painel.php — Protegendo a Área Restrita

O script guardião é incluído no topo de toda página privada. Ele centraliza a verificação de autorização, a impressão digital da sessão e o tempo de inatividade, evitando repetir o mesmo código em dezenas de arquivos.

Script guardião (autenticacao.php):

<?php
declare(strict_types=1);

// Reaproveita a sessão se ela já estiver ativa; caso contrário, inicia
if (session_status() === PHP_SESSION_NONE) {
    session_start();
}

// (A) Verificação de autorização
if (!isset($_SESSION['usuario_id'])) {
    header('Location: login.php');
    exit; // Interrompe o script: nada da página restrita é gerado
}

// (B) Impressão digital: User-Agent registrado no login
$fingerprintAtual = $_SERVER['HTTP_USER_AGENT'] ?? '';
if (($_SESSION['user_agent'] ?? '') !== $fingerprintAtual) {
    $_SESSION = [];
    session_destroy();
    header('Location: login.php?erro=sequestro');
    exit;
}

// (C) Tempo de inatividade: 30 minutos sem acessar, encerra a sessão
$tempoLimite = 30 * 60;
if (isset($_SESSION['ultimo_acesso'])
    && (time() - $_SESSION['ultimo_acesso']) > $tempoLimite) {
    $_SESSION = [];
    session_destroy();
    header('Location: login.php?erro=timeout');
    exit;
}

// Atualiza o relógio de inatividade a cada requisição autorizada
$_SESSION['ultimo_acesso'] = time();

Página protegida (painel.php):

<?php
declare(strict_types=1);

// Se o usuário não estiver autenticado, o guardião já enviou
// o Location e encerrou a execução com exit
require __DIR__ . '/autenticacao.php';

$nomeExibido = htmlspecialchars($_SESSION['usuario_nome'] ?? '', ENT_QUOTES, 'UTF-8');
?>
<!DOCTYPE html>
<html lang="pt-BR">
<head>
    <meta charset="UTF-8">
    <title>Painel do Usuário</title>
</head>
<body>
    <h1>Bem-vindo ao Painel, <?= $nomeExibido ?>!</h1>
    <p>Esta é uma página restrita, visível apenas para usuários autenticados.</p>

    <nav>
        <ul>
            <li><a href="painel.php">Início</a></li>
            <li><a href="relatorios.php">Relatórios</a></li>
            <li><a href="logout.php">Sair (Logout)</a></li>
        </ul>
    </nav>
</body>
</html>

Exemplo 3: logout.php — Encerramento Seguro da Sessão

Destrói a sessão por completo — memória, cookie e arquivo no servidor — e redireciona o usuário para a tela de login. 

<?php
declare(strict_types=1);

if (session_status() === PHP_SESSION_NONE) {
    session_start();
}

// 1. Memória: zera todas as variáveis da sessão
$_SESSION = [];

// 2. Cliente: remove o cookie PHPSESSID do navegador
if (ini_get('session.use_cookies')) {
    $params = session_get_cookie_params();
    setcookie(session_name(), '', [
        'expires'  => time() - 42000,
        'path'     => $params['path'],
        'domain'   => $params['domain'],
        'secure'   => $params['secure'],
        'httponly' => $params['httponly'],
        'samesite' => $params['samesite'] ?? 'Lax'
    ]);
}

// 3. Servidor: apaga o arquivo de sessão em disco
session_destroy();

header('Location: login.php');
exit;

Dicas, Lembretes e Segurança

  • Cookies de sessão endurecidos: antes de chamar session_start(), configure os parâmetros do cookie com session_set_cookie_params(['httponly' => true, 'secure' => true, 'samesite' => 'Strict']). Em ambiente local sem HTTPS, deixe secure => false para não perder a sessão.
  • Nomes de sessão previsíveis: o ID deve ser gerado pelo PHP com entropia suficiente. Nunca aceite um PHPSESSID vindo da URL sem regenerá-lo logo em seguida, pois é exatamente assim que o Session Fixation é explorado.
  • session_regenerate_id(true) nos momentos certos: login, logout e qualquer mudança de perfil ou permissão. Chamá-lo a cada requisição também é possível, mas tem custo de disco extra.
  • Guardar o que é sensível apenas no servidor: permissões, identificadores e dados pessoais pertencem a $_SESSION. O cliente recebe somente a chave de identificação.
  • Serviços e tempo de vida: revise session.gc_maxlifetime, session.cookie_lifetime e o caminho gravado em session.save_path no php.ini; em produção, considere armazenar as sessões em banco de dados ou Redis para escala e segurança.
  • LGPD: dados de identificação mantidos na sessão devem ser descartados no logout e permanecer pelo menor tempo necessário à finalidade declarada ao usuário.

Como aplicar na Prática

  • Login real: monte a tabela usuarios com coluna senha_hash, cadastre senhas com password_hash($senha, PASSWORD_DEFAULT) e autentique apenas com password_verify().
  • Guardião reutilizável: coloque a verificação em um único arquivo incluído com require no topo de cada página privada, em vez de copiar o if por toda a aplicação.
  • Redirecionamento sempre com exit;: após header('Location: ...') em login, logout e guardião.
  • Registro de auditoria: grave em log o momento do login, do logout e das falhas de verificação de impressão digital, úteis para investigar acessos suspeitos.
  • Recuperação de senha: fluxo complementar com token de uso único e prazo curto, também gravado na sessão ou em banco, nunca em cookie editável.
  • Próxima aula: com autenticação e sessão funcionando, organizaremos o código em camadas seguindo o padrão MVC.
