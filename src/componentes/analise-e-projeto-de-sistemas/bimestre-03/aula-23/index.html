Teoria & Conceitos

1. O que são Operadores de Controle?

Na UML 2.0, o fluxo puramente sequencial de mensagens pode ser estendido para representar comportamentos condicionais ou repetitivos através dos Fragmentos Combinados. Eles permitem que o projetista expresse algoritmos de forma detalhada diretamente no diagrama, aproximando o modelo do código-fonte.

  • Estrutura Visual: um operador é representado por um quadro (frame) retangular que envolve uma parte da interação.
  • Tag de Operador: no canto superior esquerdo, há um pequeno pentágono contendo uma palavra-chave (tag) que define o comportamento do quadro (ex: alt, loop, opt).
  • Operandos e Guardas: o quadro pode ser dividido em regiões (operandos) por linhas tracejadas. Cada região pode ter uma condição de guarda [condição], uma expressão booleana que deve ser verdadeira para que aquele fragmento seja executado.

2. Principais Operadores de Controle

Tag Nome Descrição Técnica e Exemplo
alt Alternativas Equivale a uma estrutura if-then-else. Contém múltiplos operandos; apenas aquele cuja guarda for verdadeira será executado. Se mais de uma for verdadeira, a escolha é não-determinística.
opt Opção Equivale a um if sem o else. O fragmento só executa se a guarda for verdadeira; caso contrário, é ignorado.
loop Laço Representa repetição. Pode incluir limites numéricos como loop(min, max). O fragmento repete enquanto a guarda for verdadeira e os limites forem respeitados.
par Paralelo Indica que as mensagens dentro dos diferentes operandos podem ocorrer simultaneamente ou em qualquer ordem (intercaladas), sem que uma dependa do término da outra.
break Interrupção Se a condição for atendida, o fragmento executa e o restante do diagrama (ou do quadro pai) é ignorado, funcionando como um return ou tratamento de exceção.
ref Referência Permite modularidade. O quadro aponta para outro diagrama de sequência já definido, facilitando o reuso de interações comuns (como uma "Autenticação").

3. Operadores Avançados e Especializados

  • critical (Região Crítica): garante que a sequência de eventos dentro do fragmento seja atômica, ou seja, não pode ser intercalada por outras mensagens de regiões paralelas.
  • neg (Negativo): descreve uma interação que é explicitamente proibida ou considerada inválida.
  • assert (Asserção): indica que o comportamento descrito é o único válido naquele ponto; qualquer outra variação é um erro.
  • ignore / consider: filtram quais mensagens são relevantes para aquela visão do diagrama, permitindo omitir detalhes irrelevantes para focar em uma lógica específica.

4. Sequenciamento Fraco (seq) vs. Estrito (strict)

Nem todo diagrama de sequência precisa exibir a ordem das mensagens de forma rígida. A UML distingue dois modos de interpretar a ordem vertical das mensagens:

  • seq (sequenciamento fraco) — padrão: mensagens em diferentes linhas de vida podem intercalar; a ordem é preservada apenas entre mensagens de uma mesma linha de vida ou que possuam dependência direta.
  • strict (sequenciamento estrito): a ordem vertical de cima para baixo deve ser seguida rigidamente por todos os participantes.

Exemplo Prático: Processamento de Pedido

Considere o cenário "Fechar Pedido". Os operadores de controle são usados em conjunto para expressar a lógica completa do fluxo:

  • Operador loop: o sistema percorre cada item do pedido para verificar estoque.
  • Operador alt:
    • [estoque disponível]: reserva o item.
    • [else]: envia mensagem de "Item indisponível" ao cliente.
  • Operador opt: se o cliente for VIP, o sistema aplica um desconto especial automaticamente.
  • Operador par: simultaneamente, o sistema solicita a autorização do cartão de crédito e inicia a preparação da nota fiscal.
sequenceDiagram actor Cliente participant Sistema participant Estoque participant Pagamento participant Fiscal Cliente->>Sistema: fecharPedido() activate Sistema loop para cada item do pedido Sistema->>Estoque: verificarEstoque(item) alt [estoque disponível] Estoque-->>Sistema: disponível Sistema->>Estoque: reservarItem(item) else [else] Sistema-->>Cliente: "Item indisponível" end end opt [cliente VIP] Sistema->>Sistema: aplicarDescontoEspecial() end par [paralelo] Sistema->>Pagamento: autorizarCartão(valor) Sistema->>Fiscal: prepararNotaFiscal(pedido) end Sistema-->>Cliente: pedidoConfirmado deactivate Sistema

O mesmo fluxo traduzido para código: cada operador do diagrama encontra um equivalente direto na linguagem de programação. 

public void fecharPedido(Pedido pedido, Cliente cliente) {
    for (Item item : pedido.getItens()) {                       // loop
        if (estoque.verificarEstoque(item)) {                   // alt [estoque disponível]
            estoque.reservarItem(item);
        } else {                                                // else
            enviarMensagem(cliente, "Item indisponível");
        }
    }

    if (cliente.isVip()) {                                      // opt [cliente VIP]
        this.aplicarDescontoEspecial(pedido);
    }

    // par: as duas tarefas podem ocorrer simultaneamente
    CompletableFuture.allOf(
        CompletableFuture.runAsync(() -> pagamento.autorizarCartao(pedido.getValor())),
        CompletableFuture.runAsync(() -> fiscal.prepararNotaFiscal(pedido))
    ).join();

    enviarMensagem(cliente, "pedidoConfirmado");                // retorno ao ator
}

Break como tratamento de exceção

O operador break interrompe o restante do diagrama. No fluxo do pedido, se a autorização do cartão falhar, o processamento é encerrado antes da confirmação:

sequenceDiagram participant Sistema participant Pagamento Sistema->>Pagamento: autorizarCartão(valor) break [pagamento negado] Sistema->>Pagamento: cancelarReserva(item) Sistema-->>Sistema: registrarErro("pagamento negado") end Sistema->>Sistema: confirmarPedido() 
try {
    pagamento.autorizarCartao(valor);
} catch (PagamentoNegadoException e) {     // break [pagamento negado]
    pagamento.cancelarReserva(item);
    this.registrarErro("pagamento negado");
    return;                                 // ignora o restante do diagrama
}
this.confirmarPedido();                     // só executa se não houve interrupção

Representação Gráfica

Fragmento combinado: estrutura do quadro

sequenceDiagram participant A as A participant B as B alt [guarda 1] A->>B: mensagem1() else [guarda 2] A->>B: mensagem2() end opt [condição opcional] B->>A: resposta() end loop(min, max) [repetição] A->>B: processar() end

Tradução direta dos operadores para código: 

if (guarda1) {                    // alt [guarda 1]
    b.mensagem1();
} else if (guarda2) {             // else [guarda 2]
    b.mensagem2();
}

if (condicaoOpcional) {           // opt [condição opcional]
    b.resposta();
}

for (int i = 0; i < max; i++) {   // loop(min, max)
    b.processar();
}

Referência (ref) para reuso de interação

sequenceDiagram participant Usuario participant Portal Usuario->>Portal: acessarSistema() rect rgb(230, 240, 255) note over Portal: ref Autenticação(usuário, senha) end Usuario->>Portal: executarFuncionalidade()

No quadro ref, o nome "Autenticação" aponta para outro diagrama de sequência já definido, que descreve o detalhamento daquela interação.

Em código, o ref corresponde a uma delegação: a interação detalhada vive em outro método (ou serviço), reutilizado por vários cenários: 

public void acessarSistema(String usuario, String senha) {
    autenticar(usuario, senha);           // ref Autenticação(usuário, senha)
    executarFuncionalidade();
}

// Método que detalha o diagrama referenciado
private boolean autenticar(String usuario, String senha) {
    return repositorioDeUsuarios.validar(usuario, senha);
}

Região crítica dentro de um fluxo paralelo

sequenceDiagram participant T as Thread A participant D as Dado Compartilhado participant S as Thread B par [paralelo] T->>D: atualizar(valor) and S->>D: ler() end critical [região crítica] T->>D: atualizar(valor) D-->>T: ok end

Em código, a região crítica corresponde a um bloco atômico que não pode ser intercalado por outras threads — no exemplo, um bloco synchronized que protege o dado compartilhado: 

public class DadoCompartilhado {
    private int valor;

    // par: leitura e escrita podem ocorrer em qualquer ordem entre threads
    public synchronized void atualizar(int novoValor) {  // critical
        this.valor = novoValor;                          // não pode ser intercalada
    }

    public synchronized int ler() {
        return this.valor;
    }
}

Dicas & Lembretes

  • Legibilidade: Martin Fowler alerta que o uso excessivo de quadros de interação pode tornar o diagrama mais confuso que o próprio código; use-os para clarificar o design, não para documentar cada linha de lógica.
  • Sentinela [else]: é recomendável usar a guarda [else] em blocos alt para garantir que o modelo seja bem-formado caso as condições primárias falhem.
  • Seqüenciamento: no seq (padrão), mensagens em diferentes linhas de vida podem intercalar; no strict, a ordem vertical de cima para baixo deve ser seguida rigidamente por todos os participantes.
  • Guarda com limites: o loop(min, max) combina a condição booleana com limites numéricos de repetição.
  • Reuso: utilize ref para interações comuns (autenticação, auditoria) em vez de duplicar o diagrama em vários cenários.

Como aplicar na Prática

  • Especificação de fluxos alternativos: use alt e opt para registrar os fluxos alternativos e de exceção dos casos de uso, entregando uma especificação completa à equipe de desenvolvimento.
  • Modelagem de concorrência: use par para representar processamentos paralelos reais (pagamento + emissão de nota) e critical para proteger trechos que não podem ser intercalados.
  • Tratamento de erros: use break e neg para documentar interrupções e interações inválidas que o sistema deve impedir.
  • Reuso de interações: extraia interações comuns para ref, mantendo os diagramas enxutos e facilitando a manutenção da documentação.
  • Controle da leitura: use ignore/consider para focar o leitor nas mensagens relevantes de uma visão específica do diagrama.
